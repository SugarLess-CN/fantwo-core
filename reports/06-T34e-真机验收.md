| # | 验什么 | 手段 |

## 二、功能变化（验收确认后的最终行为）

| 场景 | 改前（T-34 之前） | 现在（验收确认） |
|---|---|---|
| 改上传大小上限 | 改 `.env` + 重启 | `PATCH /config {"key":"upload_max_image_size","value":"7"}` → **下一个请求** `/upload/config` 立刻返回 `mb:7 / bytes:7340032`；真机传 8MB 文件被拒，报错文案带 DB 值 `8.0MB > 7MB` |
| 改单次上传文件数 | 同上 | `PATCH` 后 `/upload/config` 的 `maxFileCount` 从 10 变 3，立即生效 |
| 读配置项列表 | `GET /config` 返回 GORM 实体，**密钥明文** | 返回 `ConfigView`：字段集合与改前一致（`id`/`createdAt`/`updatedAt`/`key`/`value`/`description`/`type`/`group`/`public` 全在）+ 新增三个（`hasValue`/`masked`/`startupOnly`）；敏感项 `value` 恒为 `***` |
| 改密钥配置 | 直接写什么就是什么；前端回传打码值会把密钥清成 `***` | 敏感项传 `""` 或 `"***"` 一律**不写库**（验证：库里 `real-secret-123` 经过两次回写仍是 `real-secret-123`） |
| 创建启动期配置（`s3_bucket`） | 可以创建，创建后永远不生效、无任何提示 | **400 + 可执行提示**：「属于启动期配置（存储 / 搜索客户端在服务启动时按它初始化），写入数据库不会生效；请改环境变量或配置文件后重启服务才会生效」 |
| 匿名读公开配置 | 若有人误把 `s3_secret_key` 的 `public` 改成 true，密钥会匿名泄漏 | `/config/public` 只返回 `advertisement` / `cdn` / `site` / `search.search_enabled` 等公开项，敏感项与 `sensitive_words` 一律剔除 |
| 压缩开关 | 只是展示项，关掉后图仍被处理 | 真正控制「是否压缩 + 是否生成缩略图」；关掉后主图不重编码、`thumbnails` 为 `[]`（不再是 `null`） |
| ES 连接参数 | 改 `.env` + 重启 | 改 DB 后下一次用到 client 的请求按签名惰性重建 |

### 4.3 `EnsureSeeds` 幂等（起服务后有 42 条，没有变成 84）

```
$ docker exec postgre psql -U postgres -d fantwo_core -t -c "SELECT count(*) FROM config;"
    42

$ docker exec postgre psql -U postgres -d fantwo_core -t -c "SELECT count(*) FROM config WHERE key LIKE 's3_%';"
     0
```

**意义**：库里这 42 条里有 7 条是我在 T-34b3 之后手工 INSERT 的。服务启动时 `EnsureSeeds` 按 key 幂等检查（已存在则 skip），所以**没有重复插入**，也没有覆盖已有值 —— 手工 SQL 与种子保持了逐字一致。

### 4.4 敏感项读时打码

```
$ curl -X PATCH .../config -d '[{"key":"search_password","value":"real-secret-123"}]'
{"code":200,"message":"操作成功","data":{"skipped":0,"updated":1}}

$ curl .../config | grep search_password
{"id":"b23b20d2-...","key":"search_password","value":"***",
 "description":"Elasticsearch 密码（敏感：管理端返回打码）","type":"string","group":"search",
 "public":false,"hasValue":true,"masked":true,"startupOnly":false,
 "createdAt":"2026-11-23T02:44:23.943889+08:00","updatedAt":"2026-11-23T03:05:14.443451+08:00"}

$ docker exec postgre psql ... -t -c "SELECT value FROM config WHERE key='search_password';"

```

**意义**：API 返回 `***`，库里是真实值；`createdAt` / `updatedAt` 都在（改前的契约字段没有被删），且 `updatedAt` 确实是刚改的时间。

**意义**：`skipped:1, updated:0` 明确告诉调用方「本次没有真正写入」，而不是假装成功。

```

$ curl .../upload/config
"limits":{"maxFileCount":10,"maxSize":{"image":{"bytes":20971520,"mb":20},...}}

# 只改 DB（走 API，不重启进程）
$ curl -X PATCH .../config -d '[{"key":"upload_max_image_size","value":"7"},{"key":"upload_max_file_count","value":"3"}]'
```

**意义**：`mb:7` 与 `bytes:7340032` 满足 7×1024×1024，**mb 与 bytes 同源**（不是算两遍各自读配置）。`uptime:153` 证明是同一个进程，没有重启。

**意义**：不只是展示层变了，**校验逻辑也用 DB 值**，且报错文案里的 `7MB` 就是刚从 DB 改的值。

## 五、遗留与风险

| # | 项 | 说明 |
|---|---|---|
| 1 | **SQL 直改库有 ≤10 分钟延迟** | `configCacheTTL` 保持 10 分钟（用户已决策不收窄）。走后台 API 改会立即 `invalidate`（本轮全部验收都是走 API，故立即生效）；用 SQL 直接改库则要等 Redis 缓存过期。**运维改配置应走 API** |
| 2 | **ES 参数有 ≤1 秒快照延迟** | `searchParamsTTL = 1s`（为了压住 bulk 每行一次 `Index()` 的放大）。改 `search_*` 后最多 1 秒 + 一次请求才生效 |
| 3 | **S3 分支未真机验证** | 本机拉不到 minio 镜像（T-32 阻塞），S3 三分支（压缩开/水印/跳过）只有单元层保证 |
| 4 | **主图压缩版缺口（T-35）** | 压缩开启时原实现会另存 `<filename>-original.webp`，Go 侧只出缩略图。已拍板独立任务 |
| 5 | **`withThumbnails` 统计口径（T-36）** | `migration.go:72` 把 jsonb `'null'` 算成「有缩略图」，压缩关闭后误差放大 |
| 6 | **`config` 表主键仍是 `character(36)`** | 其它表已改 `varchar(36)`，这张表是遗留。本次插入的 UUID 正好 36 字符未触发空格填充，但类型不一致仍在 |
| 7 | **老库残留 S3 行** | 若某环境历史上手工插过 `s3_*` 配置，四个写入口已拒改，但读接口会返回它们（带 `startupOnly:true`）。清理需一次性 SQL：`DELETE FROM config WHERE key LIKE 's3_%' OR key='storage_driver'` |
| 8 | **`search_password` 验收后留了测试值** | 库中当前是 `real-secret-123`。若该库要继续用于开发，应清空：`UPDATE config SET value='' WHERE key='search_password'` |
