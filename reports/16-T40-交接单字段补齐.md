## 三、三个技术判断

### 3.1 `sort_by` 后端早就实现了（交接单半错）

前端说「评论排序点了没反应」。实际：
- `handler/comment.go:24` 一直在读 `sort_by`
- `repository/comment.go` 的 `commentOrder()` 三档齐全 + **`is_pinned DESC` 打头**（置顶恒最前）
- 未知值走 `default` 回落，不 400

**缺的只是 swagger 声明** —— 前端按 spec 生成 SDK 时 `sortByParam` 无处可传，所以看起来「没反应」。
所以只补注解，**没动排序逻辑**（也没让它变成另一种排序）。

### 3.2 `read-all` 只补参数是不够的（真 bug）

站内消息有**两套已读载体**：
- 广播（`is_broadcast=true`）→ 已读在 `message_read` 回执表
- 个人（`is_broadcast=false`）→ 已读是行内 `is_read` 列

原实现 `if is_broadcast { 标广播 } else { 标个人 }` 是**二选一**。
前端只传 `?type=system` → 走 else → **广播型通知永远标不掉**。

真机对比：
```
只补注解：?type=system 之后 → system 仍是未读   ← 就是「点了没反应」
两种都标：?type=system 之后 → system=0，另两条未动 ✅
```

### 3.3 `GET /user/{id}` 恢复公开的连带安全修复

只改路由不够：`Wallet: u.Wallet` 是无条件赋值，`FindUser` 还填 `view.Config`。
一旦公开，匿名能看他人真实余额 + 用户配置（佣金比例、隐私开关）。

已在 `FindUser` 里按「是不是自己」收口：
```go
if actor.UserID != "" && actor.UserID == id {
    view.Config = s.configOf(ctx, id)   // 只有自己
} else {
    view.Wallet = 0                      // 他人一律 0
}
```

真机：`匿名看他人 → wallet=0, config 不存在` / `自己看自己 → config 存在, is_followed=false`。

### 3.4 `equipped_decorations` 的 key 必须大写

原 NestJS `user-decorator.util.ts:114`：
```typescript
equippedDecorations[decoration.type] = transformDecorationToFrontend(decoration)
```
key 就是 `decoration.type` 原值，而该枚举是大写（`AVATAR_FRAME` / `COMMENT_BUBBLE` / `ACHIEVEMENT_BADGE`），
我们 DB 存的也是大写。

> 不违反「全站 snake_case」：那条规则管**字段名**，这是 map 的**动态 key**（key 本身是枚举取值）。

## 五、遗留与风险

### 5.1 浏览历史「同一天看两次两条」**不做**（有明确依据）

原 NestJS 就是唯一索引 + 计数：
```typescript
// article/entities/browse-history.entity.ts:15
@Index(["userId", "articleId"], { unique: true })
@Column({ type: "int", default: 1, comment: "浏览次数" })  viewCount: number;
```
同一用户 + 同一文章 = 一行，重复浏览 `viewCount++`。这是**有意的产品语义**
（历史列表里同篇文章出现多次是噪音）。

`id` 已给出 → 前端 `keyExtractor` 问题解决。
若要「浏览流水」是新需求：另建 `browse_events` 表存流水，`browse_history` 保持聚合。

### 5.2 数据完整性：存在孤儿数据

排查 `AuthorBriefDto` 时发现：有文章 `author_id = e879b777-…` 在 `user` 表**不存在**。
是历史测试残留。

不影响功能（`author` 为空，前端不渲染作者块），但说明**文章表缺少对用户的引用完整性**。
建议后续加外键约束或定期清理脚本。

### 5.3 各成员报告的遗留（已评估，本轮不做）

| 项 | 评估 |
|---|---|
| 写接口（`POST/PATCH /comment`）不带内嵌 `article`/`parent` | 读路径够用，写接口前端本地已有数据；要加是 2 处 × 1 次预取 |
| 管理端 `/comment` 的 `sort_by` 硬编码 `latest` | 注解照实写（没骗人），要接是 1 行，属行为变更 |
| `parent` 只有一层（不追 root） | 与前端「回复 @某某」需求一致；要整链需前端自己拼 |
| `UpdateUser` / `UpdateContact` 返回不带 `equipped_decorations` | 保守未动，要一致是两行调用 |
| `required_likes`/`required_comments` 只对活动来源的装饰填 | **正确语义**（装饰表本身无此列，门槛在活动上），非假契约 |
