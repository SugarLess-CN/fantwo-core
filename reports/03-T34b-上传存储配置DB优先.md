## 一、本轮改了什么

### 1. 新增：运行期可调项统一读取层（`storage.go:968-1058`）

原来每个读取点各自拼「env 值 → 默认值」，DB 覆盖散落在个别函数里。现在抽成一组包内私有辅助函数，全部遵循 `watermark.go:183-196` 的范式（① env 兜底 ② `cfgSvc` 非 nil 时 DB 优先）：

| 函数 | 行号 | 作用 | DB key |
|---|---|---|---|
| `uploadLimitMB(key, envMB, defMB)` | 976-986 | 单类型上限定值（含 `mb<=0` 回落默认） | 由调用方传 `upload_max_*_size` |
| `uploadMaxFileCount()` | 988-998 | 单次文件数上限 | `upload_max_file_count` |
| `compressionEnabled()` | 1000-1010 | 图片压缩总开关 | `upload_compression_enabled` |
| `localDirRoot()` | 1012-1022 | 本地存储根目录（空值 → `./uploads`） | `storage_local_dir` |
| `cdnBaseURL()` | 1024-1034 | CDN 前缀（去空格） | `cdn_base_url` |
| `thumbnailSpecs()` | 1036-1058 | 缩略图规格（JSON 解析 + 脏数据过滤 + 兜底） | `upload_thumbnail_specs` |

`thumbnailSpecs()` 的解析策略：DB 值去空格后非空才尝试 `json.Unmarshal` 成 `[]config.ThumbSpec`；解析成功但仍需过滤 `Size<=0` 的项，过滤后为空则**整体回退 env 值**；env 值也空时兜底单档 `{thumb,200}`。任何脏数据都不会让缩略图生成中断。

### 2. `checkSize`（`storage.go:434-469`）

- 改前：`switch kind` 取 `f.cfg.Upload.MaxXxxMB` → `if maxMB<=0` 再一轮 `switch` 设 `DefaultMaxXxxMB` → 再 `if f.cfgSvc != nil` 第三轮 `switch` 选 key → `GetInt`。三段 switch 重复表态。
- 改后：一次 `switch` 同时给出 `key / envMB / defMB`，然后 `maxMB := f.uploadLimitMB(key, envMB, defMB)`。
- 行为等价，意义在于**与 `/upload/config` 展示共用同一实现**，不会出现「前端看到 5MB、后端按 20MB 拒绝」。

### 3. `HandleUpload` 的 maxCount（`storage.go:137-141`）

- 改前：`maxCount := f.cfg.Upload.MaxCount`（裸读 env，后台改成 3 也不生效）。
- 改后：`maxCount := f.uploadMaxFileCount()`。
- 这条不在任务书的 A 段里，但它是 `upload_max_file_count` 的**真实执行点**：只改 `/upload/config` 展示而不管真实校验，会让前端限制与后端行为不一致，故一并收敛。

### 4. `uploadOne` 的本地落盘目录（`storage.go:249-252`）

- 改前：
  ```go
  if f.cfg.Storage.LocalDir == "" { f.cfg.Storage.LocalDir = "./uploads" }  // 回写共享配置
  storedPath = filepath.Join(f.cfg.Storage.LocalDir, filename)
  ```
- 改后：
  ```go
  localDir := f.localDirRoot()
  storedPath = filepath.Join(localDir, filename)
  ```
- 顺带消除一处并发隐患：原来在请求路径上写 `f.cfg.Storage.LocalDir`，多个上传请求并发时会形成对同一 `*InfraConfig` 字段的并发写。

### 5. `ensureThumbnails`（`storage.go:429`）

- 改前：`specs := f.cfg.Upload.ThumbnailSpecs` + 空则单档兜底。
- 改后：`specs := f.thumbnailSpecs()`。

### 6. `localURL`（`storage.go:552-573`）

两处改动，都是**一致性必需**，不是可选优化：

- `filepath.Rel(f.cfg.Storage.LocalDir, path)` → `filepath.Rel(f.localDirRoot(), path)`。
  若只把写入目录改成 DB 值而不改这里，`Rel` 会用「旧 env 目录」去减「新目录下的绝对路径」，结果是一条 `../../..` 式的相对路径，前端拿到的 URL 直接坏掉。
- CDN 前缀 `f.cfg.CDN.BaseURL` → `f.cdnBaseURL()`。

### 7. `LocalDir()`（`storage.go:574-580`）

- 改前：driver 判定 → 空则 `./uploads` → 返回 `f.cfg.Storage.LocalDir`。
- 改后：driver 判定 → 直接 `return f.localDirRoot()`。
- 该方法供静态文件路由挂载 `/uploads`，与写入目录必须同源。

### 8. `s3AccessURL`（`storage.go:589-611`）

- CDN 前缀改用 `f.cdnBaseURL()`（DB 优先）。
- **endpoint / bucket / useSSL / forcePathStyle 保持 env**，并在注释里写明原因：minio client 在 `New()` 期固定（`storage.go:97-101`），若此处改用 DB 值，URL 里的桶名会与实际读写目标错位——改桶之后，历史文件落在老桶、`removeStored` 却去新桶删，直接删不掉。

### 9. `removeStored` 的目录穿越判断（`storage.go:824`）

- 改前：`if strings.HasPrefix(path, f.cfg.Storage.LocalDir)`。
- 改后：`if strings.HasPrefix(path, f.localDirRoot())`。
- 这是任务书特别点名的必改项：前缀与写入目录不同源时，把 `storage_local_dir` 改成 DB 值之后，删除判断必然不命中，文件永远留在盘上。

### 10. `GetUploadConfig`（`storage.go:834-933`，`/upload/config`，NoAuth）

- 4 个 `mb`（`storage.go:836-839`）：先各算一次 `uploadLimitMB`，再由 `const mbBytes` 统一换算 `bytes`。**mb 与 bytes 用同一个变量**，不再像改前那样每个字段各读一次（改前甚至 `mb` 与 `bytes` 是两次独立读取，理论上可被并发改配置撕开）。
- `limits.maxFileCount`（909）：`f.uploadMaxFileCount()`。
- `imageProcessing.compressionEnabled`（906）：`f.compressionEnabled()`。
- `s3` 段（848-869）：**只有 `cdnDomain` 走 DB**（`f.cdnBaseURL()`）。五项 `region / bucket / endpoint / useSSL / forcePathStyle` **直接读 `f.cfg.S3.*`，完全不碰 DB**——`storage.type` 同理保持 env。
- `watermark` 段（871-883, 921-927）：与 `watermark.go` 的 `watermarkOptions` **同 key 常量、同默认值**——`model.ConfigKeyUploadWatermarkEnabled` / `...TextTemplate`（默认 `{nickname}`）/ `...Position`（默认 `bottom-right`）/ `...OpacityPercent`（默认 55 → 0.55）。改前这三个值是写死的字面量，导致后台改了水印模板，前端预览仍显示旧值。
- `compression` / `videoProcessing` 两段纯前端提示参数**未改**（按任务书 A6）。

### 11. `s3_image.go:121`

- 改前：`specs := f.cfg.Upload.ThumbnailSpecs` + 空则单档兜底（与 `ensureThumbnails` 是同一份重复逻辑）。
- 改后：`specs := f.thumbnailSpecs()`。S3 图片链路与本地链路规格同源。
- 连带：`internal/config` 在该文件已无引用，移除 import。

### 12.（第二轮）压缩开关三分支落地：`processImageThumbnails`（`storage.go:355-423`）+ `processS3Image`（`s3_image.go:55-173`）

第一轮只把 `upload_compression_enabled` 接成展示项，lead 核原实现后裁定「这是复刻漏掉的功能」，必须真正生效。语义对齐 `tmp/picart/src/modules/upload/upload.service.ts:332-373`：

| 条件 | 本地链路行为 | S3 链路行为 |
|---|---|---|
| `compression=false && needWatermark=false` | 整体跳过：不重编码、不生成缩略图，`processed=true` 后 return | 跳过：**不下载、不回传**，`processed=true` 后 return |
| `compression=false && needWatermark=true` | 只打水印（`applyWatermarkToFile`，必然重编码主图）+ 写 `original` 元数据，**不生成缩略图** | 下载 → 解码 → 画水印 → 回传主图 + 写 `original`，**不生成缩略图、不写 thumbnails 字段** |
| `compression=true` | 水印（如需）+ 按 `thumbnail_specs` 生成缩略图（= 第一轮行为） | 水印（如需）+ 缩放 + 缩略图（= 第一轮行为） |

三处实现细节：

1. **`processed` 置 true 而不是留 false**。`processed` 在 Go 侧是「该图已决最终态」的补偿标记，`migration.go:100` 按 `processed=false` 拣选补处理；跳过时留 false 会被 `/upload/migration/process` 反复挑中重跑。
2. **水印判定复用 `watermarkOptions(up)`**，没有另写一套：它已经包含 `upload_watermark_enabled` + `SceneAvatar` 排除 + 模板替换后非空三重条件。改造后每个处理函数只调用一次（原来本地/S3 各调一次，现在提前算好复用）。
3. **S3 压缩关闭时不写 `thumbnails` 字段**（`s3_image.go:166`）：保持库里原值，而不是覆盖成 `null`/`[]`。本地链路同理——跳过时根本不进 `Updates`。

### 13.（第二轮）水印 key 常量化

`storage.go` 里 4 个字符串字面量（`"upload_watermark_enabled"` 等）改为 `model.ConfigKeyUploadWatermark*`；`watermark.go` 的 4 个字面量不在本成员写作用域，未动（lead 另派）。

## 二、功能变化（对用户/前端/运维可见）

| 配置项 | 改前行为 | 改后行为 |
|---|---|---|
| 4 类上传上限 | `MaxImageMB` 等只读环境变量，改 env 必须重启 | 后台改 `upload_max_*_size` → 下一请求生效，`/upload/config` 与真实校验同步变 |
| 单次文件数 | `/upload/config` 展示 env 值；真实校验也是 env 值（两处各读一次） | 展示与校验都读 DB，且共用 `uploadMaxFileCount()` |
| 图片压缩开关 | `/upload/config` 展示 env 值（且是裸读），**关掉也照样压缩、照样生成缩略图** | 读 DB；关掉后真正跳过处理（压缩+缩略图都不做），但水印仍独立生效；展示值与真实行为同源 `compressionEnabled()` |
| 缩略图规格 | 只认 yaml/env 的 `thumbnail_specs`（四档） | 后台改 `upload_thumbnail_specs` 的 JSON 即可换档位/尺寸；本地与 S3 两条链路同时生效 |
| 本地存储目录 | env `local_dir`，且写入时会回写该字段 | DB `storage_local_dir` 优先；写入、URL 生成、删除前缀判断、静态路由四处同源 |
| CDN 前缀 | env `cdn.base_url` | DB `cdn_base_url` 优先；本地文件 URL 与 S3 访问 URL 同时跟随 |
| S3 展示信息 | env 值 | **仍是 env 值（第二轮回退）**：五项不迁，避免「展示 B、实际写 A」的假配置；`cdnDomain` 例外，走 `cdn_base_url` |
| 水印参数 | `enabled` 读 env，`template/position/opacity` 是写死的 `{nickname}`/`bottom-right`/`0.55` | 四项全部读 DB（key 用 `model.ConfigKeyUploadWatermark*` 常量），且与真正叠加水印的 `watermark.go` 同源 |
| 单次上传并发 | 并发上传会写 `f.cfg.Storage.LocalDir`（共享配置并发写） | 不再回写配置，只取局部变量 |
| 关掉压缩后的上传响应 | 不适用（开关原本无效） | `thumbnails` 为 `null`（不是 `[]`）；`processed=true`；`original` 仍有宽高；水印关时 `size` = 上传原始字节数（未重编码） |

对前端无 JSON 结构变化：字段名、层级、类型全部保持不变，仅取值来源从 env 变成 DB（`opacity` 仍是 float，`mb`/`bytes` 仍是 int）。

## 七、T-34b5 追加：thumbnails 契约与补处理链路对齐

写作用域本轮扩至 `internal/handler/upload.go`、`internal/service/infra/migration.go`。未碰 `internal/handler/config.go`（cfg-mask 正在改）。

### 7.1 `thumbnails` 契约：`null` → `[]`（`handler/upload.go:355-386`）

- 改前：`out["thumbnails"] = infraJSONOrNil(up.ThumbsJSON)`。压缩关闭时 `ThumbsJSON` 是 jsonb `'null'`，`infraJSONOrNil` 解出 `nil`，响应给前端 `"thumbnails": null`。
- 改后：`out["thumbnails"] = infraThumbnailsOrEmpty(up.ThumbsJSON)`，新增函数 `infraThumbnailsOrEmpty`（`handler/upload.go:370`）：空串 / `'null'` / 非法 JSON / 解析出 nil → 一律 `[]interface{}{}`。

**为什么不改 `infraJSONOrNil`**：它是通用工具，被 4 个字段共用（`original` / `thumbnails` / `videoCompressionJob` / `auditResult`）。前三个里 `original`、`videoCompressionJob`、`auditResult` 的「无值」语义就该是 `null`（nullable 对象），只有 `thumbnails` 是集合类型——**集合的空值是空数组，不是 null**。所以只在调用点兜底，其它字段保持原样。

契约意义：前端可以无条件 `thumbnails.forEach(...)` / `.length` / `.map(...)`，不再需要 `?.` 或 `|| []` 防御。库里的 jsonb 值**不变**（仍是 `'null'`），只是响应层做了集合语义归一——这样不触发数据迁移，也不影响 `migration` 的既有统计条件。

### 7.2 补处理链路加开关判断（`migration.go:110-152`）

- 改前：`MigrationProcess` 对每条 `processed=false` 的记录**无条件** `ensureThumbnails`。运维在压缩关闭状态下跑一次补处理，缩略图照样生成——开关语义被绕开，跟「假开关」是同一类毛病。
- 改后：批次开头算一次 `compression := f.compressionEnabled()`（`migration.go:113`，与本地/S3 实时链路同一函数）；`if !compression { ... }` 分支（`migration.go:131`）：
  - **跳过 `ensureThumbnails`**（不生成缩略图）；
  - **仍补 `original` 元数据**（仅当缺失时）：宽高与压缩无关，前端排版需要；
  - **`processed` 置 true**，并计入 `Skipped` 而非 `Processed`。

**为什么置 `processed=true`（lead 要求写清取舍）**：本端点的拣选条件是 `processed = false`（`migration.go:100` 的 `Where`）。若不置 true，压缩关闭期间上传的记录会永远留在待补队列里，每次调用都被挑中、每次都被跳过——形成噪声，并让 `stats` 的 `unprocessed` 永久虚高。语义上「压缩关闭 ⇒ 这类记录本就不该有缩略图」就是它们的最终态，与实时链路 `processImageThumbnails` 的处置（同样置 true 后 return）一致。
**计入 `Skipped` 而非 `Processed`**：`Processed` 的口径是「本次真的生成了缩略图」，压缩关闭的没生成，混淆它会让运维从返回里看不出真实产出。

### 7.3 只记录不改（`migration.go:72`）

`WithThumbnails` 的 `thumbnails IS NOT NULL` 把 jsonb `'null'` 算进「有缩略图」。见 R10。没改：它牵动统计 SQL 与前端展示口径，且是改动前既有口径，超出本批。
