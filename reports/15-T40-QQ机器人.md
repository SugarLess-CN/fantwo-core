# 15 — T-40 QQ 官方机器人：发邀请码 + 后台对话

> 用户需求：用 QQ 官方机器人发放邀请码，做成**独立第三方 SDK**；暴露发送消息 / 拉申请名单 /
> 拒绝发送等接口；核心难点是**时效窗口过期后消息要留在池子里等激活**。
> 后续明确「不止邀请码，是发送消息」+「支持后台通过机器人和用户聊天」。

## 二、值得记下的两个技术发现

### 2.1 官方 DEMO 的签名值不可复现（不能当验收标准）

官方「安全和授权」页给了两段 DEMO：

| 锚点 | 内容 | 结果 |
|---|---|---|
| A | secret → publicKey | ✅ **逐字节匹配** |
| B | secret + body + timestamp → sig | ❌ **无法复现** |

锚点 B 穷举了 60 种合理解释全部不匹配：
- 3 种 seed 派生：repeat 截断 / 补零 / sha256
- 5 种 body 字节：原文 / 紧凑 / 尾换行 / 前后换行 / 尾空格
- 4 种拼接：`ts+body` / `body+ts` / `ts\n+body` / `ts+body\n`

**锚点 A 匹配而 B 不匹配 ⇒ 密钥派生正确，B 的 sig 本身是文档占位值。**

对策：**不拿错的锚点当验收标准**（会让写对的人怀疑自己），改为
「锚点 A 证明密钥派生 + 自洽锚点证明语义」：
- 自签自验必须过
- 任何字节改动（多空格 / 换 timestamp / 重新序列化）必须验不过

已固化为 `pkg/qqbot/anchor_test.go` 注释，后来人不必重复踩。

### 2.2 部分唯一索引（不是普通唯一索引）

官方明确「相同 `msg_id` 可能多次推送」，去重必须靠数据库约束（应用层「先查后插」
在并发 webhook 下仍会插两条）。但**出站消息的 `qqbot_msg_id` 允许为空**，
完整唯一索引会让所有空串互相冲突，第二条出站消息就插不进去：

```sql
CREATE UNIQUE INDEX uk_qqbot_message_msg_id
    ON qqbot_messages (qqbot_msg_id)
    WHERE qqbot_msg_id <> ''
```

已在 `internal/model/qqbot.go` 的字段注释里写明「**不要给它加 gorm uniqueIndex tag**」。

### 3.2 配置项（6 条种子）

`qqbot_enabled` / `qqbot_app_id` / `qqbot_app_secret`(敏感) / `qqbot_bot_secret`(敏感) /
`qqbot_invite_auto_reply` / `qqbot_invite_command`

**`qqbot_api_base` 与 `qqbot_token_url` 刻意不进种子**：代码有默认值，且
`qqbot_token_url` 会命中 `_token` 命名兜底被误判为敏感（详见 §一.4 第 6 条）。

### 3.3 池子状态机

```
PENDING ──成功──→ SENT
   │                 ↑
   ├─窗口过期→ DEFERRED ──用户发新消息──┘
   ├─可重试→ PENDING（指数退避 1m/5m/15m/1h，到 6 次转 DEFERRED 不丢）
   └─永久失败→ FAILED
```

### 4.4 真机全链路（端口 4121）

**① 三张表 + 部分唯一索引自动建出**

```
qqbot_invite_applications | qqbot_messages | qqbot_outbox

CREATE UNIQUE INDEX uk_qqbot_message_msg_id ON public.qqbot_messages
    USING btree (qqbot_msg_id) WHERE ((qqbot_msg_id)::text <> ''::text)
```

**② webhook 推送 → 落库 + 建申请单 + 自动回复进池**

```
HTTP 200  body: {}

qqbot_messages:            INBOUND | 我要邀请码 | ROBOT1.0_t41msg001 | T41_OPENID_001
qqbot_invite_applications: PENDING | 我要邀请码 | ROBOT1.0_t41msg001 | T41_OPENID_001
qqbot_outbox:              AUTO_REPLY | FAILED | attempts=1 | last_kind=config | last_code=100007
```

`100007 appid invalid` → `config` → `FAILED`（假 appid，映射正确）

**③ 幂等：重复推送 2 次仍各 1 条**

```
messages=1
applications=1
```

**④ 审批通过 → 分配邀请码 + 关联 invites 表 + 建池任务**

```
申请单: APPROVED | code=INVNQC5HURJR | invite_id=cc361393-3... | note=T41真机验证
池子:   INVITE_CODE | FAILED | "你的邀请码：INVNQC5HURJRHPEM\n注册时填写即可" | config/100007
```

**⑤ 二次审批 → `10005 conflict`（幂等保护）**

**⑥ ★ 核心验证：`DEFERRED` 留池 + 用户发消息激活**

把 `INVITE_CODE` 那条改成 `DEFERRED`（模拟窗口过期），再推一条该用户的新消息：

```
激活前: INVITE_CODE → DEFERRED, reply_msg_id='', reply_msg_at=NULL
推送:   {"id":"EVT-T41-002", "d":{"id":"ROBOT1.0_t41msg002", "content":"什么时候给我码"}}
激活后: INVITE_CODE → reply_msg_id='ROBOT1.0_t41msg002'（已换成新消息）→ 重投
```

**这正是用户要求的语义**：窗口过期不丢消息，等用户再次开口才发。
（本例因假凭据重投后进 `FAILED`，真凭据下会 `SENT`。）

**⑦ 配置移除两个 URL 键后行为不变**

`GET /qqbot/status` 在种子只剩 6 条时仍 `configured: true`，`token_url` 读代码默认值：

```json
{"enabled": true, "configured": true, "webhook_ready": true,
 "app_id": "test_appid_123", "token_ok": false, "token_error": "config",
 "missing": [], "outbox_failed": 2, "pending_applications": 0}
```

## 五、遗留与风险

### 5.1 必须真机才能证伪的一条

**业务事件验签的头名**（`X-Signature-Ed25519` / `X-Signature-Timestamp`）在官方
webhook 页面只给了 op=13 的样例，业务事件的头名是从「安全和授权」页推出来的
（该页明确列了这两个头 + `timestamp+body` 算法，可信度高）。

但**真实平台推送从未验过** —— 首次与 QQ 平台联调时，若头名不同，只需改
`pkg/qqbot/webhook.go` 的两个常量，逻辑不动。

### 5.2 本轮不做（已明确排除）

| 项 | 理由 |
|---|---|
| WebSocket 长连接 | webhook 已够用，ws 引入常驻连接与重连复杂度 |
| 群聊发码 | 邀请码私密，只走单聊；但 SDK 已分开 `GroupUser` 结构，后续可加 |
| 富媒体 / 卡片 / 按钮 | 先用纯文本，`msg_type` 留扩展位 |
| 频道（Guild） | 与社区业务无关 |

### 5.3 需要产品确认

- **邀请码来源**：当前审批时自动生成（`INV...` 前缀）。若要走「邀请人有配额」的既有
  邀请体系，需要改成从 `invites` 表按 inviter 分配。
- **`qqbot_invite_command` 默认「邀请码」**：若用户发别的词（如「申请」）不触发申请单，
  只记会话。是否放宽匹配规则需产品定。

### 5.4 业务侧无测试的补偿

`qqbot-core` 成员写完代码后未交报告即停止，**没有写任何测试**。
lead 补了最关键的纯函数测试（窗口判断 / 失败去向 / 退避节奏），
但**未覆盖**：webhook handler 的幂等落库、审批的事务边界、worker 的捞取逻辑。
这三块目前只靠真机验证过（§4.4），建议下轮补 service 层接口注入测试
（参照 `internal/service/oauth_service_test.go` 的做法）。
