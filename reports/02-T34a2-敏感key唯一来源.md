## 二、功能变化

| # | 改前 | 改后 |
|---|---|---|
| 1 | 敏感 key 清单只能散落在 `config_service.go`、`handler/config.go` 里各自硬编码字符串数组，加一处忘一处 | 唯一来源 `model.ConfigSensitiveKeys` + `model.IsSensitiveConfigKey`，service/handler 一律薄包装调用，加新密钥项只改一处 |
| 2 | 新增一个名为 `xxx_password` 的配置项 → 管理端 `GET /config` 会把明文密码吐出来 | 命名兜底自动命中 → 自动打码（T-34c 落地后生效） |
| 3 | 无 | 种子与白名单的**一致性由测试守住**：新增密钥类种子忘补白名单 → `TestConfigSensitiveKeysCoverSeeds` 直接 fail |

**判定边界（实测，已写进函数注释防后人误改）**：

| key | 结果 | 原因 |
|---|---|---|
| `s3_access_key` / `s3_secret_key` / `search_password` | ✅ 敏感 | 白名单 |
| `foo_password` / `mail_password_backup` / `S3_SECRET_KEY_V2` | ✅ 敏感 | 含 `password` / `secret`（大小写不敏感） |
| `x_access_key` / `b_private_key` | ✅ 敏感 | 含 `access_key` / `private_key` |
| `refresh_token` / `a_token` | ✅ 敏感 | 含 `_token` |
| `tokenizer` | ❌ 不敏感 | `_token` 要求前导下划线，**故意避开这个经典误伤点** |
| `sensitive_words` | ❌ 不敏感 | `sensitive` 不在关键词表；敏感词表本身要明文展示（管理端要能看词表） |
| `search_username` | ❌ 不敏感 | 用户名不是密钥 |
| `s3_endpoint` / `cdn_base_url` / `upload_max_image_size` / `site_name` | ❌ 不敏感 | 非密钥项 |
| `""` | ❌ 不敏感 | 空串 |

## 五、遗留与风险

| # | 项 | 说明 |
|---|---|---|
| 1 | **打码尚未生效** | 本轮只提供判定函数，`GET /config` 仍返回明文。由 T-34c（`cfg-mask`）接上后才改变 API 行为。这属分工顺序造成的正常中间态 |
| 2 | **兜底规则的语义取舍** | 采用「宁可多打码也不漏」取向：`secret` 子串命中意味着 `xxx_secret_hint` 这类无害配置也会被打码。代价是管理员看不到原值（仍可 PATCH 改值），换来的是不会漏掉新增密钥项。若日后出现被误打码的非密钥项，正确做法是给它改名或从关键词表剔除，**不要**在 service 层开白名单例外 |
| 3 | **`_token` 漏判风险** | 形如 `tokensecret`（无下划线）不会被兜底命中。目前项目里没有这种命名，但新增时要注意：密钥类配置一律用 `_token` / `_secret` / `_password` 结尾 |
| 4 | **白名单与兜底是两套口径** | 兜底命中 ≠ 已打码（打码以白名单为准，兜底只是保险）。`TestConfigSensitiveKeysCoverSeeds` 就是为了强约束这一点；将来若想改成「兜底也打码」，测试需要同步调整语义 |
| 5 | **`model_test.go` 的格式改动混入本次提交** | 提交信息里要单独说明，避免 review 时误以为动了测试逻辑 |
