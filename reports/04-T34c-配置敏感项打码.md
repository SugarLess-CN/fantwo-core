**`buildUpdates` 的三条规则（PATCH 语义中心）**

1. `in.Value != ""` 且 `!skipValueUpdate(key, in.Value)` 才写 `value` 列；
   旧写法 `in.Value != "" || in.Type != ""` 会在「只改 type」时把 value 覆盖成空串 —— 该缺陷已修掉
2. `description / type / group` 非空才写；`public` 非 nil 才写（语义不变）
3. 敏感 key 拿到 `"***"` 或空串 → `value` 列不出现在 updates 里，库里保持原值

## 二、功能变化（对用户/前端/运维可见）

| 端点 | 改前行为 | 改后行为 |
|---|---|---|
| `GET /config` | 返回 `[]model.Config`，字段 `id/createdAt/updatedAt/key/value/description/type/group/public`，其中 `s3_access_key`/`s3_secret_key`/`search_password` 的 `value` 是**明文密钥** | 返回 `[]ConfigView`：**字段集合与改前一致（未删任何字段，`createdAt`/`updatedAt` 照旧下发）**，敏感项 `value="***"`，**仅新增** `hasValue`（后端是否已配置）、`masked`（本条是否打码）；非敏感项 `value` 原样 |
| `GET /config/group/:group` | 同上明文 | 同上打码（**跨出任务书的一处补强**，否则分组读取可绕过打码） |
| `GET /config/key/:key` | 同上明文 | 同上打码 |
| `GET /config/:id` | 同上明文 | 同上打码 |
| `PATCH /config/:id` | `value` 传空串时，若同时带了 `type` 会把 value 写成空串；敏感项传什么写什么 | 敏感项传空串或 `"***"` → 库值不变；非敏感项空串不写 value（`{"type":"number"}` 这类请求不再误清空 value）；响应体为打码视图 |
| `PATCH /config`（批量） | 响应 `{"updated": 请求条数}`，每条无条件写 value | 响应 `{"updated": 真实写库条数, "skipped": 跳过条数}`；敏感项空值/占位符与不存在的 key 都计入 skipped，库值不变 |
| `PATCH /config/group/:group` | 响应 `{"updated": 请求条数}` | 响应 `{"updated": 真实写库条数, "skipped": 跳过条数}` |
| `GET /config/public`（NoAuth） | 只删 `sensitive_words`，若有人把 `s3_secret_key` 的 public 改成 true，密钥会**匿名泄露** | 敏感项一律不下发（`isSensitiveKey` 兜底）+ `sensitive_words` 继续不下发 |
| `GET /config/advertisement`（NoAuth） | 无变化 | 无变化（只加兜底注释） |
| `GET /config/sensitive-words` | 明文词表 | **无变化**（明文字表是管理端职责，故意不打码） |
| `PATCH /config/:id` 改 `sensitive_words` | 写入后前缀树不重建（需额外调 clear-cache） | 写入后自动 `ReloadSensitiveWords()`（与批量路径行为统一） |

## 六、T-34c2 追加：启动期配置写入拦截（+ T-34c3 `startupOnly` 标记）

### 6.1 为什么加这一层

T-34b3 删掉 7 条 S3 种子，只堵住「启动时自动写入」；`POST /config` 仍能手工造一条
`s3_bucket` → 创建成功、永远不生效、还没有任何提示。这与「假配置比不迁移更危险」是同一个坑，
入口换成了 POST。本节的改动把所有运行期写入口统一堵住，并让读接口把这类行标出来。

### 6.2 改了什么（全部在 `internal/service/infra/config_service.go`）

| 位置（改后行号） | 改动 |
|---|---|
| **326–350** | 新增纯函数 `rejectStartupOnlyKey(key string) error`：空 key（含纯空白）放行 → 交给调用方各自的「key 不能为空」；`model.IsStartupOnlyConfigKey(key)` 命中 → 返回 `errcode.ErrBadRequest`。规则本体只在 `model.ConfigStartupOnlyKeys` 维护，service 侧零硬编码 |

- **写路径**：先判启动期 → 拒绝（否则打码毫无意义，密钥能被改成任意值）；
- **读路径**：按敏感打码（老库历史数据可能在，读出来必须遮住）。

`s3_access_key` / `s3_secret_key` 同时命中两者 → 响应里 `startupOnly=true` 且 `masked=true`，
测试用 `启动期与敏感同时命中-互不排斥` 与 JSON 契约里的 `startupOnly==true` 双重锁定，**没有**写成 if-else 互斥。

### 6.3 功能变化（对运维/前端可见）

| 入口 | 改前 | 改后 |
|---|---|---|
| `POST /config` `{"key":"s3_bucket",...}` | 201/200 创建成功，库里多一条永不生效的行 | **400**，文案点名 key 并说明「写库不生效，改环境变量 + 重启」 |

| `GET /config`（含老库残留的启动期行） | 只显示 value，前端不知道不可写 | 多 `startupOnly=true`，前端可置灰只读 |

### 6.6 遗留与风险（本节新增）

1. **`Create` 返回类型变更属「口径统一」，不是破坏性变更**：字段集合与 `List` 完全一致（`ConfigView`），
   前端只需一套解析；但若有调用方按 GORM 实体读过 `Create` 响应里没有的字段（本仓没有），需要知会。
2. **老库残留的启动期行不会被自动清理**：它们仍出现在 `GET /config`（带 `startupOnly=true`），
   `PATCH` 会 400。若要彻底清掉，需一条一次性 SQL（不在本次范围，属运维决策）。
3. **`UpdateAll` 整批 400 的取舍**：批量里混入一条启动期 key 会失败整批。选它是因为静默跳过会让调用方
   误以为都改了；若后续认为太重，可改为「计入 skipped + 返回 warning」，但当前更保守更安全。
4. **前端置灰只是提示，不是防线**：真正的防线是 service 层 400；前端漏判也不会写坏数据。
5. **仍未 git commit**：由 lead 统一提交。
