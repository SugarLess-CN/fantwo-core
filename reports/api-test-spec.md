# 接口测试规范（测试智能体必须严格遵守）

> 本文件定义**测试日志的强制格式**与**测试执行规则**。写日志时不遵守格式 = 日志作废。
> 最后更新：2026-11-25

---

## 一、两份产物

| 文件 | 性质 | 写入时机 |
|---|---|---|
| `reports/api-test-log.md` | **增量测试日志** | **每测完一个接口立即追加一条**，不许攒批 |
| `reports/11-picartgo-接口测试报告.md` | **最终技术报告** | 全部测完后一次性写 |

日志是流水，报告是结论。**日志不可事后补写**——时间戳必须是真实执行时间。

---

## 二、测试日志条目格式（强制，字段不可增删改名）

每测完一个接口，立即向 `reports/api-test-log.md` **追加**以下块：

```markdown
### [L-序号] YYYY-MM-DD HH:mm:ss ｜ METHOD /api/v1/path

**逻辑链**：链-<编号> <链路名>　｜　**步骤**：<本链第几步>

| 字段 | 内容 |
|---|---|
| 请求头 | `Content-Type: application/json`　`Authorization: Bearer eyJ...<后8位>`　`device-id: xxx` |
| 请求体 | `<原样请求体，敏感值打码>` |
| HTTP 码 | `200` |
| status_code | `0` |
| 响应体 | `<原样响应体，token 打码为 eyJ...<后8位>>` |
| 耗时 | `123ms` |
| 是否需要修改 | **否** / **是** |
| 修改内容 | `—` / `<具体改了什么：文件:行号 改前→改后>` |
| 有问题 | **无** / `<具体问题：期望 X 实际 Y>` |
| 结论 | **✅ 通过** / **⚠️ 通过但有问题** / **❌ 失败** |

**备注**：<可选。为什么这么测、有什么发现>
```

### 字段规则（逐条）

| 字段 | 规则 |
|---|---|
| `[L-序号]` | 全局递增，从 `L-001` 开始，**不重复不跳号** |
| `HH:mm:ss` | 真实执行时刻（`date +%H:%M:%S`），不许估 |
| `METHOD /path` | 完整路径含 `/api/v1` |
| 逻辑链 / 步骤 | 必须标注属于哪条链的第几步；独立接口写 `链-00 独立` |
| 请求头 | **只列有意义的**（Content-Type / Authorization / device-id / 特殊头）。Authorization 打码 |
| 请求体 | 原样。密码/token/密钥一律打码 |
| HTTP 码 + status_code | **两个都记**（本项目它们独立：HTTP 表示传输层，status_code 是业务码） |
| 响应体 | 原样，超过 800 字符可截断但需注明 `...(截断，完整 N 字符)` |
| 耗时 | curl 的 `time_total` |
| 是否需要修改 | 二选一，**不许写「待定」** |
| 修改内容 | 若「是」必须给 `文件:行号` 与改前→改后；若「否」写 `—` |
| 有问题 | 若「无」写 `无`；若有必须写**期望 vs 实际** |
| 结论 | 三选一。`⚠️ 通过但有问题` 用于「返回对了但契约/文案/性能有瑕疵」 |

## 三、逻辑链定义（按链路顺序测，链内必须顺序执行）

同一链内后一步依赖前一步的产物（token / id），**不许跳步或换序**。

| 链号 | 链路 | 覆盖要点 |
|---|---|---|
| **链-01** | 注册 → 登录 → 取用户信息 → 更新资料 → 改密码 → 重新登录 | 账号生命周期；含重复注册、弱密码、错误密码等异常 |
| **链-02** | 登录 → 发文章 → 列表查询 → 详情 → 更新 → 点赞 → 评论 → 收藏 → 删除 | 内容主链路；含越权改他人文章的负向用例 |
| **链-03** | 登录 → 上传图片 → 查上传记录 → 关联到文章 | 文件链路；含超大文件、错 MIME 的负向用例 |
| **链-04** | 登录 → 签到 → 查积分 → 查积分流水 → 查成就 | 运营链路；含重复签到幂等 |
| **链-05** | 登录 → 查分类/标签 → 按分类查文章 → 搜索 | 浏览链路；含不存在分类、空结果 |
| **链-06** | 登录 → 下单 → 查订单 → 取消订单 | 交易链路（不真实支付）；含库存/金额校验 |
| **链-07** | 未登录 → 访问需鉴权接口（批量） | **安全**：所有该 401 的必须 401 |
| **链-08** | 普通用户 → 访问管理员接口（批量） | **安全**：所有该 403 的必须 403 |
| **链-09** | OAuth 授权 URL → 回调（伪造 code）→ App 伪造 token → 绑定列表 → 解绑 | 第三方登录；重点验「伪造 token 被拦」 |
| **链-10** | 越权：用户 A 的 token 访问用户 B 的资源 | **安全**：IDOR 检查 |

**链-00**：不属于任何链的独立接口（如 `/health`、swagger、公开配置）。

## 四、执行规则

1. **先起服务，后测**。服务地址统一 `http://127.0.0.1:3990`（避开常用端口，防与常驻进程冲突）。
2. **每测一个接口立刻写日志**，不许测完一批再补。日志文件用**追加**，不覆盖。
3. **响应体必须来自真实 curl**，不许手写或推测。
4. **发现问题时的处理**：
   - 契约级问题（错误码错、字段名错、空数据是 null、文案中文）→ **记日志 + 立即修**，修完**重测一次**并追加一条 `[L-xxx] 复测`
   - 业务逻辑 bug → 记日志 + 修 + 复测 + 在最终报告单列一节
   - 需要改表结构 / 涉及安全机制 / 改动面超过 3 个文件 → **停下来报 lead**，不要自行大改
5. **不许为了「通过」而改测试断言**。接口错就修接口，不许放宽断言。若认为接口行为正确而测试预期错，在日志里写清理由。
6. **每个接口至少覆盖一种异常路径**（缺参 / 错 token / 不存在 id），除非该接口无入参。

## 五、最终技术报告结构（`reports/11-picartgo-接口测试报告.md`）

```markdown
# 11 — picartgo 接口测试技术报告

## 一、测试范围与方法
环境、启动方式、测试工具、时间窗口、总接口数、实际覆盖数

## 二、总体结果
| 指标 | 数值 |
|---|---|
| 测过的接口 | N |
| ✅ 通过 | N (%) |
| ⚠️ 通过但有问题 | N (%) |
| ❌ 失败 | N (%) |
| 发现并修复的缺陷 | N |
| 未修复（已记录） | N |

## 三、逻辑链实测结果
逐链：链号 / 链路 / 步数 / 结果 / 发现的链路级问题

## 四、发现的问题清单（按严重度）
| # | 严重度 | 接口 | 问题（期望 vs 实际） | 是否已修 | 修改内容 |
|---|---|---|---|---|---|
| 1 | P0 | ... | ... | 是/否 | 文件:行号 |

严重度定义：P0 安全/数据错误、P1 契约不符、P2 体验瑕疵、P3 建议

## 五、已修复的缺陷明细
逐条：症状 → 根因 → 改动 → 复测证据

## 六、与 Apifox 文档的差异
Apifox 定义 vs 实际实现，逐条列差异与判定（实现错 / 文档旧 / 双方都不对）

## 七、未覆盖与遗留
明确写出没测的、测不了的原因、建议后续怎么测

## 八、结论与建议
是否可交付、上线前必改项、后续测试建议
```

## 六、测试数据约定

- 测试账号统一前缀 `test_`，测试后**清理**（或明确标注「测试数据保留」并说明原因）
- 违反了唯一约束的测试数据（重复注册）必须用**确定的后缀**，便于清理
- 造出的数据不得污染既有 `testuser1` 等历史账号
