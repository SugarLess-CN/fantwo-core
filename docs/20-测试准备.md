### 3.3 登录拿 token

```bash
TOKEN=$(curl -s -X POST http://127.0.0.1:3999/api/v1/user/login \
  -H "Content-Type: application/json" -H "device-id: my-test-device" \
  -d '{"account":"test_user","password":"Test123456"}' \
  | grep -oE '"token":"[^"]+"' | cut -d'"' -f4)
echo "$TOKEN" | head -c 40      # 确认拿到了
```

⚠️ **`device-id` 请求头必填**（缺失返回 `20016`）。这是本项目相对原仓库新增的约束。

### 3.4 登录接口怎么传 token（真机实测 5 种方式，只有 1 种有效）

**登录响应**（`POST /api/v1/user/login`）：

```json
{
  "data": {
    "token": "eyJhbGciOiJIUzI1NiIs...",       ← access token，放 Authorization 头
    "refreshToken": "eyJhbGciOiJIUzI1NiIs...", ← 用来换新 access token，不要拿去调业务接口
    "user": {...},
    "username": "test_user",
    "id": "8f423bad-..."
  },
  "message": "Success", "status_code": 0, "trace_id": "...", "timestamp": ...
}
```

**token 在 `data.token`，不在顶层。**

**唯一的传递方式**：请求头 `Authorization: Bearer <token>`

```bash
curl -H "Authorization: Bearer $TOKEN" http://127.0.0.1:3999/api/v1/user/profile
```

**实测四种错误写法全部 401**（`internal/middleware/authz.go:104-112`）：

| 写法 | 结果 |
|---|---|
| `Authorization: Bearer <token>` | **200** ✅ |
| `Authorization: <token>`（少 `Bearer ` 前缀） | 401 |
| `?token=<token>`（query 参数） | 401 |
| `Cookie: token=<token>` | 401 |
| `Authorization: bearer <token>`（小写） | 401 |

**实现细节**（想改中间件时看这里）：

```go
h := c.GetHeader("Authorization")
token := strings.TrimPrefix(h, "Bearer ")  // 大小写敏感，且必须是 "Bearer "（带空格）
if token == h {                             // 没匹配到前缀 → 原样返回 → 判为未登录
    return nil, "", errcode.ErrNeedAuth
}
```

**几个必须知道的点**：

1. **`device-id` 请求头必填**（登录时）——缺失返回 `20016`。这是本项目相对原仓库新增的约束。
   同一 device-id 重复登录会更新该设备的记录，不是新建设备。
2. **access token 有效期 1h**，过期返回 `20001`（去登录）或 `20002`（权限变更，需刷新）——
   靠 `refreshToken` 换新的，不要拿 refreshToken 直接调业务接口。
3. **登出后 token 立刻失效**（服务端黑名单，Redis 存）。2026-11-25 修完 P0 后，
   **全部 10 个域**都校验黑名单了 —— 之前只有 user 域校验，其他 7 个域登出后仍可用。
4. **改了角色/权限后旧 token 不自动更新** —— JWT 里的 perms 是签发时快照。
   要么重新登录，要么后端 bump 权限版本（旧 token 会收到 `20002` 提示刷新）。

### 3.5 验证角色隔离（造完号先跑这三条）

```bash
# 管理员能看全站用户列表 → 200
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:3999/api/v1/user -H "Authorization: Bearer $ADMIN_TOKEN"
# 普通用户看不了 → 403
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:3999/api/v1/user -H "Authorization: Bearer $USER_TOKEN"
# 管理员能改他人资料 → 200（这条是反向验证：别把管理员也拦掉）
curl -s -o /dev/null -w "%{http_code}\n" -X PATCH http://127.0.0.1:3999/api/v1/user/<user_id> \
  -H "Authorization: Bearer $ADMIN_TOKEN" -H "Content-Type: application/json" -d '{"nickname":"x"}'
```

## 四、造数据必踩的四个坑（都是实测踩出来的）

### 坑 1：`deleted_at = 0` 表示未删除，**不是 NULL**

本项目用 `gorm.io/plugin/soft_delete`（`internal/model/base.go:28`），语义与 gorm 原生 `gorm.DeletedAt` **相反**：

| 插件 | 未删除 | 已删除 |
|---|---|---|
| `gorm.DeletedAt`（原生） | `deleted_at IS NULL` | 时间戳 |
| **`soft_delete.DeletedAt`（本项目）** | **`deleted_at = 0`** | Unix 时间戳（如 `1795576632`） |

**后果**：手工 `INSERT ... deleted_at = NULL` 造的数据，接口查不出来（返回空数组），**很容易误判成接口 bug**。

```sql
-- ❌ 错（插进去但查不到）
INSERT INTO user_oauth_binding (...) VALUES (..., NULL);
-- ✅ 对
INSERT INTO user_oauth_binding (...) VALUES (..., 0);
```

### 坑 2：`psql -c "多语句"` 是**单事务**

中间任何一句报错，**前面的 DELETE 全部回滚** —— 你以为清了，实际没清。

```bash
# ❌ 危险
docker exec postgre psql -U postgres -d fantwo_core -c "DELETE FROM a; DELETE FROM 不存在的表; DELETE FROM b;"
# ✅ 用文件 + ON_ERROR_STOP
docker exec -i postgre psql -U postgres -d fantwo_core -v ON_ERROR_STOP=1 -f /tmp/clean.sql
```

### 坑 3：`user_roles` 是纯联合主键表

只有 `user_id` + `role_id` 两列，**没有 id / created_at / deleted_at**。照其它表的习惯写 `INSERT ... (id, created_at, deleted_at)` 会直接报错。

```sql
-- ✅ 正确
INSERT INTO user_roles (user_id, role_id)
VALUES ('<uid>', '<rid>')
ON CONFLICT (user_id, role_id) DO NOTHING;
```

### 坑 4：改了角色后旧 token 的权限**不会自动更新**

JWT 里的 perms 是签发时的快照。改完角色要**重新登录**拿新 token（或后端 `bump` 权限版本让旧 token 返回 `20002`）。

## 五、常用 SQL 速查

```bash
# 进 psql
docker exec -it postgre psql -U postgres -d fantwo_core
```

```sql
-- 看用户 + 角色
SELECT u.id, u.username, u.status, string_agg(r.name, ',') AS roles
  FROM "user" u
  LEFT JOIN user_roles ur ON ur.user_id = u.id
  LEFT JOIN "role" r ON r.id = ur.role_id
 WHERE u.deleted_at = 0
 GROUP BY u.id, u.username, u.status ORDER BY u.username;

-- 看某用户的实际权限点
SELECT p.name
  FROM permission p
  JOIN role_permissions rp ON rp.permission_id = p.id
  JOIN user_roles ur ON ur.role_id = rp.role_id
  JOIN "user" u ON u.id = ur.user_id
 WHERE u.username = 'test_user' AND u.deleted_at = 0
 ORDER BY p.name;

-- 看某个第三方绑定（注意 openid/unionid 是 PII，只用于本地排查）
SELECT user_id, provider, channel, LEFT(openid, 8) || '...' AS openid_prefix, nickname
  FROM user_oauth_binding WHERE deleted_at = 0;

-- 看配置（敏感项也能看到明文，只用于本地）
SELECT "key", value FROM config WHERE "group" = 'oauth' AND deleted_at = 0 ORDER BY "key";

-- 看评论楼层（排查楼层重复）
SELECT article_id, floor, COUNT(*) FROM comments
 WHERE deleted_at = 0 GROUP BY article_id, floor HAVING COUNT(*) > 1;
```

## 六、测试数据命名与清理

| 约定 | 说明 |
|---|---|
| 账号前缀 | 一律 `test_`（如 `test_user`、`test_idor_a`）—— 便于 `DELETE ... WHERE username LIKE 'test_%'` 批量清 |
| 内容标题前缀 | 用 `T-<任务号>-` 或 `p0-` 等可识别前缀，别用「测试」这种泛词 |
| 测完必清 | 账号、文章、评论、订单、上传记录、绑定、上传的**物理文件** |
| 清不了的写清原因 | 比如「无 upload:delete 权限删不掉，已走文件系统删除」 |

**一条命令清干净（按依赖顺序）**：

```sql
DELETE FROM user_roles        WHERE user_id IN (SELECT id FROM "user" WHERE username LIKE 'test_%');
DELETE FROM user_device       WHERE user_id IN (SELECT id FROM "user" WHERE username LIKE 'test_%');
DELETE FROM user_config       WHERE user_id IN (SELECT id FROM "user" WHERE username LIKE 'test_%');
DELETE FROM user_oauth_binding WHERE user_id IN (SELECT id FROM "user" WHERE username LIKE 'test_%');
DELETE FROM comments          WHERE author_id IN (SELECT id FROM "user" WHERE username LIKE 'test_%');
DELETE FROM articles          WHERE author_id IN (SELECT id FROM "user" WHERE username LIKE 'test_%');
DELETE FROM "user"            WHERE username LIKE 'test_%';
```

> 但要保留 `test_admin` / `test_user`（文档基准账号）→ 清理时把它们的用户名排除掉。

## 九、已知的「看起来像 bug 但其实不是」

| 现象 | 真相 |
|---|---|
| `GET /article` 登出后仍 200 | 这是**公开接口**（文章列表不需要登录）。真正需要登录的是 `POST /article` |
| 发文返回 `status: PUBLISHED` 但库里是 `PENDING` | 审核流语义：提交即进待审队列，**不是 bug** |
| `GET /upload` 普通用户 `total=0` | 降级设计：无 `upload:manage` 只能看自己，**不是漏洞** |
| 不存在路径返回纯文本 `404 page not found` | gin 原生 404 未接管（已知 P2，待修 `NoRoute`） |
| 会员订单 `authorId` 是 `"1"` | 平台单的哨兵值，不是真实用户 ID（已知 P3） |
| 自动签到有记录但积分余额 0 | `DAILY_LOGIN` 积分活动未启用（数据问题，非接口缺陷） |
