## 1. 总览

### 1.1 支持矩阵

| 平台 | 渠道 | 授权方式 | 后端端点 | 状态 |
|---|---|---|---|---|
| 微信 | web（PC 扫码） | 前端 302 到微信授权页 | `GET /user/oauth/wechat/web/url`、`GET+POST /user/oauth/wechat/web/callback` | ✅ 已实现 |
| 微信 | app（App 内 SDK） | 客户端 `WXApi.sendAuthReq` → 交 code | `POST /user/oauth/wechat/app/login` | ✅ 已实现 |
| QQ | web（网页登录） | 前端 302 到 QQ 授权页 | `GET /user/oauth/qq/web/url`、`GET+POST /user/oauth/qq/web/callback` | ✅ 已实现 |
| QQ | app（移动端 SDK） | 客户端 `Tencent.login` → 交 access_token+openId | `POST /user/oauth/qq/app/login` | ✅ 已实现（**待补 qq_app_appid**） |
| GitHub | web | 前端 302 到 GitHub 授权页 | `GET /user/oauth/github/url`、`GET+POST /user/oauth/github/callback`（既有端点，已迁移到 SDK） | ✅ 已实现 |

全前缀 `/api/v1`。共 **8 个核心端点**（微信 4 + QQ 4）+ GitHub 既有 3 条。

### 1.2 登录流程（文字版）

**Web 渠道（微信扫码 / QQ 网页 / GitHub，三者同构）：**

```
① 前端 GET /user/oauth/<p>/web/url
   → 后端生成随机 state 写入 Redis（10 分钟 TTL，fail-closed：写不进 Redis 直接 503）
   → 返回 {url, state}
② 前端 302 / 弹窗打开 url → 用户在平台授权页确认
③ 平台 302 回 redirect_uri?code=CODE&state=STATE（redirect_uri 指向后端 callback 端点）
④ 后端校验 state（一次性消费，防重放；渠道间互不串用）→ 用 code 向平台换 token → 拉用户信息
⑤ 账号归属判定（unionid → openid → GitHub email → 建新号，见 §5）→ 签发本站双 token
   → SPA 模式（POST callback）直接 JSON 返回；重定向模式（GET callback）302 回前端地址带 token
```

**微信 App：**

```
客户端微信 SDK sendAuthReq → 得 code（可信，SDK 换不到 token）
→ POST /user/oauth/wechat/app/login {"code": "..."}
→ 后端用 appid+secret 换 token（无 state；token 是后端自己换的，天然可信，无需校验）
→ 拉用户信息 → 账号归属 → 双 token
```

**QQ App（与微信 App 的关键差异：token 不可信）：**

```
客户端 QQ SDK Tencent.login → 直接得 access_token + openid（后端不换 token）
→ POST /user/oauth/qq/app/login {"accessToken": "...", "openId": "..."}
   （或 {"payload": {...SDK 回调 JSON 原文...}}）
→ 后端必须调 oauth2.0/me 校验 token 并比对 openid 一致性（ValidateToken）
   —— access_token 与 openid 都可被客户端伪造，未校验的 token 会被硬拒绝（403 forged）
→ 校验通过 → 拉用户信息 → 账号归属 → 双 token
```

> **这个不对称是设计决策，不许抹平**：微信 App 交 code（可信）vs QQ App 交 token（必须校验）。
> 依据：docs/14 §8.5 问题 2、禁令 5。

## 2. 前端接入

### 2.1 统一响应契约

所有端点走全站统一响应体（详见 AGENTS.md「响应契约与 i18n」）：

```json
{
  "data": { ... },
  "message": "<英文文案>",
  "status_code": 0,
  "trace_id": "<uuid>",
  "timestamp": 1735099999999
}
```

- `status_code` 是**业务码，与 HTTP 状态码无关**：0 成功；10008 参数错误；10009 依赖故障（503）；
  10002 未登录；10003 无权限（403）；10007 内部错误；20026 第三方登录未配置。
- `data` / `message` 为空时整个字段省略。

### 2.2 登录成功响应结构（8 端点 + GitHub 3 条全部一致）

```json
{
  "status_code": 0,
  "data": {
    "user": { "id": "...", "username": "...", "nickname": "...", "avatar": "...", "...": "ViewUser 脱敏视图，与既有 /auth/login 响应里的 user 逐字一致" },
    "token": "<JWT access token>",
    "refreshToken": "<JWT refresh token>",
    "id": "<user.id，单独给一份，前端历史习惯>",
    "isMember": false
  }
}
```

> 前端按既有 GitHub 登录的解析逻辑零改动复用。

### 2.3 微信 web（PC 扫码）

**第一步：取授权链接**

```
GET /api/v1/user/oauth/wechat/web/url
```

成功（真机验证输出，端口 3985）：

```json
{
  "status_code": 0,
  "data": {
    "url": "https://open.weixin.qq.com/connect/qrconnect?appid=wx546665b783674034&redirect_uri=<urlEncode 后的回调地址>&response_type=code&scope=snsapi_login&state=<32位hex>#wechat_redirect",
    "state": "<32位hex>"
  }
}
```

失败（未配置 wechat_web_appid/secret 时）：

```json
{ "message": "Third-party login is not configured", "status_code": 20026, "trace_id": "...", "timestamp": ... }
```

**第二步**：前端拿 `data.url` 做 `window.location.href = url`（或弹窗），用户扫码确认。

**第三步：回调**（两种模式二选一，可与 GitHub 现状保持一致）：

```
SPA 模式：
POST /api/v1/user/oauth/wechat/web/callback
{"code": "<平台带回的 code>", "state": "<平台带回的 state>"}
→ 200，data 即 §2.2 登录结构

重定向模式（平台直接 302 到后端，后端处理完再 302 回前端）：
GET /api/v1/user/oauth/wechat/web/callback?code=...&state=...
→ 302 到 wechat_web_success_redirect_url（未配置回落 /）
   成功带 ?token=<access token>；失败带 ?error=<英文文案>
```

### 2.4 QQ web（网页登录）

与微信 web 完全同构，仅路径与授权页不同：

```
GET /api/v1/user/oauth/qq/web/url
POST /api/v1/user/oauth/qq/web/callback   {"code","state"}
GET /api/v1/user/oauth/qq/web/callback    （重定向模式）
```

授权页样例（真机验证，appid 102065886）：
`https://graph.qq.com/oauth2.0/authorize?response_type=code&client_id=102065886&redirect_uri=<...>&state=<...>`

### 2.5 微信 App

```
POST /api/v1/user/oauth/wechat/app/login
{"code": "<WXApi.sendAuthReq 返回的 code>"}
```

| 场景 | HTTP | status_code | 说明 |
|---|---|---|---|
| 成功 | 200 | 0 | data = §2.2 结构 |
| code 为空 | 400 | 10008 | 参数错误 |
| code 无效/过期/已用 | 400 | 10008 | Third-party login failed |
| 微信 app 未配置 | 400 | 20026 | 检查 wechat_app_appid / wechat_app_secret |

> App 渠道**没有 state**（客户端不参与浏览器跳转）；code 一次性 + 服务端换 token 已覆盖 CSRF 面。

### 2.6 QQ App

两种提交方式，二选一：

```
结构化（推荐）：
POST /api/v1/user/oauth/qq/app/login
{"accessToken": "<SDK 返回的 access_token>", "openId": "<SDK 返回的 openid>"}

原始载荷（SDK 把 pay_token/pf/pfkey 一并回传、expires_in 是字符串时）：
POST /api/v1/user/oauth/qq/app/login
{"payload": { "ret":0, "access_token":"...", "openid":"...", "expires_in":"7776000", ... }}
```

| 场景 | HTTP | status_code | 说明 |
|---|---|---|---|
| 成功 | 200 | 0 | data = §2.2 结构 |
| accessToken/openId 缺失 | 400 | 10008 | 两种形态都没给时 |
| token 与 openid 不匹配 | 403 | 10003 | **客户端伪造组合**，ValidateToken 拦截 |
| token 过期/被撤销 | 401 | 10002 | 真机实测：伪造 token 打到 ValidateToken，`class=token_expired`，返回 10002 且**未建号** |
| qq_app_appid 未配置 | 400 | 20026 | 当前线上状态（见 §3 待补项） |

> 客户端上报的 `expires_in` 后端**一律不采信**（SDK 回调 JSON 里那 90 天的数字对后端没用）。

### 3.2 未配置降级行为

任一 `(provider, channel)` 组合的 appid/secret 未配齐 → 该组合的全部端点降级返回 **20026**
（HTTP 400，message "Third-party login is not configured"）。**不 500、不静默放行**——这是可观测的配置事故信号。

## 4. 运维

### 4.1 灌库脚本

```bash
# 项目根目录
docker exec -i postgre psql -U postgres -d fantwo_core < tmp/oauth-credentials.sql
# 或
psql -h 127.0.0.1 -p 5432 -U postgres -d fantwo_core -f tmp/oauth-credentials.sql
```

脚本特性：`INSERT ... ON CONFLICT`（服务没启动也能直接灌、重复灌幂等，只更新 value）；
id 显式 `gen_random_uuid()::text`（char(36) 无默认值）；脚本尾自带两条校验 SQL。

**时序提醒（真机踩过）**：先启动服务再灌库，进程内配置缓存（Redis 一级事实源 + TTL 10 分钟）
会让新值延迟生效 —— **灌完库重启服务**，或等 TTL 自然过期，或走 `PATCH /api/v1/config` 写入（自带 invalidate，立即生效）。

### 4.2 上线前必改清单

| 项 | 现状 | 动作 |
|---|---|---|
| `qq_app_appid` | 空（用户未创建 QQ 移动应用） | 去腾讯开放平台创建移动应用，拿到 appid 灌库（SQL 模板见 oauth-credentials.sql 注释块） |
| `wechat_web_redirect_uri` | 空 | 填 `https://<真实域名>/api/v1/user/oauth/wechat/web/callback`；**微信侧只需在开放平台「授权回调域」登记域名（不带路径）** |
| `qq_web_redirect_uri` | 空 | 填 `https://<真实域名>/api/v1/user/oauth/qq/web/callback`；**QQ 侧登记的回调地址必须与这里逐字一致、主域名下、不能用 IP+端口** |
| 两个 `*_success_redirect_url` | 空（302 回 `/`） | 按前端路由填 |

### 4.3 常见故障排查

| 现象 | status_code / HTTP | 根因 | 处置 |
|---|---|---|---|
| 登录端点返回 "Third-party login is not configured" | 20026 / 400 | 对应 (provider, channel) 的 appid/secret 未配齐（含 qq_app_appid 未建应用） | 对照 §3.1 补配置；改完走管理端写入或重启 |
| 空 code / 空 accessToken / 空 openId / 空 state | 10008 / 400 | 前端没传或传了空白 | 检查前端表单与 SDK 回调取值 |
| "Third-party login failed" | 10008 / 400 | code 无效 / 过期 / 已用过（code 10 分钟有效且一次性） | 引导用户重新走授权流程 |
| "Your third-party session has expired..." | 10002 / 401 | 平台 token 过期 / refresh 死亡 | 引导重新授权（不是本站 token 问题） |
| "Invalid third-party credentials" | 10003 / 403 | **客户端伪造**：QQ App 上报的 token 与 openid 不匹配，或未校验的 app token | 真实攻击或客户端 SDK 接错；日志有 `class=token_mismatch` / `token_not_verified` |
| 授权链接 403 forged 且日志 `class=not_configured` | 20026 / 400 | state 写不进 Redis（fail-closed 拒发） | 检查 Redis；**绝不放行是设计行为** |
| 同一 state 第二次提交失败 | 10008 / 400 | state 一次性消费，正常防护 | 前端不得复用 state；重新取 url |

## 5. 给未来接线者的提醒

**先读 docs/14 §7.1.2 的 7 条接线禁令，再动手。**（此处不重复，只链接。）

最快的理解路径：

1. **账号归属逻辑**（`internal/service/oauth_service.go` `FindOrCreateByOAuth`）查找顺序固定四步：
   ① unionid 非空才查 unionid（**空串一律不参与查询**，SQL 空串会互相匹配把不同的人并成同一账号）
   → ② provider+openid（**故意不带 channel**：同一平台跨渠道登录靠它兜底）
   → ③ GitHub 特例：email 合并只认未软删账号 → ④ 都未命中建新号+绑定。
   `internal/service/oauth_service_test.go` 的 FindOrCreate 系列用例是这条顺序的回归防线，改逻辑必须先让测试说话。
2. **绑定表**是独立表 `user_oauth_binding`（方案 B），唯一键 `(provider, openid)`，
   不存任何平台 token（纯泄漏面）。
3. **错误映射**（`mapOAuthErr`）与**日志分类**（`oauthErrClass`）已收敛：日志只打分类标签，
   错误信息不夹带上游响应体（token 明文风险）。
