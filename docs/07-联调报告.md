## 三、联调中发现并修复的缺陷（编译期发现不了）

| # | 缺陷 | 影响 | 修复 |
|---|---|---|---|
| 1 | `hashPassword(refresh)` 用 bcrypt 处理约 1KB 的 JWT | **登录必 500**（bcrypt 72 字节上限） | 改 `hashToken`（SHA-256 + 常量时间比对），密码仍 bcrypt |
| 2 | `user_device.refresh_token varchar(512)` | 登录 SQLSTATE 22001（JWT 1055 字节） | 改 `text`；hash 列改 `varchar(128)` |
| 3 | main.go 与消息域重复注册 `/api/v1/ws-message` | **启动即 panic**（handlers already registered） | 删 main 侧注册 |
| 4 | viper `AutomaticEnv` 对 `Unmarshal` 无效 | `POSTGRES_DATABASE/USER/PASSWORD` 等**环境变量完全失效** | 每个键补 `SetDefault` |
| 5 | `GET /user` 用 `user:read`（普通用户持有）守卫 | **越权**：普通用户可列全站用户 | 收紧为 `user:manage` |
| 6 | 统计硬编码 `Table("users")`，实际表名 `user` | 统计 user 数**恒为 0** | 改 `model.User{}.TableName()` |
| 7 | `UserPaymentView.TableName()` = `users` | `/order/wallet/balance` **500** | 改 `user` |
| 8 | `ReportTargetUserView.TableName()` = `users` | 举报校验查错表 | 改 `user` |
| 9 | `/profile/menus` 未注册 | 404（swagger 有此端点） | 新增 `RoleService.MyMenus` + 路由 |
| 10 | `POST /order/article` 入参 `article_id` | 违反 camelCase 口径，前端绑不上 | 改 `articleId` |

**共性根因**：①跨域视图/统计硬编码表名，与实际 `TableName()` 不一致；②外部库硬约束（bcrypt 72 字节、列长度）在编译期不可见。已增加 TableName 全量校验脚本，确保所有声明表名都指向真实存在的表（当前 62 个声明全部有效）。

## 十一、自检审核（provider=none）端到端验证

用户决策：内容审核用**自检服务**（本地敏感词 trie），不接云厂商。

**修复前（真实缺陷）**：含敏感词的文章 = PASSED 放行。根因是 `AuditService` 有两个实例：
| 实例 | 创建位置 | 是否注入敏感词检查 |
|---|---|---|
| 路由层 | `audit_routes.go` / `article_routes.go` | ✅ 已注入 |
| **worker 层** | `cmd/server/main.go` | ❌ **未注入** |

「提交审核 → 入队 → 消费」走的是 worker 路径，所以线上生效的恰恰是没注入的那个，
`s.sensitive == nil` → `checkSensitive` 直接返回 false → 敏感词被完全跳过。

**修复后实测（单实例，provider=none，autoBlock=true）**：
| 输入 | 结果 |
|---|---|
| `content=正文包含违禁词内容` | 文章 **REJECTED**；audit_records = `BLOCKED / sensitive_word / block` |
| `content=这是一段完全正常的内容` | 文章 **PUBLISHED**；audit_records = `PASSED` |

### 附带发现：asynq 多实例会抢任务

排查中曾出现「修复看起来无效」：3988/3989/3990 三个进程同时跑，共享同一 Redis 队列，
**旧的无注入实例抢到了测试任务**。清理到单实例后立即验证通过。

> 部署提示：滚动更新时新旧版本 worker 并存会互相抢任务，
> 涉及审核逻辑变更时需确保 worker 版本一致（或先停旧实例）。

## 十二、集成测试（真机 PG）揪出的 2 个真实缺陷

集成测试位于 `test/integration/`，用 `//go:build integration` 隔离，
默认 `go test ./...` 不执行、不引入新依赖（不用 sqlite driver）。

运行：
```bash
INTEGRATION_PG_DSN="host=127.0.0.1 port=5432 user=postgres password=*** dbname=fantwo_test sslmode=disable" \
  go test -tags=integration ./test/integration/... -v
```

### 缺陷 1：分页 limit=0 导致查不到任何数据

`repository` 层把调用方传入的 `limit` 直接透传给 GORM 的 `Limit()`，
而 `Limit(0)` 会生成 `LIMIT 0` → **返回空结果集**。

症状极具迷惑性：`meta.total` 有值、`list` 却是空数组——接口不报错，前端只看到"没数据"。

修复：新增 `internal/repository/pagination.go` 统一兜底
（`page<1 → 1`、`limit<=0 → 10`、上限 200），已应用到 category / collection / comment 的 List。

### 缺陷 2：`char(36)` 的空格填充污染

PostgreSQL 的 `char(n)` 是**定长**类型，存储时会用空格 pad 到 n。
非 36 字符的 ID（外部系统 ID、测试数据、手工插入的数据）取回后带尾随空格：

- Go 侧 `row.AuthorID == "author-1"` 比较失败（实际是 `"author-1"` + 28 个空格）
- JSON 输出被污染，前端拿到带空格的值

修复：118 处 `gorm:"type:char(36)"` 改为 `varchar(36)`。
UUID 语义不变（36 字符仍够），且 PG 内部 char/varchar 都是变长存储，无性能差异。
实测 AutoMigrate 平滑迁移，已有数据无损。

| 用例 | 防的 bug |

## 十三、关键路径性能基线（benchmark）

`go test ./internal/service/ -bench Benchmark -benchtime=2000x -run '^$'`
（本机：Windows / Go 1.26 / 单线程基准，仅供纵向对比）

| 基准 | ns/op | B/op | allocs/op | 说明 |
|---|---|---|---|---|
| SignerGenerateAccess | 3,403 | 3,591 | 36 | 登录成功时签发 access token |
| **SignerParseAndVerify** | **5,591** | 3,904 | 67 | **每个受保护请求的中件开销** |
| MaskPhone | 8.3 | 0 | 0 | 手机号脱敏 |
| MaskEmail | 19.7 | 24 | 1 | 邮箱脱敏 |
| NormPage | 0.25 | 0 | 0 | 分页规范化 |
| CalculateLevel | 0.80 | 0 | 0 | 等级计算 |
| IsProfileComplete | 0.25 | 0 | 0 | 资料完整度 |

### 结论

- **鉴权是唯一的显著固定开销**：验签 5.6µs/op，单核理论约 18 万 QPS。
  业务侧远达不到这个量级，**无需优化**；但这是日后回归的对比基线。
- 67 allocs 主要来自 JWT 库内部（Claims 结构 + 解析中间对象）。
  用 `sync.Pool` 复用 Claims 有风险（返回给调用方后生命周期不确定），收益不划算。
- 其余热点（脱敏/分页/等级）都在纳秒级，可忽略。

### 回归用法

改动鉴权/中间件后跑一次，与上表对比；若 `SignerParseAndVerify` 明显变慢，
说明中间件里加了额外工作（如每请求查库）。

## 十四、计数器一致性验证（社区系统最易漂移处）

社区类系统的典型线上问题不是 5xx，而是**计数慢慢对不上**：点赞了但 `likes` 没加、
取消收藏两次导致 -2、删评论后 `comment_count` 不回退。这类 bug 不报错、不告警，
只表现为用户投诉"我的赞数不对"。

`test/integration/counter_test.go` 验证「操作 → 计数」的配对：

| 用例 | 断言 |
|---|---|
| 点赞计数 | 3 人点赞 → `likes=3`；同一人重复点赞/改表情 → 仍 3，且 like 表仍只有 1 行 |
| 评论计数 | 2 条一级评论 → `comment_count=2`；删除 1 条 → 回退为 1 |
| 收藏计数 | 收藏 → `favorite_count=1`；重复收藏仍 1；取消 → 0；**重复取消不变负** |

### 产品语义发现：点赞不可撤销

核对 MCP 与 swagger 两处文档，确认原设计如此：

| 操作 | 是否可撤销 | 接口 |
|---|---|---|
| 点赞 | **不可撤销** | 只有 `POST /article/{id}/like`，无 DELETE 版本 |
| 收藏 | 可撤销 | `POST` + `DELETE /article/{id}/favorite` |
| 不喜欢 | 可撤销 | `POST` + `DELETE /article/{id}/dislike` |

所以「取消点赞」不是漏实现，而是原产品不做。改表情走 `reactionType`
（`like/love/haha/wow/sad/angry/dislike`），是 **UPDATE 而非 INSERT**——
这也是计数不重复累加的原因，测试已锁定该行为。

## 十五、依赖安全扫描（govulncheck）

`govulncheck ./internal/...` 扫描结果：**No vulnerabilities found**（代码级 0，模块级 0）。

### 修掉的两个漏洞

| 编号 | 内容 | 处置 |
|---|---|---|
| **GO-2026-6859** | `net/http` HTTP/1 server 因 MaxBytesReader header race **崩溃**（标准库） | Go toolchain 1.26.10 → **1.26.11**（`go.mod` 声明 `toolchain go1.26.11`，本地/CI 自动下载） |
| **GO-2026-6865** | `klauspost/compress` 双块帧 **panic** | v1.19.2 → **v1.20.5** |
| GO-2026-5932 | `x/crypto/openpgp` 已弃用且设计不安全 | v0.58.0 → **v0.59.0**（我们只用 bcrypt，本不调用 openpgp，顺手消除模块级告警） |

### 说明

- 第一个是**标准库**漏洞，只能靠升级 Go 版本修 —— 也是本次最有价值的一条：
  它是 `HTTP/1 server crash`，不是理论问题，线上可被触发。
- 用 `go.mod` 的 `toolchain` 指令而非手工装 Go：声明后任何环境（本地、CI、同事机器）
  跑 `go build` 都会自动下载并使用 1.26.11，避免"我这里是好的"。
- Dockerfile 同步改为 `golang:1.26.11-bookworm`。
