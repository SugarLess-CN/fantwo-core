## 三、联调中发现并修复的缺陷（编译期发现不了）

| # | 缺陷 | 影响 | 修复 |
|---|---|---|---|
| 1 | `hashPassword(refresh)` 用 bcrypt 处理约 1KB 的 JWT | **登录必 500**（bcrypt 72 字节上限） | 改 `hashToken`（SHA-256 + 常量时间比对），密码仍 bcrypt |
| 2 | `user_device.refresh_token varchar(512)` | 登录 SQLSTATE 22001（JWT 1055 字节） | 改 `text`；hash 列改 `varchar(128)` |
| 3 | main.go 与消息域重复注册 `/api/v1/ws-message` | **启动即 panic**（handlers already registered） | 删 main 侧注册 |
| 4 | viper `AutomaticEnv` 对 `Unmarshal` 无效 | `POSTGRES_DATABASE/USER/PASSWORD` 等**环境变量完全失效** | 每个键补 `SetDefault` |
| 5 | `GET /user` 用 `user:read`（普通用户持有）守卫 | **越权**：普通用户可列全站用户 | 收紧为 `user:manage` |
| 6 | 统计硬编码 `Table("users")`，实际表名 `user` | 统计 user 数**恒为 0** | 改 `model.User{}.TableName()` |
| 7 | `UserPaymentView.TableName()` = `users` | `/order/wallet/balance` **500** | 改 `user` |
| 8 | `ReportTargetUserView.TableName()` = `users` | 举报校验查错表 | 改 `user` |
| 9 | `/profile/menus` 未注册 | 404（swagger 有此端点） | 新增 `RoleService.MyMenus` + 路由 |
| 10 | `POST /order/article` 入参 `article_id` | 违反 camelCase 口径，前端绑不上 | 改 `articleId` |

**共性根因**：①跨域视图/统计硬编码表名，与实际 `TableName()` 不一致；②外部库硬约束（bcrypt 72 字节、列长度）在编译期不可见。已增加 TableName 全量校验脚本，确保所有声明表名都指向真实存在的表（当前 62 个声明全部有效）。

## 九、asynq 队列真实投递验证（T-24）

| 步骤 | 结果 |
|---|---|
| 投递前 Redis `asynq:{text-audit}:processed` | 9 |
| 发 1 篇文章（普通用户 → PENDING → 提交审核 → 入队） | ✅ |

## 十一、自检审核（provider=none）端到端验证

用户决策：内容审核用**自检服务**（本地敏感词 trie），不接云厂商。

**修复前（真实缺陷）**：含敏感词的文章 = PASSED 放行。根因是 `AuditService` 有两个实例：
| 实例 | 创建位置 | 是否注入敏感词检查 |
|---|---|---|
| 路由层 | `audit_routes.go` / `article_routes.go` | ✅ 已注入 |
| **worker 层** | `cmd/server/main.go` | ❌ **未注入** |

「提交审核 → 入队 → 消费」走的是 worker 路径，所以线上生效的恰恰是没注入的那个，
`s.sensitive == nil` → `checkSensitive` 直接返回 false → 敏感词被完全跳过。

**修复后实测（单实例，provider=none，autoBlock=true）**：
| 输入 | 结果 |
|---|---|
| `content=正文包含违禁词内容` | 文章 **REJECTED**；audit_records = `BLOCKED / sensitive_word / block` |
| `content=这是一段完全正常的内容` | 文章 **PUBLISHED**；audit_records = `PASSED` |

### 附带发现：asynq 多实例会抢任务

排查中曾出现「修复看起来无效」：3988/3989/3990 三个进程同时跑，共享同一 Redis 队列，
**旧的无注入实例抢到了测试任务**。清理到单实例后立即验证通过。

> 部署提示：滚动更新时新旧版本 worker 并存会互相抢任务，
> 涉及审核逻辑变更时需确保 worker 版本一致（或先停旧实例）。
