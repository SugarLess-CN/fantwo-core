# F-012 — 权限判定改为数据库实时读取（不再信 JWT 快照）

## 元信息

| 项 | 值 |
|---|---|
| 日期 | 2026-11-28 |
| 影响范围 | 全部需要权限点的接口（`user:manage` / `config:update` 等） |
| 严重级 | P1（权限变更滞后，改完角色对方要重登才生效） |
| 发现方式 | 用户指出「token 里带权限这样设计不好」 |
| 状态 | 已重构并真机验证 |

## 一、现象

管理员给某人加了角色后，**对方的旧 token 里权限还是老的**：

```
管理员：给用户 A 加 super-admin
用户 A：仍调不了管理接口（token 里没有 user:manage）
       必须等 token 过期，或系统用 perm_ver 把他踢下线重登
```

配置类场景更明显：刚给管理员授权，他去改配置仍 `403 common.forbidden`，
必须重新登录。

## 二、根因

```go
// internal/middleware/jwt.go（改前）
func RequirePermissions(required ...string) gin.HandlerFunc {
    claims := ...                     // 从 JWT 取
    for _, req := range required {
        for _, p := range claims.Permissions {   // ← 只比对 token 里的快照
            if p == req { c.Next(); return }
        }
    }
}
```

JWT 的 `perms` 是**签发那一刻**的快照。原有补救是 `perm_ver`：

```go
if cur := authtoken.PermVer(ctx, st, claims.UserID); cur != 0 && cur != claims.PermVer {
    return nil, "", errcode.ErrPermVersionStale   // 让用户重新登录
}
```

`perm_ver` 的语义是「权限变了 → 版本号 bump → 旧 token 失效 → 重新登录」。
**这等于把权限同步问题转嫁给用户**：改一次权限就要踢一次人。

## 三、修复方案

**权限每次判定都从数据库读**，JWT 只负责「你是谁」。

### 3.1 实时权限源

新增 `internal/middleware/permsource.go`：

```go
type PermissionSource struct {
    db, roles, log, cache, enable
}

func (p *PermissionSource) Permissions(userID string) ([]string, bool)
```

底层两个查询（`repository/role.go` 新增，各一条 JOIN SQL）：

```sql
-- 权限点
SELECT DISTINCT permission.name FROM permission
  JOIN role_permissions rp ON rp.permission_id = permission.id
  JOIN role ON role.id = rp.role_id
  JOIN user_roles ur ON ur.role_id = role.id
 WHERE ur.user_id = ? AND role.is_active = true

-- 角色名（同一套 JOIN）
SELECT role.name FROM role
  JOIN user_roles ur ON ur.role_id = role.id
 WHERE ur.user_id = ? AND role.is_active = true
```

只算 `is_active = true` 的角色 —— 禁用角色立即失去权限（这条以前也做不到）。

### 3.2 中间件改用实时值

`RequirePermissions` / `RequireAnyPermission` 两处统一走：

```go
func currentPermissions(c *gin.Context, claims *jwtx.Claims) ([]string, bool) {
    if src := ...; src != nil {
        if perms, fresh := src.Permissions(claims.UserID); fresh {
            return perms, true      // 实时值
        }
    }
    return claims.Permissions, false // 回退：查库失败 / 降级 / 测试
}
```

**回退是关键设计**：权限查询失败（DB 抖动）不该让全站 403 —— 那是可用性事故，
比权限滞后严重得多。所以查不到就退回 JWT 快照。

### 3.3 缓存与失效

每请求 JOIN 三张表太贵，加**进程内缓存，TTL 5 秒**：

| 机制 | 作用 |
|---|---|
| TTL 5 秒 | 兜底刷新周期；同时保护高 QPS 场景不重复查库 |
| `InvalidateUserPermissions(id)` | 角色变更处主动失效，**立即生效**（不用等 TTL） |
| 缓存上限 10000 条 | 超了整体重建，防无限增长 |

失效点已接在两个权限变更处：
`role_service.go`（改角色权限，波及该角色下全部用户）、
`user_actions_service.go`（给用户改角色）。

全局单例 `globalPermSource` 让 service 层能拿到中间件的缓存实例
（两者分属不同包，且实例是 router 构造的）。

## 四、验证（真机，端口 4440）

### 4.1 授权立即生效（**同一个旧 token**）

```
① 改角色前       GET /user?limit=2  →  20003 common.forbidden
② 库里加 super-admin（不重启服务）
③ 等 6 秒后，用**同一个旧 token** 再调
   →  status 0，返回 2 条  ✅ 无需重登
```

### 4.2 撤权立即生效

```
④ 库里删掉 super-admin
⑤ 等 6 秒，同一 token 再调
   →  20003 common.forbidden  ✅ 权限撤销立即生效
```

### 4.3 决定性证据：token 里有权限也不认

```
⑥ 解析该 token 的 payload：
   perms: ['user:read','user:create','user:update','user:delete','user:manage'] … 共 88 个
   roles: ['super-admin', 'user']
   → token 里明明还是 super-admin 的 88 个权限，接口却返回 403
   → 证明判定走的是数据库，不是 token
```

质量门：gofmt 空 / build OK / vet 零输出 / 17 包全绿 FAIL 0

## 五、影响与风险

### 5.1 行为变化

| 场景 | 改前 | 改后 |
|---|---|---|
| 加角色 | 需重新登录 | **立即生效**（≤5 秒，或 0 秒如果命中失效钩子）|
| 撤角色 | 需重新登录 | **立即生效** |
| 禁用角色 | 需重新登录 | **立即生效**（查询带 `is_active = true`） |
| DB 抖动 | token 快照仍可用 | 回退 token 快照，行为同改前 |

### 5.2 性能

每个用户每 5 秒最多查一次库（两条 JOIN SQL，命中 `user_roles.user_id` 与
`role_permissions.role_id` 索引）。相比每个请求都查库，开销可忽略。

### 5.3 多副本部署

进程内缓存不跨实例 —— 各副本独立，最长 5 秒收敛。
若将来要多副本且要求秒级一致，应把缓存换成 Redis（`SetPermissionSource`
已封装，只需换 `permCache` 的实现）。

### 5.4 `perm_ver` 的 401 已停用（2026-11-28 追加）

**`perm_ver` 原来干什么**：签发时把版本号写进 token（`pv: 3`），
管理员改权限时 Redis bump 成 4，中间件比对 `3 ≠ 4` → 返回
`20002 auth.perm_version_stale` → 前端被迫重新登录。

**为什么多余**：它的唯一触发点是「权限变更」（全仓只有 2 处 bump：
`role_service.go:597` 改角色权限、`user_actions_service.go:818` 给用户改角色）。
权限既然已经实时读库，用户不重登就能拿到新权限，再返回 401 只是把用户踢下线。

**历史上它还声称覆盖登出/改密，但实际没有**（原注释写错了）：
`currentPermVer` 的注释说「登出/改密后 bump」，但代码里登出用
`BlacklistAdd`、全端登出/改密/封号用 `SetLogoutAll`，**都不碰 perm_ver**。

**处理方式**：中间件那条比对**停用**（保留注释说明原因），
`perm_ver` 的**写入保留**（签发仍记 `pv`、变更仍 bump）——
将来若需要「强制某用户重登」，把比对打开即可，不用改签发侧。

### 5.5 验证：token 失效能力未被破坏

停用 perm_ver 后，专门回归了三条真正负责失效的路径：

```
④ 单端登出 POST /user/logout      → 旧 token 20001 auth.need_login  ✅ Blacklist 生效
⑤ 全端登出 POST /user/logout-all  → 旧 token 20001 auth.need_login  ✅ LogoutAllAt 生效
⑥ 改密     POST /user/password/change → 旧 token 20001 auth.need_login  ✅ 改密失效生效
```

并验证 perm_ver 不一致时放行：

```
token 里 pv=0，Redis bump 到 5（故意不一致）
→ GET /user?limit=1  →  status 0  ✅ 不再返回 2002
```

### 5.6 遗留

**JWT 里的 `perms` 字段仍在签发**（`GenerateWithPermVer` 的参数）。
它现在是「查库失败时的回退快照」，保留是有意的（见 §三 3.2）。
若要彻底精简可去掉，但要同步改 `jwtx` 的签发与解析，属于后续清理项。
