# F-013 — 头像与水印图去重串场景（同一张图复用了错误产物）

## 元信息

| 项 | 值 |
|---|---|
| 日期 | 2026-11-28 |
| 影响端点 | `POST /upload/file`、`POST /upload/avatar` |
| 严重级 | P1（头像复用到带水印图；第二个接口直接 500） |
| 发现方式 | 用户实测报障 |
| 状态 | 已修复并真机验证 |

## 一、现象

用户上传同一张图到两个接口，**第二次复用了第一次的记录**：

```
① POST /upload/file   （应加水印）
   id: 1c326b2f | scene: image | watermarked: True | ref: 1

② POST /upload/avatar （应无水印）
   id: 1c326b2f | scene: image | watermarked: True | ref: 2   ← ❌ 复用了 file 的记录
```

头像拿到带水印的图，两个接口的产物串了。

## 二、根因（两层，都要修）

### 2.1 去重查询不看 scene

```go
// internal/service/infra/storage.go（改前）
existing, err := f.findByHash(ident)          // ← 只按 hash 查
if existing != nil { ref+1; return existing } // ← 直接返回，不管 scene

func (f *Infra) findByHash(hash string) (*model.Upload, error) {
    err := f.db.Where("hash = ?", hash).First(&up).Error   // ← 没有 scene 条件
}
```

同一份内容（hash 相同）在 image 场景下已有一行，avatar 场景直接命中它。

### 2.2 唯一的根子在 DB 唯一索引

`internal/model/upload.go`（改前）：

```go
Hash string `gorm:"column:hash;type:varchar(128);uniqueIndex;not null"`
```

`uniqueIndex` 是**单列**唯一约束。所以「按 (hash, scene) 查不到 → 走新建」
这条路根本走不通 —— INSERT 会撞上 `idx_uploads_hash`：

```
ERROR: duplicate key value violates unique constraint "idx_uploads_hash" (SQLSTATE 23505)
→ 500 common.operation_failed
```

**只改查询不改索引**会从「串数据」变成「500」，这是我第一轮踩到的中间态。

### 2.3 scene 在去重时还没归一化

去重发生在 `uploadOne` 靠前的位置，而 `scene` 直到建记录时才 `orDefaultStr(scene, SceneImage)`。
空 scene 直接参与比对会比不上任何已有行，去重静默失效。

## 三、修复

### 3.1 模型：改成 (hash, scene) 复合唯一索引

```go
Hash  string `gorm:"column:hash;type:varchar(128);not null;index:idx_upload_hash_scene,priority:1"`
Scene string `gorm:"...;index:idx_upload_scene;uniqueIndex:idx_upload_hash_scene,priority:2"`
```

语义变成：**同一内容在每个场景下只有一行，跨场景互不影响**。

### 3.2 查询：带上 scene

```go
func (f *Infra) findByHash(hash, scene string) (*model.Upload, error) {
    err := f.db.Where("hash = ? AND scene = ?", hash, scene).First(&up).Error
}
```

两个调用点都改：`uploadOne`（普通上传）与 `ConfirmUpload`（S3 直传确认）。

### 3.3 scene 提前归一化

```go
// 3.5) 必须在去重判定之前
scene = orDefaultStr(scene, SceneImage)
```

### 3.4 迁移：AutoMigrate 不会删旧索引，必须显式处理

新增 `migrations/infra.go` 的 `fixUploadHashIndex`：

```go
db.Exec(`DROP INDEX IF EXISTS idx_uploads_hash`)      // 删历史的单列唯一索引
db.Exec(`CREATE UNIQUE INDEX IF NOT EXISTS idx_upload_hash_scene ON uploads (hash, scene)`)
```

**为什么必须单独做**：AutoMigrate 只新增索引、不删旧的。
模型改了但老库那条 `UNIQUE (hash)` 还在，行为不会变（仍是 500）。

## 四、验证（真机，端口 4462）

### 4.1 索引迁移

```
迁移前：idx_uploads_hash       UNIQUE (hash)              ← 单列，旧
迁移后：idx_upload_hash_scene  UNIQUE (hash, scene)       ← 复合，新
```

### 4.2 两个接口彻底分离

同一张 PNG（270448 字节）先传 file 再传 avatar：

| 步骤 | id | scene | watermarked | reference_count |
|---|---|---|---|---|
| ① `POST /upload/file` | `974d7d90` | `image` | **`True`** | 1 |
| ② `POST /upload/avatar` | `91740376` | `avatar` | **`False`** | 1 |
| ③ 再传一次 avatar | `91740376` | `avatar` | — | **2** |

- ① ② 是**两条独立记录**，头像无水印 ✅
- ③ 同场景内仍然去重（ref 1→2），没有退化成「每次都新建」✅

### 4.3 迁移前先检查重复行

建唯一索引前查过 `GROUP BY hash, scene HAVING count(*) > 1` → **0 行**，可安全建索引。

若老库真有重复行，迁移会失败 —— **这是故意的**：那说明历史上已经出过 bug，
需要人工合并，不能静默跳过。

## 五、影响与风险

### 5.1 存储成本上升（可接受）

同一张图在不同场景下会存多份。这是**故意接受的**：
水印图与无水印图本就是不同产物，为了省一份空间而让它们混用是功能错误。

### 5.2 存量数据不受影响

老数据里每个 hash 只有一行（单列唯一约束保证过），符合新的
`UNIQUE (hash, scene)` 语义，不需要回填。

### 5.3 排查要点

若再遇到类似「不同上传接口互相复用」，按这个顺序查：

1. `findByHash` 的 WHERE 是否带全了区分维度
2. DB 的唯一索引是否与代码里的去重键**一致**（最容易漏）
3. 去重判定所用变量在该时刻是否已归一化

### 5.4 遗留

`ConfirmUpload`（S3 直传确认）也改了，但**未做真机验证** —— 本地没有 S3 环境。
逻辑与 `uploadOne` 完全同构（同样提前归一化 scene、同样带 scene 查重），
风险低，但严格来说属于「未验证路径」。
