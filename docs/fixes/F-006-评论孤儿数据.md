## 一、现象

```
POST /api/v1/comment {"articleId":"<不存在的id>","content":"test"}
→ HTTP 200 / status_code=0  评论创建成功
```

数据库多了一条 `article_id` 指向不存在文章的评论 —— **孤儿数据**。
后续任何按文章聚合评论的查询、统计、级联删除都会因此出错。

## 二、复现步骤

```bash
curl -s -X POST .../comment -H "Authorization: Bearer $T" \
  -H "Content-Type: application/json" \
  -d '{"articleId":"00000000-0000-0000-0000-000000000000","content":"orphan"}'
# 改前：200 建成功
```

## 三、根因

原仓库在**事务内先查文章**：

```ts
// tmp/picart/src/modules/comment/comment.service.ts:565-572
const articleQuery = ...where("article.id = :articleId", { articleId });
if (!parentId && initialStatus === "PUBLISHED") {
  articleQuery.setLock("pessimistic_write");   // 顶层评论取行锁
}
const article = await articleQuery.getOne();
if (!article) {
  throw new Error("Article not found");
}
```

我们的实现直接建评论，没有文章存在性校验。

## 四、修复方案

`internal/service/comment.go:212`：

```go
// 文章存在性校验：对齐原仓库 comment.service.ts:570-572
// （article 不存在直接报错，不落脏数据）
_, artErr := repository.NewArticleRepository(s.repo.DB()).FindByID(ctx, req.ArticleID)
if artErr != nil {
    return nil, errcode.ErrNotFound.WithKey(i18n.ArticleNotFound)
}
```

## 五、验证

```bash
curl -s -X POST .../comment -d '{"articleId":"<不存在>","content":"x"}'
→ HTTP 404 / 10004 / "Article not found"    ✓

# 正常文章评论仍成功
curl -s -X POST .../comment -d '{"articleId":"<有效>","content":"x"}'
→ HTTP 200 / 0                              ✓
```

孤儿数据已 SQL 清理。

## 六、影响与风险

**Breaking change**：无（本来就是错误输入）。

**同类未修（已记 todo）** —— 同一个 `Create` 里还有两个相关缺陷：

1. **校验不在事务内**：查到文章存在 → 文章可能在毫秒级窗口内被删 → 评论仍落库成孤儿。
   概率极低（文章多为软删），但语义弱于原仓库。
2. **楼层号并发不安全**：`MaxFloor` 是事务外查询，
   `comments` 表无 `(article_id, floor)` 唯一约束，SQL 也没有 `FOR UPDATE`。
   两个并发的一级评论会读到同样的 `MAX(floor)` → **楼层重复**。
   原仓库用 `pessimistic_write` 锁 article 行（注释明确写「只有需要分配楼层号的顶层评论才取行锁，
   回复不再互相阻塞」）。

**修法建议**（两项一起做）：事务内 `SELECT ... FOR UPDATE` 锁 article 行，
既解决「文章被删」也解决「楼层重复」。

**复发预防**：凡是「子表引用父表」的创建操作，都应先校验父记录存在。
已记入 `todo.md` 供逐域复查。
