# F-011 — 普通用户改自己头像返回「没有权限」

## 元信息

| 项 | 值 |
|---|---|
| 日期 | 2026-11-28 |
| 影响端点 | `PATCH /user/{id}`（普通用户改自己资料） |
| 严重级 | P1（新用户注册后无法改头像，核心资料功能不可用） |
| 发现方式 | 用户实测报障，lead 复现并定位 |
| 状态 | 已修复并真机验证 |

## 一、现象

新注册用户（`user` 角色）调 `PATCH /user/{自己的id}` 改头像：

```
status_code: 20003
message: common.forbidden
```

而 `PATCH /user/profile`、`POST /upload/avatar` 都正常 —— 只有这一个端点拒绝。

## 二、复现步骤

```bash
# 1. 注册新用户（自动获得 user 角色，33 个权限）
curl -X POST .../api/v1/user/register \
  -d '{"username":"regtest1","password":"Test123456","email":"regtest1@test.com"}'

# 2. 登录拿 token
T=$(curl -X POST .../api/v1/user/login \
  -d '{"account":"regtest1","password":"Test123456"}' | jq -r .data.token)

# 3. 改自己头像
curl -X PATCH .../api/v1/user/<自己的id> \
  -H "Authorization: Bearer $T" \
  -d '{"avatar":"https://x/a.png"}'
# → {"status_code":20003,"message":"common.forbidden"}
```

## 三、根因

**2026-11-25 一次「安全收紧」矫枉过正。**

当时的推理是：
> `PATCH /user/{id}` 的中间件用 `user:update`，而这个权限**普通用户人人都有** →
> 任何登录用户都能改任意人的资料，而 `UpdateUser` 支持 `status`/`wallet`/`role_ids` →
> 封禁任何人、直接改余额、给自己加管理员角色（提权）。所以要收紧成 `user:manage`。

**这个推理只看了中间件层，漏了原 NestJS 在 service 层的两道防护**（`user.service.ts:864-892`）：

```typescript
// ① 改别人 → 要 user:manage
if (currentUser.id !== id && !hasPermission(currentUser, "user:manage")) {
    throw new ForbiddenException("userNoPermission");
}

// ② 改自己且非管理员 → 字段白名单，其余静默剔除
if (isUpdatingSelf && !isAdmin) {
    const allowedFields = ["nickname","avatar","username","background",
                           "birthDate","gender","address","description"];
    Object.keys(userData).forEach((key) => {
        if (!allowedFields.includes(key)) delete userData[key];
    });
}

// ③ roleIds 仅管理员
if (roleIds && isAdmin) { ... }
```

**所以原版没有提权漏洞** —— 防护在 service 层的字段白名单。

而我们的 `UpdateUser(ctx, id, in)` **既不接收 actor、也没有白名单**，所以当时收紧中间件是唯一能防提权的手段。但副作用是：**按原契约调用 `PATCH /user/{id}` 改自己头像的普通用户全部 403**。

## 四、修复方案

把防护放回**正确的位置**（对齐原 JS），中间件恢复原权限。

### 4.1 service：加 actor + 两道防护

```go
func (s *UserService) UpdateUser(ctx, id string, in UpdateUserInput, actor Actor) (...) {
    isAdmin := actor.Has("user:manage")
    isSelf  := actor.UserID != "" && actor.UserID == id

    if !isSelf && !isAdmin {
        return nil, errcode.ErrNoPermission          // 改别人 → 403
    }
    if isSelf && !isAdmin {
        restrictSelfUpdate(&in)                       // 改自己 → 白名单
    }
    ...
}
```

### 4.2 白名单（`selfUpdatableFields`）

**允许**：`username` / `nickname` / `avatar` / `description` / `background` / `address` / `gender` / `birth_date`

**禁止**（静默置 nil）：
| 字段 | 为什么本人不能改 |
|---|---|
| `password` | 走 `POST /user/password/change`（要旧密码校验），从这条路径改等于绕过 |
| `role_ids` | 提权 |
| `status` / `banned` / `ban_reason` | 自我解封 |
| `wallet` | 直接造钱 |
| `membership_*` | 自我开会员 |
| `invite_code` | 邀请关系伪造 |

**为什么静默剔除而不是 400**：前端可能把整个 `UserDto` 回传（含 `role_ids`/`wallet`），
报错会让「改昵称」这种正常操作失败。原 NestJS 同样是 `delete` 掉字段。

### 4.3 路由：恢复 `user:update`

```go
admin.PATCH("/:id", canUserWrite, userH.Update)   // canUserWrite = user:update | user:manage
```

`PATCH /user/profile`（我们额外加的便利端点）保持不变，只要登录 —— 它走 `UpdateProfile`，
天然只改自己。

## 五、验证

真机（端口 4211，新建 `user` 角色账号）：

```
① 普通用户改自己头像
   PATCH /user/{自己id}  {"avatar":"https://x/mine.png","nickname":"reg昵称"}
   → status_code: 0 | avatar: https://x/mine.png | nickname: reg昵称    ✅（改前 20003）

② 普通用户改别人
   PATCH /user/{他人id}  {"nickname":"hacked"}
   → status_code: 20003 | common.forbidden                              ✅ 挡住

③ 普通用户夹带敏感字段
   PATCH /user/{自己id}  {"nickname":"reg昵称2","wallet":99999,"status":"BANNED","role_ids":["admin"]}
   → status_code: 0
     nickname: reg昵称2 | wallet: 0 | status: ACTIVE                    ✅ 只改了昵称

④ 管理员改别人（不受白名单限制）
   PATCH /user/{他人id}  {"nickname":"admin改的昵称","wallet":88}
   → status_code: 0 | wallet: 88                                       ✅ 生效

⑤ PATCH /user/profile 仍可用
   → status_code: 0 | avatar: https://x/profile.png                     ✅
```

质量门：`gofmt` 空 / `build` OK / **17 包全绿 FAIL 0**。

测试账号已删（`user_roles` / `user_device` / `user_config` / `user` 全部清理，残留 0）。

## 六、影响与风险

- **权限行为变更**：`PATCH /user/{id}` 的中间件从 `user:manage` 回到 `user:update`
  - 普通用户：改自己 ✅（原来 403）/ 改别人 ❌ 403（不变）
  - 管理员：不变
- **前端不用改**：按原 NestJS 契约调 `PATCH /user/{id}` 的代码现在能正常工作。
- **安全性未降**：提权面由 service 层白名单挡住，且有 ③ 的真机用例守着
  （`wallet`/`status`/`role_ids` 全部被剔除）。

### 遗留

1. **`PATCH /user/profile` 与原契约的关系**：原 NestJS **没有**这个端点（改自己资料也是走
   `PATCH /user/:id`）。这是我们为「改自己」额外加的便利端点，保留无害（只要登录 + 只改自己），
   但前端若同时存在两条路径，建议统一用 `PATCH /user/{id}` 对齐原契约。
2. **`restrictSelfUpdate` 的字段清单需与 `UpdateUserInput` 同步维护**：将来 `UpdateUserInput`
   加字段时，必须判「本人能否改」，否则默认会**落到禁止侧**（安全默认，但可能误伤）。
   已在函数注释里写明。
3. **注册不返回 token**：注册响应是 `UserDto`，前端要再调一次 login。这是既有行为
   （与本 bug 无关），若产品希望一次拿到 token 可单独立项。
