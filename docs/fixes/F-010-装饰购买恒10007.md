# F-010 — 装饰品购买一律 10007 内部错误

## 元信息

| 项 | 值 |

| 影响端点 | `POST /decoration/purchase` |
| 严重级 | P1（购买功能完全不可用，且客户端拿不到任何可操作信息） |

| 状态 | 已修复并真机验证 |

## 一、现象

**修复前**：任何购买请求都返回同一个 500 级错误，无信息量。

```
POST /decoration/purchase {"decoration_id":"<0 元装饰>"}
→ {"message":"common.internal_error","status_code":10007}

POST /decoration/purchase {"decoration_id":"<9999 元装饰>"}
→ {"message":"common.internal_error","status_code":10007}
```

两种完全不同的业务情形（免费领取 / 余额不足）表现为**同一个错误码**，
前端「购买」按钮永远报错且无法提示用户「去充值」或「这件是免费的」。

## 二、复现步骤

```bash
# 1. 造两个装饰品：一个 price=0，一个 price=9999（都 is_purchasable=true, status=ACTIVE）
# 2. 用任意有 token 的用户购买
curl -X POST .../api/v1/decoration/purchase \
  -H "Authorization: Bearer $T" -H "Content-Type: application/json" \
  -d '{"decoration_id":"<price=0 的那件>"}'
# → status_code: 10007

curl -X POST .../api/v1/decoration/purchase \
  -H "Authorization: Bearer $T" -H "Content-Type: application/json" \
  -d '{"decoration_id":"<price=9999 的那件>"}'
# → status_code: 10007（应为 20019 余额不足）
```

## 三、根因

**两条独立的错误，都被同一个兜底吞掉。**

### 3.1 `DeductBalance` 拒绝 `amount <= 0`

`internal/service/user_wallet.go:33`
```go
if amount <= 0 {
    return fmt.Errorf("扣款金额必须大于 0")
}
```
→ **0 元装饰永远买不了**（价格是 0，`DeductBalance` 必报错）。

### 3.2 余额不足返回的不是 `*errcode.Err`

`internal/service/user_wallet.go:17`
```go
var errInsufficientBalance = errors.New("余额不足")   // 普通 error
```
`internal/service/decoration_service.go` 的 `Purchase` **原样透出**：
```go
if err := s.wallet.DeductBalance(...); err != nil {
    return nil, err        // ← 普通 error
}
```
handler 的 `fail()` 只认 `*errcode.Err`，见到普通 error 一律收敛为 `ErrInternal`（10007）。

**所以客户端拿到 500 + 「内部错误」，既不知道余额不足，也不知道 0 元不能扣。**

### 3.3 对照原 NestJS

```typescript
// decoration.service.ts:244
if (!decoration.isPurchasable) throw new BadRequestException("该装饰品不可购买");
// :248
if (decoration.status !== "ACTIVE") throw new BadRequestException("该装饰品已下架");
// :262 已拥有
throw new BadRequestException("您已拥有该装饰品");
// 然后 walletService.deductBalance(...)
```
原版用 `BadRequestException` 抛业务错 → 400 + 可读文案。
我们的「前置校验」（不可购买/已下架/已拥有）**已经对了**（`decorationPurchaseRejection`），
唯独**钱包这一段**透出了裸 error。

## 四、修复方案

`internal/service/decoration_service.go` 的 `Purchase`：

```go
// 0 元装饰（免费发放）**不走扣款**
if d.Price > 0 {
    if err := s.wallet.DeductBalance(userID, d.Price, "DECORATION", "购买装饰品："+d.Name); err != nil {
        if errors.Is(err, errInsufficientBalance) {
            return nil, errcode.ErrInsufficientBalance      // 20019 + HTTP 400
        }
        return nil, errcode.ErrInternal.WithKey(i18n.DecorationWalletUnavailable)
    }
}
```

两个改动点：

| 改动 | 理由 |
|---|---|
| `price > 0` 才扣款 | 0 元装饰是**免费发放**，不是「扣 0 元」。跳过扣款直接走 `grantModel` 授予 |
| `errors.Is(err, errInsufficientBalance)` → `ErrInsufficientBalance` | 把钱包层的普通 error 翻译成业务码（20019），前端可引导充值 |

**否掉的备选**：改 `DeductBalance` 允许 `amount == 0`。
不改，因为「扣 0 元」在语义上是调用方错误，让钱包层放宽会给其它调用方开坏头。
正确的做法是**调用方按业务语义决定要不要扣**。

## 六、影响与风险

- **行为变更**：`POST /decoration/purchase` 的错误码契约变准了
  - 0 元装饰：`10007` → **`0`（成功）**
  - 余额不足：`10007` → **`20019`（`points.insufficient`，HTTP 400）**
  - 其它钱包故障（DB 不可用等）：仍 `10007`（合理，那是真内部错误）
- **前端应适配**：购买失败时按 `status_code === 20019` 提示「积分不足，去充值」；
  不要再用「10007 = 一切购买失败」的旧假设。
- **同类隐患（未修，已记录）**：`DeductBalance` 还有其它调用方
  （`internal/service/user_wallet.go` 是跨域公共能力）。
  凡是「把它的 error 原样透出」的地方都会有同样的 10007 问题。
  建议后续统一在 `DeductBalance` 外层加一个 `mapWalletErr(error) *errcode.Err` 帮助函数，
  所有调用方都用它，而不是各自 `if errors.Is`。本轮只修了装饰购买这一处。
