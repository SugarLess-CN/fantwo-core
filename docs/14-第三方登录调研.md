## 0. 结论摘要

### 0.1 三家差异一句话总结

| 平台 | 一句话定位 | 最大特征 |
|---|---|---|
| **GitHub** | 事实标准 OAuth2，最规范 | 唯一一个"照 RFC 6749 抄就能跑通"的；连错误体都是标准 `error`/`error_description` |
| **微信** | 半标准：协议骨架是 OAuth2，细节全是私货 | 换 token 用 **GET**（不是 POST）＋授权 URL 必须以 **`#wechat_redirect`** 收尾＋错误体是自家 `errcode`/`errmsg` |
| **QQ** | 最不规范，三种响应格式混用 | 同一个平台里同时存在 **URL query string**（换 token）、**JSONP**（取 openid）、**JSON**（取用户信息）三种返回体，OAuth 通用参数还叫 `oauth_consumer_key` |

**最大的坑（谁排第一）**：**QQ**。它一个 Provider 要写三个解析器：

1. `oauth2.0/token` 返回裸 query string `access_token=xxx&expires_in=xxx&refresh_token=xxx`，**不是 JSON 也不是 form-encoded body，而是整个 body 就是一个 query string**，`url.ParseQuery(string(body))` 才解得开；
2. `oauth2.0/me` 返回 JSONP `callback( {...} );`，**必须剥壳**（且默认不是合法 JSON，加 `fmt=json` 才会返回纯 JSON）；
3. `user/get_user_info` 返回标准 JSON，但错误用 `ret`/`msg` 而不是 `errcode`/`errmsg`，且 `ret != 0` 时 HTTP 状态码**仍是 200**。

微信排第二：授权 URL 少写 `#wechat_redirect` 会直接白屏/报"该链接无法访问"；`sns/userinfo` 的官方文档正文与响应样例自相矛盾（见 §1.4）。

### 0.2 SDK 选型结论

**结论：自己实现（`internal/pkg/oauthkit`），其中 GitHub 分支底层引用 `golang.org/x/oauth2`，微信/QQ 分支用标准库 `net/http` 手写，整体结构借鉴 `markbates/goth` 的 provider 形态。**

拆开说（四选一逐项落定）：

| 平台 | 结论 | 理由 |
|---|---|---|
| GitHub | **引用 `golang.org/x/oauth2`** | ★5908 / BSD-3-Clause / 2026-11-09 仍在提交；go.mod 只有 **1 个**依赖（`cloud.google.com/go/compute/metadata`）；Go 官方维护，等价标准库 |
| 微信 | **借鉴 `markbates/goth` 的 `providers/wechat` 设计**，代码自写 | goth 的 wechat provider 端点常量与字段映射与我们需求**完全一致**（`qrconnect` + `snsapi_login` + `sns/oauth2/access_token` + `sns/userinfo`），可直接抄思路；但 goth 的 `BeginAuth` **漏了 `#wechat_redirect`**（源码 `providers/wechat/wechat.go:89`），且整体拖入 10+ 直接依赖 / 20+ 间接依赖，为 3 个端点引它不划算 |
| QQ | **自己实现** | GitHub 上 QQ OAuth 的 Go 实现**全部是玩具级**：`leo0o/simpleoauth` ★32（2017，无 LICENSE）、`sanxia/goauth` ★15（2022，MIT，但只覆盖 openid 不覆盖 userinfo 完整字段）、`phachon/qq-OAuth` ★7（2018，无 LICENSE）、`feymanlee/goauth` ★1（2026，无 LICENSE）。无一个达到"维护活跃 + 许可证明确 + 覆盖完整"三条线 |

**为什么不整体引用 goth**：goth 是"多 provider 全家桶"，它的价值在于 74 个 provider 的广度；我们只要 3 个。代价是 `go.mod` 里塞进 `chi/v5`、`gorilla/mux`、`gorilla/pat`、`gorilla/sessions`、`lestrrat-go/jwx`、`golang-jwt/jwt/v5`、`markbates/going`、`mrjones/oauth` 等 10 个直接依赖（含 `lestrrat-go` 那条 jwt/jwx 链带出 secp256k1、goccy/go-json 等一堆间接依赖），且它**没有 QQ provider**，QQ 照样得自己写。投入产出不成立。

### 0.3 统一抽象建议

三家能统一的部分其实**只有四件事**：拼授权 URL、code 换 token、token 换用户、refresh token。
差异全部集中在"响应怎么解"和"唯一标识叫什么"。建议接口（详见 §7）：

```go
type Provider interface {
    Name() string
    AuthURL(state string) (string, error)
    Exchange(ctx context.Context, code string) (*Token, error)
    UserInfo(ctx context.Context, tok *Token) (*User, error)
    Refresh(ctx context.Context, tok *Token) (*Token, error)
}

// Token 归一化后：AccessToken / RefreshToken / ExpiresIn(秒) / OpenID / UnionID / Scope / Raw
// User  归一化后：ID(平台内唯一，即 openid/github id) / UnionID / Nickname / Avatar / Email / Raw
```

关键决策：**`Token` 里保留 `OpenID` 字段**。因为微信和 QQ 的 `openid` 是**换 token 时就返回的**（不是靠 userinfo 拿），而 GitHub 的 `id` 要靠 `/user` 才拿到——如果只按 OAuth2 标准抽象成 `{AccessToken, RefreshToken, Expiry}`，微信/QQ 的 openid 就得在 `UserInfo` 里再传一遍，反而绕。保留 `OpenID` 让"登录主键"在 `Exchange` 阶段就能落地。

### 0.4 多渠道结论（T-37a2 追加，详见 §8）

用户追加需求：微信与 QQ 要同时支持「移动端 SDK 授权登录」与「网页版扫码/快捷登录」。四条结论：

1. **微信：三形态后端几乎零成本**。移动应用/网站应用是**两套独立 appid**，但 `sns/oauth2/access_token`、`refresh_token`、`userinfo`、`sns/auth` **四个端点 100% 复用**，只有 appid/secret、scope（web=`snsapi_login` / app=`snsapi_userinfo`）、拼的授权 URL 不同。**App 一定能拿到 unionid**（官方："当且仅当已获得 userinfo 授权"，而 App 的 scope 只能是 userinfo）。两形态的 `refresh_token` 有效期不同：**web 30 天 / app 180 天**。
2. **QQ：移动端与网页端流程截然不同，这是本轮最大的坑**。移动端 SDK **直接返回 `access_token` + `openid` + `expires_in`，后端不换 token**、**没有 `refresh_token`**、有效期是 **90 天（7776000）**——与网页端的 **60 天（5184000）** 不是同一个数（第一轮判定"7776000 是历史值"的结论**据此修正**）。拿到 token 后调 `user/get_user_info` 需传 `oauth_consumer_key` + `openid`，与网页端同一端点。
3. **移动端 token 由客户端上报 → 不可信 → 必须新增 `ValidateToken`**。这是本轮唯一真正改变接口设计的发现：缺的不是"注入 token 的入口"，而是"校验 token 的能力"。QQ 用 `oauth2.0/me` 校验并**比对 openid 一致性**；`UserInfo` 对未校验的 app 渠道 token 硬拒绝。
4. **GitHub 无移动端 SDK 模式**（只有 Web Flow + Device Flow），App 内嵌 WebView 即可；**Device Flow 本轮不做**（场景是 CLI，要用户手输 8 位码，且需在 App 设置里单独启用）。公众号 H5 授权也**本轮不做**（只能在微信内置浏览器、需第四套凭据、`snsapi_base` 拿不到 unionid）。

**最终渠道矩阵**：微信 `web` + `app`、QQ `web` + `app`、GitHub `web`，共 **8 个核心后端端点**（3 组"取 URL + 回调" + 微信 App 登录 + QQ App 登录）。

## 1. 微信登录

**适用场景**：微信开放平台 → 网站应用 → 微信登录（PC 扫码）。走 `authorization_code` 模式，必须有 server 端。

### 1.1 流程

```
① 前端跳转/内嵌 iframe
   https://open.weixin.qq.com/connect/qrconnect?appid=...&...#wechat_redirect
   ↓ 用户扫码并在手机上确认
② 微信 302 回 redirect_uri?code=CODE&state=STATE
   ↓ 后端拿 code
③ GET  api.weixin.qq.com/sns/oauth2/access_token   → access_token + openid(+unionid) + refresh_token
   ↓
④ GET  api.weixin.qq.com/sns/userinfo              → 昵称 / 头像 / unionid
   （access_token 过期后 → GET sns/oauth2/refresh_token 续期）
```

- `code` 超时 **10 分钟**，**一次性**：一个 code 只能成功换一次 token，换过即失效（换第二次报 `40163 code been used`）。
- 用户禁止授权时**不会发生重定向**（前端拿不到回调，只能超时处理）——这是与 GitHub/QQ 的差异，GitHub 会带 `?error=access_denied` 回来。
- access_token 有效期 **7200 秒（2 小时）**；refresh_token 有效期 **30 天且无法续期**。

### 1.2 端点清单

#### 1.2.1 授权页（请求 code）

- **URL**：`https://open.weixin.qq.com/connect/qrconnect`
- **Method**：`GET`（浏览器跳转）
- **注意**：完整 URL 必须以下列锚点结尾 → `#wechat_redirect`。少这个后缀会白屏或提示"该链接无法访问"。

**请求参数**

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `appid` | string | **是** | 应用唯一标识，开放平台提交应用审核通过后获得 |
| `redirect_uri` | string | **是** | 回调地址，**必须 urlEncode**；域名必须与审核时填写的授权域名一致 |
| `response_type` | string | **是** | 固定填 `code` |
| `scope` | string | **是** | 授权作用域，网页应用目前仅填 `snsapi_login`；多个用逗号分隔 |
| `state` | string | 否 | 用于保持请求与回调状态，授权后原样带回；防 CSRF 建议必带（随机数 + session 校验） |
| `lang` | string | 否 | 界面语言：`cn`（中文简体）/ `en`（英文），默认 `cn` |

**完整 URL 样例**

```
https://open.weixin.qq.com/connect/qrconnect?appid=wx1234567890abcdef&redirect_uri=https%3A%2F%2Fapi.example.com%2Fapi%2Fv1%2Fauth%2Fwechat%2Fcallback&response_type=code&scope=snsapi_login&state=9f8a7b6c5d4e3f2a#wechat_redirect
```

**回调返回**

```
https://api.example.com/api/v1/auth/wechat/callback?code=CODE&state=STATE
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `code` | string | 授权临时票据，10 分钟有效、一次性 |
| `state` | string | 原样回带 |

> 用户拒绝授权时**不重定向**，前端只有超时一条路。需前端自行做"用户取消"兜底。

**内嵌二维码（可选，非 SDK 必需）**：引入 `http://res.wx.qq.com/connect/zh_CN/htmledition/js/wxLogin.js`，`new WxLogin({self_redirect, id, appid, scope, redirect_uri, state, style, href, stylelite, fast_login, color_scheme, onReady, onQRcodeReady})`。SDK 不封装，前端自理；后端只需要同一个 `redirect_uri` 收 code。

#### 1.2.2 通过 code 换取 access_token

- **URL**：`https://api.weixin.qq.com/sns/oauth2/access_token`
- **Method**：**`GET`**（注意：不是 POST，参数全在 query）

**请求参数**

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `appid` | string | **是** | 应用唯一标识 |
| `secret` | string | **是** | 应用密钥 AppSecret（**注意参数名是 `secret`，不是 `client_secret`**） |
| `code` | string | **是** | 第一步获取的 code |
| `grant_type` | string | **是** | 固定填 `authorization_code` |

**响应字段**

| 字段 | 类型 | 说明 |
|---|---|---|
| `access_token` | string | 接口调用凭证 |
| `expires_in` | int | access_token 超时时间，**单位秒，实测值 7200** |
| `refresh_token` | string | 用于刷新 access_token |
| `openid` | string | 授权用户唯一标识（**该网站应用内**唯一） |
| `scope` | string | 用户授权的作用域，逗号分隔 |
| `unionid` | string | 用户统一标识，**同一微信开放平台账号下的应用间唯一**（见 §1.4 第 3 条） |

**真实响应样例（官方原文）**

```json
{
  "access_token": "ACCESS_TOKEN",
  "expires_in": 7200,
  "refresh_token": "REFRESH_TOKEN",
  "openid": "OPENID",
  "scope": "SCOPE",
  "unionid": "o6_bmasdasdsad6_2sgVt7hMZOPfL"
}
```

**错误响应样例（官方原文）**

```json
{
  "errcode": 40029,
  "errmsg": "invalid code"
}
```

**调用频率限制**：1 万次/分钟。

#### 1.2.3 刷新 / 续期 access_token

- **URL**：`https://api.weixin.qq.com/sns/oauth2/refresh_token`
- **Method**：**`GET`**

**请求参数**

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `appid` | string | **是** | 应用唯一标识 |
| `grant_type` | string | **是** | 固定填 `refresh_token` |
| `refresh_token` | string | **是** | 上一步获取到的 refresh_token |

**响应字段**

| 字段 | 类型 | 说明 |
|---|---|---|
| `access_token` | string | 接口调用凭证 |
| `expires_in` | int | 超时时间，秒（7200） |
| `refresh_token` | string | 新的 refresh_token |
| `openid` | string | 用户唯一标识 |
| `scope` | string | 授权作用域 |

**真实响应样例（官方原文）**

```json
{
  "access_token": "ACCESS_TOKEN",
  "expires_in": 7200,
  "refresh_token": "REFRESH_TOKEN",
  "openid": "OPENID",
  "scope": "SCOPE"
}
```

**刷新语义（官方原文，很关键）**：

- 若 access_token **已超时** → 返回**新** access_token，新的超时时间；
- 若 access_token **未超时** → **不会改变 access_token**，但超时时间会刷新，相当于**续期**。
  → 所以"刷新后 access_token 变了"不能作为判断依据，必须以响应里的 access_token 为准直接覆盖。
- `refresh_token` 有效期 **30 天且无法续期**；失效后必须让用户重新授权（否则拿不到头像昵称）。
- 刷新频率限制：5 万次/分钟。

**错误响应样例**

```json
{ "errcode": 40030, "errmsg": "invalid refresh_token" }
```

#### 1.2.4 获取用户个人信息

- **Method**：`GET`

**请求参数**

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|

| `openid` | string | **是** | 普通用户标识，对当前开发者账号唯一 |

**响应字段**

|---|---|---|
| `openid` | string | 普通用户标识，对当前开发者账号唯一 |
| `nickname` | string | 普通用户昵称 |
| `sex` | int | 1 男 / 2 女（**2021-10-20 起官方已停止返回，见 §1.4**） |

**真实响应样例（官方原文）**

```json
{
  "openid": "OPENID",
  "nickname": "NICKNAME",
  "sex": 1,
  "province": "PROVINCE",
  "city": "CITY",
  "country": "COUNTRY",
  "headimgurl": "https://thirdwx.qlogo.cn/mmopen/g3MonUZtNHkdmzicIlibx6iaFqAc56vxLSUfpb6n5WKSYVY0ChQKQkiaJSgQ1dZuTOgvLLrhJbERQQ4eMsv84eavHiaiceqxibJxCfHe/0",
  "privilege": ["PRIVILEGE1", "PRIVILEGE2"],
  "unionid": "o6_bmasdasdsad6_2sgVt7hMZOPfL"

```

**错误响应样例**

```json

```

**调用频率限制**：5 万次/分钟。

> **头像 URL 会失效**：用户换头像后旧 URL 失效，官方明确建议"自己在获取用户信息后把头像下载保存"。SDK 层面至少要保证每次登录都重新拉取并覆盖 `avatar`。

### 1.3 错误码

微信没有独立的 OAuth 错误码体系，全部走**全局返回码**（`errcode` + `errmsg`，HTTP 状态码恒 200）。以下为 OAuth 链路（授权/换 token/刷新/userinfo）相关的全部常见码，取自微信开放平台[全局错误码](https://developers.weixin.qq.com/doc/oplatform/developers/errCode/)原文：

| errcode | errmsg | 含义 / 处置 |
|---|---|---|
| `-1` | `system error` | 系统繁忙，此时请开发者稍候再试 |
| `40001` | `invalid credential, access_token is invalid or not latest` | access_token 无效或不是最新的 → **重新刷新或重新授权** |
| `40002` | `invalid grant_type` | grant_type 非法（不是 `authorization_code`/`refresh_token`） |
| `40003` | `invalid openid` | openid 非法 → 检查 openid 来源 |
| `40013` | `invalid appid` | appid 非法 → 检查配置 |
| `40014` | `invalid access_token` | access_token 非法 |
| `40029` | `invalid code` | code 无效 → 引导用户重新扫码 |
| `40030` | `invalid refresh_token` | refresh_token 无效 → 必须重新授权 |
| `40066` | `invalid url` | 回调域名不在授权域名列表 / URL 非法 |
| `40163` | `code been used` | **code 已被使用**（一次性）→ 引导重新扫码，不要重试 |
| `40164` | `invalid ip, not in whitelist` | 调用 IP 不在白名单（开启了 IP 白名单时） |
| `41001` | `access_token missing` | 缺 access_token 参数 |
| `41002` | `appid missing` | 缺 appid 参数 |
| `41003` | `refresh_token missing` | 缺 refresh_token 参数 |
| `41004` | `appsecret missing` | 缺 secret（AppSecret）参数 |
| `41008` | `missing code` | 缺 code 参数 |
| `41009` | `missing openid` | 缺 openid 参数 |
| `42001` | `access_token expired` | access_token 超时 → 用 refresh_token 刷新 |
| `42002` | `refresh_token expired` | refresh_token 超时（30 天）→ **只能重新授权** |
| `45009` | `reach max api daily quota limit` | 接口日调用量超限 |
| `45011` | `api minute-quota reach limit, must slower, retry next minute` | 分钟级限频 → 需限速重试 |
| `48001` | `api unauthorized` | 接口未授权 → 应用未获得该 scope/接口权限 |

**判定逻辑建议**：`40001`/`42001` → 走 refresh；`40030`/`42002`/`40029`/`40163` → 让用户重新授权，**不要重试**；`-1`/`45009`/`45011` → 可重试（退避）。

### 1.4 坑与注意

1. **`#wechat_redirect` 是硬要求**。授权 URL 不带这个锚点会被微信拒绝（提示"该链接无法访问"）。`markbates/goth` 的 `providers/wechat/wechat.go:89` 拼出来的 URL **没有**这个后缀——这是不能直接抄它 `BeginAuth` 的具体原因。
2. **换 token 用 GET**。绝大多数 OAuth 实现默认 POST，微信这里是 GET，参数全在 query 里；`secret` 参数名也不是标准的 `client_secret`。
3. **`unionid` 的获取条件（官方原文）**：「用户统一标识。针对一个微信开放平台账号下的应用，同一用户的 unionid 是唯一的」。落地注意两点：
   - 只有**同一微信开放平台账号下**的应用之间 unionid 才一致；不同开放平台账号下同一用户 unionid **不同**；
   - 官方文档把它列为**响应字段**（不是必然存在），**官方未明文规定"未绑定同主体应用就不返回"**。工程上必须把 `unionid` 当**可空字段**处理：登录主键只认 `openid`，`unionid` 拿到就存、拿不到不报错。若将来要做"公众号 + 网站 + 小程序 一号通"，再按官方要求把应用绑定到同一开放平台账号下（[绑定开放平台账号](https://developers.weixin.qq.com/doc/oplatform/developers/product/open/bind.html)）。
4. **文档自相矛盾（必须记录）**：`sns/userinfo` 正文明确写「Open 平台授权接口将不再返回用户性别及地区信息，能力调整已于 2021 年 10 月 20 日 24 时生效」，**但同一页的响应样例里仍然列着 `sex`/`province`/`city`/`country`**。→ 实现上按"这 4 个字段可能为空"处理，不要依赖它们做任何业务展示；模型里建议干脆不落库。
5. **`refresh_token` 不能续期**。30 天到期即死，且官方明说"refresh_token 失效后，需要用户重新授权后才可以继续获取用户头像昵称"。→ 我们的 `Token` 里必须存 `refresh_token` 与到期时间，但**不能指望长期离线访问**。
6. **`access_token` 刷新后可能不变**。未超时时刷新只延长有效期、不换 token 值。不要用"access_token 是否变化"来判断刷新是否成功。
7. **用户拒绝授权无回调**。前端必须自己做取消兜底（微信不会 302 回 `?error=...`）。
8. **code 一次性 + 10 分钟**。网关/前端重复提交 callback 会直接吃 `40163`。服务端应把 `code` 做过期去重，或直接让第二次请求失败并返回"请重新扫码"。
9. **头像 URL 会失效**，官方明确要求自行转存。

### 1.5 SDK 复用结论

- **可以复用思路，不复用代码**。`markbates/goth/providers/wechat`（MIT）里 3 个端点常量（`AuthURL`/`TokenURL`/`ProfileURL`）、`ScopeSnsapiLogin = "snsapi_login"`、`userFromReader` 的字段映射与我们需求**逐字一致**，直接对着它写能少踩坑。
- **但必须自己实现**：
  - `BeginAuth` 补 `#wechat_redirect`（goth 漏了）；
  - 补 `refresh_token` 刷新端点（goth 的 wechat provider **没有实现 refresh**，只有 `RefreshToken` 字段占位）；
  - 补 `sns/auth` 校验；
  - 保留 `unionid` 为空时的容错（goth 把 `email` 拼成 `<openid>@wechat.com`，这个假邮箱策略我们**不采用**——本项目 email 是登录/合并账号的强依赖，塞假值会污染 `findOrCreate` 逻辑）。
- 依赖代价：为 3 个 GET 端点引入 goth 全量（10 直接依赖）不成立。

## 2. QQ 登录（QQ 互联）

**适用场景**：QQ 互联 → 网站应用 → QQ 登录。走 `authorization_code`（server-side / Web Server Flow）。

### 2.1 流程

```
① 前端跳转
   https://graph.qq.com/oauth2.0/authorize?response_type=code&client_id=...&redirect_uri=...&state=...
   ↓ 用户登录并授权（用户取消 → PC 端直接关闭登录页，无回调）
② 302 回 redirect_uri?code=CODE&state=STATE
   ↓
③ GET graph.qq.com/oauth2.0/token   → access_token / expires_in / refresh_token   ← 裸 query string
   ↓
④ GET graph.qq.com/oauth2.0/me      → openid                                     ← JSONP
   ↓
⑤ GET graph.qq.com/user/get_user_info → 昵称/头像/性别/省份...                     ← JSON
   （access_token 过期 → 重新走 ③ 的 grant_type=refresh_token 续票）
```

- `code` **10 分钟**有效。
- 用户取消授权：PC 端登录页**直接关闭**，无回调。
- access_token 有效期 **60 天**（官方三处一致：返回样例 `expires_in=5184000`、Step3 正文"有效期默认是 60 天"、错误码 `100014` 注释"token过期时间为60天"）。
- refresh_token：**一次有效**，每次续票返回新的；**一次登录的整个续票链最长 3 个月**。

### 2.2 端点清单

#### 2.2.1 授权页（获取 Authorization Code）

- **URL**：`https://graph.qq.com/oauth2.0/authorize`
- **Method**：`GET`

**请求参数**

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `response_type` | string | **必须** | 固定 `code` |
| `client_id` | string | **必须** | 申请 QQ 登录成功后分配的 appid |
| `redirect_uri` | string | **必须** | 回调地址，必须是注册 appid 时填写的**主域名下**的地址，需 **URLEncode** |
| `state` | string | **必须** | 客户端状态值，防 CSRF，回调原样带回；**官方标"必须"且要求严格校验绑定** |
| `scope` | string | 可选 | 请求授权的接口列表，多个用**逗号**分隔，如 `get_user_info,list_album,upload_pic`；**不传默认 `get_user_info`** |
| `display` | string | 可选 | 仅 PC 网站接入；传 `mobile` 展示移动端样式，不传默认 PC 样式 |

**回调返回样例（官方原文）**

```
http://graph.qq.com/demo/index.jsp?code=9A5F************************06AF&state=test
```

**错误返回**：`error` + `error_description` 以 **URL 参数对**形式返回，value 做 UTF-8 URL 编码。

#### 2.2.2 通过 Authorization Code 获取 Access Token

- **URL**：`https://graph.qq.com/oauth2.0/token`
- **Method**：`GET`

**请求参数**

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `grant_type` | string | **必须** | 固定 `authorization_code` |
| `client_id` | string | **必须** | appid |
| `client_secret` | string | **必须** | appkey |
| `code` | string | **必须** | 上一步的 authorization code（10 分钟过期） |
| `redirect_uri` | string | **必须** | 与上一步传入的**完全一致**（移动端 app 可不填） |
| `fmt` | string | 可选 | **历史原因默认 `x-www-form-urlencoded`**；填 `json` 则返回 JSON |
| `need_openid` | string | 可选 | `need_openid=1` 表示同时获取 openid |

**真实响应样例（官方原文，未指定 `fmt` 时）**

```
access_token=FE04************************CCE2&expires_in=5184000&refresh_token=88E4************************BE14
```

> **这是整个调研里最容易写错的一处**：整个响应 body 就是一段 query string（`a=1&b=2`），**既不是 JSON 也不是 `application/x-www-form-urlencoded` 的表单体**（没有 `Content-Type` 保证）。正确解法：`url.ParseQuery(string(body))`。

**响应字段**

| 字段 | 类型 | 说明 |
|---|---|---|
| `access_token` | string | 授权令牌 |
| `expires_in` | int | access_token 有效期，**秒；默认 60 天 = 5184000** |
| `refresh_token` | string | 续期用；**仅一次有效** |

> 若传 `fmt=json`，返回 `{"access_token":"...","expires_in":5184000,"refresh_token":"..."}`。

#### 2.2.3 刷新（权限自动续期，可选步骤）

- **URL**：`https://graph.qq.com/oauth2.0/token`（**与换 token 同一端点**，靠 `grant_type` 区分）
- **Method**：`GET`

**请求参数**

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `grant_type` | string | **必须** | 固定 `refresh_token` |
| `client_id` | string | **必须** | appid |
| `client_secret` | string | **必须** | appkey |
| `refresh_token` | string | **必须** | 首次用 Step2 拿到的；后续用**每次刷新返回的最新值** |
| `fmt` | string | 可选 | 同上，填 `json` 返回 JSON |

**真实响应样例（官方原文）**

```
access_token=FE04************************CCE2&expires_in=5184000&refresh_token=88E4************************BE14
```

**续期规则（官方原文）**：每次返回**最新的** refresh_token，**且仅一次有效**；一次登录的整个续票过程**最长有效期 3 个月**。

#### 2.2.4 获取用户 OpenID

- **URL**：`https://graph.qq.com/oauth2.0/me`
- **Method**：`GET`

**请求参数**

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `access_token` | string | **必须** | Step2 获取的 access_token |
| `fmt` | string | 可选 | **默认 jsonpb（JSONP）**；填 `json` 返回纯 JSON |
| `unionid` | string | 可选 | 传 `unionid=1` 表示**同时申请返回 unionid**（需先申请 unionid 权限，否则报 `100048`） |

**真实响应样例（官方原文，未指定 `fmt`）**

```
callback( {"client_id":"YOUR_APPID","openid":"YOUR_OPENID"} );
```

**带 unionid（官方原文）**

```
callback(
{
"client_id":"YOUR_APPID",
"openid":"YOUR_OPENID",
"unionid":"YOUR_UNIONID"
}
);
```

**错误返回样例（官方原文，注意是 JSONP 内嵌 error 对象，且带尾逗号 → 不是合法 JSON）**

```
callback(
{
"error":100016,
"error_description":"access token check failed",
}
);
```

**响应字段**

| 字段 | 类型 | 说明 |
|---|---|---|
| `client_id` | string | 对应的 appid |
| `openid` | string | 该网站/应用内唯一用户标识 |
| `unionid` | string | 同一 QQ 互联平台下不同应用间一致的用户标识（需申请权限） |
| `error` | int | 错误码（出错时替代上面字段） |
| `error_description` | string | 错误描述 |

> **剥壳实现要点**：默认返回 `callback( {...} );` —— 先取第一个 `(` 与最后一个 `)` 之间的子串再 `json.Unmarshal`。注意**错误体在对象末尾多一个逗号**（`"error_description":"..."` 后就结束，样例里 `,}`），严格 JSON 解析会失败 → 建议剥壳后先做一次 `strings.TrimRight(s, " ,\n\t")`，或干脆请求时带 `fmt=json` 规避（**推荐后者**）。

#### 2.2.5 获取用户信息

- **URL**：`https://graph.qq.com/user/get_user_info`
- **Method**：`GET`

**通用参数（所有 QQ OpenAPI 必带）**

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `access_token` | string | **必须** | 用户凭证（60 天有效期） |
| `oauth_consumer_key` | string | **必须** | 申请 QQ 登录分配的应用 appid（**参数名很特殊，不叫 `client_id`/`appid`**） |
| `openid` | string | **必须** | 用户 ID，与 QQ 号码一一对应（由 `oauth2.0/me` 获得） |

**完整请求样例（官方原文）**

```
https://graph.qq.com/user/get_user_info?access_token=YOUR_ACCESS_TOKEN&oauth_consumer_key=YOUR_APP_ID&openid=YOUR_OPENID
```

**真实响应样例（官方原文，节选）**

```json
{
  "ret": 0,
  "msg": "",
  "nickname": "YOUR_NICK_NAME",
  ...
}
```

**响应字段**（`ret`/`msg` 为通用字段，其余为 `get_user_info` 返回；QQ 官方 WIKI 该接口的完整字段表在「API 列表」中，下列为社区长期稳定观测到的字段集合，标注 `(社区)` 者官方页面未逐字段列表）

| 字段 | 类型 | 说明 |
|---|---|---|
| `ret` | int | **0 成功**，非 0 失败（HTTP 状态码仍可能 200） |
| `msg` | string | 错误信息，成功时为空串 |
| `is_lost` | int | 是否丢失相册权限等信息（社区） |
| `nickname` | string | 用户昵称 |
| `gender` | string | 性别，**默认不返回**，传 `get_user_info` 且用户授权时可能返回 `男`/`女`（社区） |
| `gender_type` | int | 性别类型，**默认不返回**，男 1 / 女 2（社区） |
| `province` | string | 省份 |
| `city` | string | 城市 |
| `year` | string | 出生年份（社区） |
| `constellation` | string | 星座（社区） |
| `figureurl` | string | 30×30 头像 URL |
| `figureurl_1` | string | 50×50 头像 URL |
| `figureurl_2` | string | 100×100 头像 URL |
| `figureurl_qq` | string | QQ 空间头像（社区） |
| `figureurl_qq_1` | string | 40×40 QQ 头像 |
| `figureurl_qq_2` | string | 100×100 QQ 头像 |
| `is_yellow_vip` | string | 是否黄钻（`0`/`1`） |
| `vip` | string | 是否会员（`0`/`1`） |
| `yellow_vip_level` | string | 黄钻等级 |
| `level` | string | QQ 等级 |
| `is_yellow_year_vip` | string | 是否年费黄钻 |

> **SDK 落库建议**：只取 `nickname` + `figureurl_qq_2`（或 `figureurl_2`）+ `gender`(若有)，其余不落库。`ret != 0` 一律当失败，把 `msg` 原样带进日志。

#### 2.2.6 获取 unionid（同一 me 端点的变体）

- **URL**：`https://graph.qq.com/oauth2.0/me?access_token=ACCESSTOKEN&unionid=1`
- **Method**：`GET`
- **前提**：**必须先在 connect.qq.com 自助申请 UnionID 权限**（应用管理 → 查看 → 应用接口 → Unionid → 申请 → 审核通过）。未申请时返回 `100048 companyid not set`。

| `110507` | 校验 APP info 签名信息失败 |
| `110508` | 获取 code 失败 |
| `110509` | SKEY 校验失败 |
| `110510` | Disable |

**网站验证失败返回码**（配置回调域名时）：`100001` 网站 url 格式不正确（长度 ≤256、只能二级目录）、`100003` 服务器连接超时、`103001` 网站 meta 信息与 QQ 提供的不一致、`103002` 网站不能使用 IP 地址和端口号。

**判定逻辑建议**：`100014`/`100013`/`100015` → 重新授权；`100036`~`100039` → refresh_token 已废，重新授权；`100020`/`100067`/`100068` → code 问题，让用户重新登录**且不要重试**；`100062`/`100032` → 限频/过载，退避重试。

### 2.4 坑与注意

1. **三种响应格式混用**（本平台最大坑，必须逐端点定制解析）：
   - `oauth2.0/token` → 裸 query string（解 `url.ParseQuery`）
   - `oauth2.0/me` → JSONP `callback( {...} );`（需剥壳）
   - `user/get_user_info` → JSON
2. **`fmt=json` 可以消掉前两个坑，但官方没说全支持**。`token` 与 `me` 的文档都写了 `fmt` 参数（填 `json` 返回 JSON），但 `me` 的 `fmt=json` 官方从未给"纯 JSON"的响应样例，只有"默认 jsonpb"。稳妥做法：**请求带 `fmt=json`，解析层同时兼容 JSON 与 JSONP**（剥壳函数是幂等的：不含 `callback(` 就直接当 JSON 解）。
3. **`user/get_user_info` 的错误不走 HTTP 状态码**。`ret != 0` 时 HTTP 可能仍是 200，body 是 `{"ret":100030,"msg":"..."}` → 必须判 `ret`。
4. **`oauth_consumer_key` 这个参数名**。所有 QQ OpenAPI 的 appid 参数都叫 `oauth_consumer_key`，不是 `client_id`。写错会得 `110404 请求参数缺少 appid` 之类。
5. **有效期口径按渠道分两套（重要，T-37a2 修正）**：**网页登录 60 天（5184000 秒）/ 移动端 SDK 登录 90 天（7776000 秒）**，两者都真实存在，不是谁抄错了谁。
   - **网页端 60 天**（官方四处一致）：`使用Authorization_Code获取Access_Token` 返回样例 `expires_in=5184000`、Step3 正文"Access_Token 的有效期默认是 60 天"、公共返回码 `100014` 注释"token 过期时间为 60 天"、`OpenAPI调用说明` 通用参数表"access_token 有 60 天有效期"。
   - **移动端 90 天**（官方唯一出处）：Android SDK 登录成功回调样例 `"expires_in":"7776000"`（`tmp/oauth/qq_login.txt:198`）。详见 §8.2.2。
   - → **代码里绝对不要硬编码天数**，一律用响应里的 `expires_in`；`Token.ExpiresIn` 直接落库即可。用固定值会导致另一渠道提前失效或延后失效。
6. **refresh_token 只一次有效 + 续票链最长 3 个月**。也就是说即使用户一直活跃，**每 3 个月也必须重新授权一次**；而且每次续票都要把新 refresh_token 覆盖旧的，否则下次必失败。
7. **`state` 官方标"必须"**。QQ 把 `state` 列为必须参数（GitHub 是"强烈建议"、微信可选）。
8. **用户取消授权无回调**：PC 端登录页直接关闭。
9. **回调地址约束最严**：必须是注册 appid 时填写的**主域名下的地址**，且不能是 IP + 端口（`103002`）。本地联调必须用 hosts + 域名，或走 QQ 提供的调试工具。
10. **unionid 要单独申请**：connect.qq.com → 应用管理 → 查看（审核状态必须"通过"）→ 应用接口 → Unionid → 申请 → 审核。未申请时 `unionid=1` 报 `100048`。
11. **iframe 不可用**：非 qq.com 域接入，用 iframe 无法携带登录态；APP 内嵌 H5 场景 QQ 互联本身不支持。

### 2.5 SDK 复用结论

- **没有可复用的库**。GitHub 上 QQ OAuth 的 Go 实现全为玩具级（见 §5），且都不覆盖 `get_user_info` 完整字段 + JSONP 剥壳 + `ret` 判定三件套。
- **自己实现**，但请把三个解析器（query string / JSONP / JSON）写成**独立可单测的纯函数**：
  - `parseQueryToken(body []byte) (*Token, error)`
  - `parseJSONP(body []byte, out any) error`（幂等：无 `callback(` 前缀直接当 JSON）
  - `getUserInfo` 里判 `ret != 0`
- 三个纯函数是 QQ 分支唯一值得单独写测试的地方（也正好对应 T-37d 的 mock server 单测）。

## 3. GitHub 登录

**适用场景**：GitHub OAuth App → Web 应用授权。标准 RFC 6749 `authorization_code`。

### 3.1 流程

```
① GET https://github.com/login/oauth/authorize?client_id=...&redirect_uri=...&scope=...&state=...
   ↓ 用户授权（拒绝 → 302 回 redirect_uri?error=access_denied）
② 302 回 redirect_uri?code=CODE&state=STATE        code 10 分钟有效
   ↓
③ POST https://github.com/login/oauth/access_token  （必须带 Accept: application/json）
   → access_token（默认不过期）
   ↓
④ GET https://api.github.com/user                    （Authorization: Bearer <token>）
   → id / login / name / avatar_url / email
   ↓ email 为空（用户设为 private）时
⑤ GET https://api.github.com/user/emails            （需 user:email scope）
   → 取 primary && verified 的那条
```

### 3.2 端点清单

#### 3.2.1 授权页

- **URL**：`https://github.com/login/oauth/authorize`
- **Method**：`GET`
- **注意**：**不支持 CORS 预检（OPTIONS）**。

**请求参数**

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `client_id` | string | **Required** | 注册 OAuth App 时获得的 client ID |
| `redirect_uri` | string | **Strongly recommended** | 授权后跳回你应用的 URL；用于与发 code 时的 URI 比对，防攻击 |
| `login` | string | Optional | 建议用指定账号登录并授权 |
| `scope` | string | Context dependent | **空格分隔**的作用域列表。不传时：从未授权过的用户 → 空 scope；已授权过的用户 → 自动带上此前授权过的全部 scope（不再弹授权页） |
| `state` | string | **Strongly recommended** | 不可猜测的随机串，防 CSRF |
| `code_challenge` | string | **Strongly recommended** | PKCE。含 `code_challenge_method` 时必填；须是随机串的 **43 字符 SHA-256 hash** |
| `code_challenge_method` | string | **Strongly recommended** | 含 `code_challenge` 时必填；**只支持 `S256`**（不支持 plain） |
| `allow_signup` | string | Optional | 未登录用户是否可注册，默认 `true` |
| `prompt` | string | Optional | 设为 `select_account` 强制弹账号选择器（非 HTTP redirect URI 或用户多账号登录时也会弹） |

**回调返回**：`redirect_uri?code=CODE&state=STATE`。`code` **10 分钟**过期；`state` 不匹配必须中止流程。

#### 3.2.2 换取 access_token

- **URL**：`https://github.com/login/oauth/access_token`
- **Method**：**`POST`**
- **注意**：**必须带 `Accept: application/json`**，否则返回 form 编码（`access_token=xxx&scope=xxx&token_type=xxx`）。

**请求参数**

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `client_id` | string | **Required** | OAuth App 的 client ID |
| `client_secret` | string | **Required** | OAuth App 的 client secret |
| `code` | string | **Required** | 第一步拿到的 code |
| `redirect_uri` | string | **Strongly recommended** | 与授权时一致，用于比对 |
| `code_verifier` | string | **Strongly recommended** | PKCE；若授权时传了 `code_challenge` 则必填，须是生成 challenge 的原串 |

**真实响应样例（官方原文，默认形式 = form 编码）**

```
access_token=gho_16C7e42F292c6912E7710c838347Ae178B4a
&scope=repo%2Cgist
&token_type=bearer
```

**真实响应样例（`Accept: application/json`，官方原文）**

```json
{
  "access_token": "gho_16C7e42F292c6912E7710c838347Ae178B4a",
  "scope": "repo,gist",
  "token_type": "bearer"
}
```

**真实响应样例（`Accept: application/xml`，官方原文）**

```xml
<OAuth>
  <token_type>bearer</token_type>
  <scope>repo,gist</scope>
  <access_token>gho_16C7e42F292c6912E7710c838347Ae178B4a</access_token>
</OAuth>
```

**带过期 token 的响应（官方原文，OAuth App 开启了 expiring tokens 或请求了 `offline_access`）**

```
access_token=gho_16C7e42F292c6912E7710c838347Ae178B4a
&expires_in=28800
&refresh_token=ghr_1B4a2e77838347a7E420ce178F2E7c6912E169246c34E1ccbF66C46812d16D5B1A9Dc86A1498
&refresh_token_expires_in=15897600
&scope=repo%2Cgist
&token_type=bearer
```

**响应字段**

| 字段 | 类型 | 说明 |
|---|---|---|
| `access_token` | string | 用户 access token，前缀 `gho_` |
| `scope` | string | 实际授予的 scope，**逗号分隔**（与请求时的空格分隔不同！） |
| `token_type` | string | `bearer` |
| `expires_in` | int | 仅过期 token：`28800`（8 小时） |
| `refresh_token` | string | 仅过期 token：前缀 `ghr_` |
| `refresh_token_expires_in` | int | 仅过期 token：`15897600`（约 6 个月不活跃过期） |

- **Method**：`GET`
- **Header**：`Authorization: Bearer OAUTH-TOKEN`（官方原文示例）

**请求**（官方原文）


**关键字段**

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | int64 | **用户唯一 ID（数值，稳定不变）** → 登录主键 |
| `login` | string | 用户名（**可变**，用户能改名）→ 只能当展示名/候选 username |

#### 3.2.4 拉取邮箱（email 为 private 时必调）

- **URL**：`https://api.github.com/user/emails`
- **Method**：`GET`
- **Header**：`Authorization: Bearer OAUTH-TOKEN`
- **前提 scope**：`user:email`

**真实响应样例（官方原文，结构）**

```json
[
  {
    "email": "octocat@github.com",
    "primary": true,
    "verified": true,
    "visibility": "public"
  },
  {
    "email": "octocat@example.com",
    "primary": false,
    "verified": true,
    "visibility": "private"
  }
]
```

**字段**

| 字段 | 类型 | 说明 |
|---|---|---|
| `email` | string | 邮箱地址 |
| `primary` | bool | 是否主邮箱 |
| `verified` | bool | 是否已验证 |
| `visibility` | string | `public` / `private` |

**取值策略**：遍历取第一条 `primary && verified`；找不到则视为"无可用邮箱"（不要拿 unverified 的邮箱做账号合并，否则可被抢注）。

#### 3.2.5 scope 含义

| scope | 含义 |
|---|---|
| `user` | **读写** profile 信息。**注意：它包含 `user:email` 与 `user:follow`** |
| `read:user` | 只读用户 profile 数据 |
| `user:email` | 读用户邮箱地址 |
| `user:follow` | 关注/取关其他用户 |
| `offline_access` | 请求"会过期的 access token + refresh token"，即使 OAuth App 未开启 expiring tokens 也生效。用于灰度测试过期 token |

> 登录场景推荐组合：**`read:user user:email`**（最小权限，正好够拿 id/login/avatar 与邮箱）。当前项目默认值就是这套（`internal/service/github_oauth.go:38`）。

### 3.3 错误码

GitHub 的 token 端点错误走标准 `error` + `error_description` + `error_uri`（**格式由 `Accept` 头决定**）。四个官方列举的错误：

**① client_id / client_secret 错误**

```json
{
  "error": "incorrect_client_credentials",
  "error_description": "The client_id and/or client_secret passed are incorrect.",
  "error_uri": "/apps/managing-oauth-apps/troubleshooting-oauth-app-access-token-request-errors/#incorrect-client-credentials"
}
```

**② redirect_uri 不匹配**

```json
{
  "error": "redirect_uri_mismatch",
  "error_description": "The redirect_uri MUST match the registered callback URL for this application.",
  "error_uri": "/apps/managing-oauth-apps/troubleshooting-authorization-request-errors/#redirect-uri-mismatch2"
}
```

**③ code 错误/过期/不匹配**

```json
{
  "error": "bad_verification_code",
  "error_description": "The code passed is incorrect or expired.",
  "error_uri": "/apps/managing-oauth-apps/troubleshooting-oauth-app-access-token-request-errors/#bad-verification-code"
}
```

**④ 主邮箱未验证**

```json
{
  "error": "unverified_user_email",
  "error_description": "The user must have a verified primary email.",
  "error_uri": "/apps/managing-oauth-apps/troubleshooting-oauth-app-access-token-request-errors/#unverified_user_email"
}
```

授权端点侧另有 `error=access_denied`（用户在授权页点拒绝，302 回 `redirect_uri?error=access_denied&error_description=...&state=...`）。

> **现状缺口**：本项目 `github_oauth.go` 已解析 `error`/`error_description`（第 164-174 行），但**未解析 `error_uri`**，也未对四个错误码做分类处置。SDK 化时建议映射成哨兵错误（`ErrCodeExpired` / `ErrBadCredentials` / `ErrRedirectMismatch` / `ErrEmailUnverified`）。

### 3.4 坑与注意

1. **`Accept: application/json` 必须带**。不带就返回 `access_token=xxx&scope=xxx&token_type=bearer` 的 form 编码，`json.Unmarshal` 直接报错。本项目已正确设置（`github_oauth.go:154`）。
2. **`email` 为 `null` 是常态**。用户把主邮箱设为 private 时 `/user` 返回 `"email": null`（不是空串）。必须走 `/user/emails`；且只认 `primary && verified`。
3. **`scope` 的分隔符在两个方向不一样**：请求时**空格**分隔（`read:user user:email`），响应里**逗号**分隔（`repo,gist`）。
4. **`login` 可变，`id` 不可变**。用 `id`（转 string 存）做唯一键。本项目已用 `github_id`（第 191 行 `strconv.FormatInt(user.ID, 10)`），正确。
5. **token 默认不过期**。官方原文：只有 OAuth App 显式开启 expiring tokens（或请求 `offline_access`）后才有 `expires_in` = 8 小时 + `refresh_token` = 6 个月。→ SDK 的 `Token.ExpiresIn` 必须容忍 **0 = 不过期**。
6. **GitHub Enterprise Server 可能不支持过期 token**。官方明确提醒：请求 `offline_access` 在 GHES 上可能无效，返回不支持的 token 且**不返回 refresh_token** → 代码不能假设 refresh_token 一定存在。
7. **PKCE 现在已列入官方"强烈建议"**。当前项目实现**没有 PKCE**，SDK 化时建议补（`code_challenge` + `code_verifier`，仅 S256）——这是纯增量，不影响现有前端流程（但需要前端配合存 `code_verifier`）。
8. **响应格式由 `Accept` 决定**：`json` → JSON，`xml` → XML，默认 → form。解析层最好按 `Content-Type` 分支，或直接强依赖 `Accept: application/json`。

### 3.5 SDK 复用结论

- **可以直接用 `golang.org/x/oauth2`** 覆盖：授权 URL 拼装（`config.AuthCodeURL`）、code 换 token（`config.Exchange`）、refresh（`token.TokenSource`）、带 token 的 HTTP client（`config.Client`）。
- **`x/oauth2` 覆盖不了 / 需要自己补的**：
  1. `/user` 与 `/user/emails` 的两次调用与 `primary && verified` 筛选（`x/oauth2` 只有 `Endpoint.UserInfoURL` 的**声明位**，不负责调用与解析）；
  2. `ExpiresIn == 0`（不过期）的语义 —— `x/oauth2` 的 `Token.Expiry` 零值就是"不过期"，天然支持；
  3. 四个错误码的分类映射；
  4. `Accept: application/json`（`x/oauth2` 默认已带，会发 `Accept: application/json`，实测满足）。
- 结论：**GitHub 分支引用 `x/oauth2`，用户信息解析自己写**。

## 4. 三家横向对比表

| 维度 | 微信（开放平台网站应用） | QQ（QQ 互联） | GitHub（OAuth App） |
|---|---|---|---|
| **授权 URL** | `https://open.weixin.qq.com/connect/qrconnect?appid=..&redirect_uri=..&response_type=code&scope=snsapi_login&state=..#wechat_redirect` | `https://graph.qq.com/oauth2.0/authorize?response_type=code&client_id=..&redirect_uri=..&state=..` | `https://github.com/login/oauth/authorize?client_id=..&redirect_uri=..&scope=..&state=..` |
| **授权 URL 特有** | 必带锚点 `#wechat_redirect`；`scope` 只能 `snsapi_login` | `state` 官方标"必须"；`display=mobile` 可切移动样式 | 可选 PKCE（`code_challenge` + `code_challenge_method=S256`）；`allow_signup`/`prompt` |
| **token 端点** | `https://api.weixin.qq.com/sns/oauth2/access_token` | `https://graph.qq.com/oauth2.0/token` | `https://github.com/login/oauth/access_token` |
| **token 端点方法** | **GET**（参数在 query） | **GET**（参数在 query） | **POST**（参数在 body） |
| **token 响应格式** | **JSON** | **URL query string**（`a=1&b=2`，非 JSON 非 form body；`fmt=json` 可切 JSON） | 默认 **form 编码**；带 `Accept: application/json` 才是 **JSON** |
| **appid 参数名** | `appid` | `client_id` | `client_id` |
| **secret 参数名** | **`secret`** | `client_secret` | `client_secret` |
| **grant_type 取值** | `authorization_code` | `authorization_code` / `refresh_token` | 不传（隐含 authorization_code） |
| **用户信息端点** | `https://api.weixin.qq.com/sns/userinfo`（GET，`access_token` + `openid`） | `https://graph.qq.com/user/get_user_info`（GET，`access_token` + **`oauth_consumer_key`** + `openid`） | `https://api.github.com/user`（GET，`Authorization: Bearer`） |
| **唯一标识字段** | 换 token 时即得 `openid`（站内唯一）+ `unionid`（开放平台账号内唯一，可空） | 需**额外一次调用** `oauth2.0/me` 拿 `openid`（JSONP）；`unionid` 需申请权限 | `/user` 返回 `id`（int64）；`login` 可变**不可用作主键** |
| **邮箱** | 不提供（`openid@wechat.com` 之类的假值是第三方库行为，非官方） | 不提供（`get_user_info` 无 email 字段） | `/user` 的 `email`（可 `null`）；私有需 `/user/emails` + `user:email` |
| **access_token 有效期** | **7200 秒（2 小时）** | **5184000 秒（60 天）** | **默认不过期**；开启 expiring tokens 后 **28800 秒（8 小时）** |
| **refresh_token 有效期** | **30 天，不可续期** | **一次有效**；整条续票链最长 **3 个月** | 仅过期 token 模式有：**6 个月不活跃过期**（15897600 秒） |
| **刷新机制** | `GET sns/oauth2/refresh_token`（`grant_type=refresh_token`）；**未超时时只续期不换 token** | `GET oauth2.0/token`（**同一端点**，`grant_type=refresh_token`）；**每次返回新 refresh_token，旧的立即失效** | 仅过期 token 模式支持；无过期 token 时无刷新概念 |
| **错误体** | `{"errcode":N,"errmsg":"..."}`，HTTP 恒 200 | `error`+`error_description`（URL 参数对）/ `ret`+`msg`（JSON）/ JSONP 内嵌 `error` | 标准 `{"error":"...","error_description":"...","error_uri":"..."}`，HTTP 4xx/200 |
| **用户拒绝授权** | **无回调**（不重定向） | **无回调**（PC 登录页直接关闭） | 302 回 `?error=access_denied` |
| **code 有效期** | 10 分钟，一次性 | 10 分钟 | 10 分钟 |
| **CORS** | — | — | **不支持 OPTIONS 预检** |
| **频率限制** | 换 token 1 万/分钟；刷新 5 万/分钟；userinfo 5 万/分钟 | 无公开统一数值（超限报 `100062`/`100032`） | REST API 5000 req/h（用户 token） |

### 6.3 字段如何解析

**token 响应**（`github_oauth.go:164-175`）：

```go
var out struct {
    AccessToken string `json:"access_token"`
    Error       string `json:"error"`
    Description string `json:"error_description"`
}
```

- 只取 `access_token`，**丢弃 `scope` 与 `token_type`**（无过期 token 场景下够用，但拿不到"实际授予的 scope"，无法校验用户是否真给了 `user:email`）。
- 错误处理：`AccessToken == ""` 时把 `error` + `error_description` 拼进 error（172-174 行）✅。

**用户信息**（`:180-196`）：

```go
var user struct {
    ID        int64  `json:"id"`
    Login     string `json:"login"`
    Name      string `json:"name"`
    Email     string `json:"email"`
    AvatarURL string `json:"avatar_url"`
}
...
ID: strconv.FormatInt(user.ID, 10),   // 191 行
```

- **`id` → string**，作为唯一键 ✅（符合官方"`id` durable、`login` 可变"的提示）。
- `name` 可能为 `null` → Go 里解成空串，无 panic ✅。

**邮箱回落**（`:197-211`）：

```go
if profile.Email == "" {
    var emails []struct {
        Email    string `json:"email"`
        Primary  bool   `json:"primary"`
        Verified bool   `json:"verified"`
    }
    if err := g.getJSON(ctx, githubEmailsAPI, token, &emails); err == nil {
        for _, e := range emails {
            if e.Primary && e.Verified { profile.Email = e.Email; break }
        }
    }
}
```

- **只在 `email` 为空时补拉**，且**只认 `primary && verified`** ✅ 完全符合官方语义（含"不能拿 unverified 做账号合并"的安全要求）。
- 注意：`email` 为 `null` 时 Go 解成 `""`，条件成立 ✅。

**默认 scope**（`:38`）：`defaultGithubScope = "read:user user:email"` ✅ 最小权限组合。

**state 管理**（`:84-121`）：Redis key 前缀 `oauth:github:state:`，TTL 10 分钟；`VerifyState` 查询后立即 `Del`（一次性）；**Redis 不可用时 `VerifyState` 直接返回 `true` 放行**（107-110 行）。

### 6.4 与 GitHub 官方文档的差异（逐条）

| # | 差异 | 影响 | 建议 |
|---|---|---|---|
| 1 | **无 PKCE**（官方现已列入"Strongly recommended"） | 中：code 被截获时可被重放（有 state + 10 分钟限制，风险可控） | SDK 化时补 `code_challenge`/`code_verifier`（S256） |
| 2 | token 响应用 **JSON body** 提交（`Content-Type: application/json`，153 行），官方文档示例全是 **form 编码** | 低：GitHub 实际接受 JSON body（已线上运行验证），但**属未文档化行为** | SDK 里改用 `application/x-www-form-urlencoded`（文档化行为，风险最低） |
| 3 | **不解析 `scope`** | 中：无法确认用户是否真的授予了 `user:email`；`/user/emails` 若因 scope 不足返回 403，现有代码走 `err == nil` 分支直接跳过，最终 email 为空 → 用户建号无邮箱 | SDK 里解析 `scope`，缺失 `user:email` 时明确报错而非静默降级 |
| 4 | **不解析 `error_uri`** | 低：只影响排错 | SDK 里带进日志 |
| 5 | **`VerifyState` 在 Redis 不可用时放行**（fail-open） | 中：Redis 挂掉时 CSRF 防护失效 | SDK 里改为 fail-closed 或至少 ERROR 日志 + 告警 |
| 6 | 错误码**未分类** | 低：`bad_verification_code` 与 `incorrect_client_credentials` 都归成同一个 `ErrInvalidParam` | SDK 里映射哨兵错误，`bad_verification_code` 返回"请重新登录"、`incorrect_client_credentials` 返回 500 并告警 |
| 7 | **无 `Accept: application/vnd.github+json` 之外的版本头**（`getJSON` 传了 `application/vnd.github+json`，222 行） | 无 | 保持 |
| 8 | **HTTP Client 超时 15s**（`:62`） | 无（合理） | SDK 里改为可配置 |

### 6.5 能否抽进 SDK 复用

**能，且改动量小**。评估：

| 现有能力 | 抽进 SDK 的形式 |
|---|---|
| 端点常量（33-36） | 直接成为 `oauthkit/github` 的包级常量 |
| `Configured()` 判空降级 | 提升为接口方法 `Configured() bool`（三家都需要"未配置即降级"语义） |
| `AuthorizeURL` + state 写 Redis | 拆两层：SDK 只管**拼 URL**（纯函数，无 Redis）；state 存取留在 `auth_service`（因为它是会话层职责，不是 OAuth 协议职责） |
| `Exchange`（换 token + 拉 profile 合一） | **拆成两步**：`Exchange(code) (*Token, error)` + `UserInfo(tok) (*User, error)`。理由：统一接口需要这样（微信/QQ 的 openid 在 Exchange 阶段就有，GitHub 的 id 要 UserInfo 才有），且拆开后 refresh 也能复用 |
| `exchangeToken` / `getJSON` | 成为 SDK 内部 HTTP 辅助（三家共用：超时、`io.LimitReader` 1MB、状态码判定） |
| `fetchProfile` + 邮箱回落 | 成为 `github.UserInfo` 的实现 |
| `findOrCreateGithubUser` | **留在 `auth_service`**，不进 SDK（这是业务：按 `github_id` 找用户 → 按 email 合并 → 建号） |

**结论**：现有 233 行里约 **150 行可直接平移**（端点、HTTP 辅助、字段解析），`AuthorizeURL` 的 Redis 部分与 `findOrCreateGithubUser` 留在业务层。改造是"搬家 + 拆接口"，不是重写。

## 7. SDK 设计建议

### 7.1 Provider 接口方法签名建议

// Package oauthkit 第三方登录（微信 / QQ / GitHub）统一抽象。
//
// 设计原则：
//  1. 抽象五件事：拼授权 URL、code 换 token、token 换用户、刷新 token、**校验外部 token**；
//  2. 平台差异全部收敛在各自实现内，调用方只见归一化后的 Token / User；
//  3. 不持有 Redis / DB / 日志，纯协议层 —— 状态存取与业务编排留在 service 层；
//  4. **实例按 (provider, channel) 构造**，因为微信/QQ 的网页应用与移动应用是两套 appid（见 §8.5 问题 1）。
package oauthkit

import (
	"context"
	"errors"
	"time"
)

// Provider 第三方登录提供方（一个实例对应一个 provider × channel 组合）。
type Provider interface {
	// Name 平台标识，与配置前缀、DB 字段前缀、路由段一致："wechat" / "qq" / "github"。
	// 注意：不含渠道 —— 账号唯一键按平台算，同一用户从 web 还是 app 登录应命中同一条绑定。
	Name() string

	// Channel 渠道标识："web"（网页扫码/PC）/ "app"（移动端 SDK）/ "mp"（公众号 H5）/ "device"（GitHub Device Flow）。
	// 用途：配置读取、日志、路由、错误提示、token 有效期语义（微信 refresh_token web=30 天 / app=180 天）。
	// 【§8 新增】
	Channel() string

	// Configured 是否已配置齐全（该 (provider, channel) 的 appid + secret 非空）。
	// 未配置时所有方法返回 ErrNotConfigured，端点据此降级为 400/4022。
	Configured() bool

	// AuthURL 生成授权跳转 URL。state 由调用方生成并自行存储校验。
	// 微信实现必须自动追加 #wechat_redirect 锚点；公众号渠道还必须保证参数顺序与官方模板一致（正则强匹配，见 §8.1.4）。
	// app 渠道（客户端 SDK 授权）不需要此方法，调用时返回 ErrAuthURLUnsupported。
	AuthURL(state string) (string, error)

	// Exchange 用授权 code 换取 token。
	// 微信/QQ 网页在此阶段即可拿到 OpenID；GitHub 的 UserID 需 UserInfo 才有。
	// 微信 app 渠道同样走这里（客户端交 code，官方同端点）；QQ app 渠道返回 ErrExchangeUnsupported（无 code）。
	Exchange(ctx context.Context, code string) (*Token, error)

	// UserInfo 用 token 拉取归一化用户信息。
	// 安全约束：Channel == "app" 且 Verified == false 时直接返回 ErrTokenNotVerified，
	// 强制调用方先经过 ValidateToken（见 §8.5 问题 2）。【§8 新增约束】
	UserInfo(ctx context.Context, tok *Token) (*User, error)

	// Refresh 刷新 token。平台不支持时返回 ErrRefreshUnsupported。
	// 注意微信「未超时时刷新只续期不换 token」，实现须以响应原值覆盖。
	// QQ app 渠道必然返回 ErrRefreshUnsupported（移动端 SDK 不返回 refresh_token，见 §8.2.2）。
	Refresh(ctx context.Context, tok *Token) (*Token, error)

	// ValidateToken 校验外部传入的 token 是否有效，并补全/校正其中的标识字段。【§8 新增】
	//
	// 用途：移动端 SDK 登录场景 —— access_token 由客户端上报，不可信，必须校验。
	//   - QQ：调 oauth2.0/me?access_token=X，比对返回的 openid 与 tok.OpenID 是否一致；
	//         不一致返回 ErrTokenMismatch（防"用 A 的 token 配 B 的 openid"）；一致则回填 Verified=true。
	//   - 微信：调 sns/auth?access_token=X&openid=Y；errcode=0 为有效。
	//   - GitHub：调 GET /user 探活（顺带校验 token 未被用户撤销）。
	//
	// 对"后端自己换来的 token"（网页/微信 app 流程），调用方可跳过本方法。
	// 返回的 Token 带上可信 openid：若调用方只传 access_token 未传 openid，QQ 实现可据此补齐。
	ValidateToken(ctx context.Context, tok *Token) (*Token, error)
}

// Token 归一化 token。
type Token struct {

**为什么 `AuthURL` 不带 context**：拼 URL 是纯字符串操作，不该有 I/O。state 存 Redis 属于会话层（现有 `GithubOAuth.AuthorizeURL` 把两者耦合在一起，是抽 SDK 时**必须拆开**的一处）。

**为什么 `Exchange` 与 `UserInfo` 分开**：三家的"用户主键何时到手"不同（微信/QQ 在 Exchange、GitHub 在 UserInfo）。若合成一个方法，返回值就得同时容纳"可能没有 ID"的状态，语义变脏；分开后各自干净，且 `Refresh` 后调 `UserInfo` 天然可复用。

#### 7.1.1 因 §8 结论修订（T-37a2）

> **上面代码块已是修订后的版本。修订全部来自第二轮多渠道调研（§8），共 3 处改动、1 处不改、2 个新增哨兵错误。**

**改了什么**

| # | 改动 | 为什么必须改（§8 依据） |
|---|---|---|
| 1 | `Name()` 收窄为**平台名**；**新增 `Channel()`** | §8.1.2 + §8.5 问题 1：微信移动应用与网站应用是**两个独立 appid**，QQ 同样（创建应用时先选类型）。若不引入 channel 维度，"配了网站 appid 去换 App 的 code"会得到 `40013 invalid appid`（微信）/ `100008`（QQ），**且错误信息看不出是配错了**。但**账号唯一键仍按平台算**，所以 `Name()` 不带渠道、`Channel()` 单独给 |
| 2 | **新增 `ValidateToken(ctx, tok) (*Token, error)`** | §8.2.2 第三步：**QQ 移动端 SDK 直接返回 access_token + openid，后端不换 token** → 该 token **由客户端上报，完全不可信**（客户端可伪造 openid/token 组合）。必须调 `oauth2.0/me` 校验并**比对 openid 一致性**。§8.2.3 结论：这是 QQ 分支的**必备能力，不是可选项** |
| 3 | `Token` **新增 `Channel` + `Verified`**；`UserInfo` 对 `Channel=="app" && !Verified` 返回 `ErrTokenNotVerified` | §8.5 问题 2：把安全要求做成**运行时硬约束**。只写在注释里靠人记，迟早有人绕过 |
| 4 | **新增哨兵错误** `ErrAuthURLUnsupported` / `ErrExchangeUnsupported` / `ErrTokenNotVerified` / `ErrTokenMismatch` | 微信/QQ 的 app 渠道没有服务端授权 URL；QQ app 渠道没有 code（`Exchange` 无输入）。用哨兵表达"这个渠道不支持这个动作"，比返回 `nil, nil` 或泛化错误更清晰 |

**为什么不改 `AuthURL` / `Exchange` / `UserInfo` / `Refresh` 的签名**

微信 App **仍然交 code**（官方原文第 788 行：与网站应用**同一端点** `sns/oauth2/access_token`），所以微信 app 渠道照常走 `Exchange`；QQ App **没有 code**，其 `Exchange` 返回 `ErrExchangeUnsupported`。这个不对称**由渠道实例的方法行为表达**，接口签名不需要变——`Provider` 仍是 6 个方法，调用方按渠道选路径。

**为什么最终没有 `UserInfoByToken(ctx, accessToken, openID)`**

`UserInfo(ctx, tok)` 本来就吃外部 `Token`，手工构造 `Token{AccessToken: x, OpenID: y}` 即可调用；再加一个方法等于同一能力两条路径（双份实现、双份测试）。**QQ 移动端真正的差异不是"token 从哪来"，而是"token 可不可信"**——那需要的是 `ValidateToken`，不是新的取值入口。完整论证见 §8.5 问题 2。

**两个渠道的最终调用姿势**

```go
// 网页渠道（微信 web / QQ web / GitHub web）：token 后端换来，天然可信
tok, err := p.Exchange(ctx, code)
u, err := p.UserInfo(ctx, tok)

// 微信 App：客户端交 code，后端换 token —— 仍走 Exchange，不需要 ValidateToken
tok, err := wechatApp.Exchange(ctx, code)
u, err := wechatApp.UserInfo(ctx, tok)

// QQ App：客户端交 access_token —— 必须先 ValidateToken
tok := &oauthkit.Token{AccessToken: req.AccessToken, OpenID: req.OpenID, Channel: "app"}
tok, err = qqApp.ValidateToken(ctx, tok)   // 内部调 oauth2.0/me，校验 + 比对 openid
u, err := qqApp.UserInfo(ctx, tok)          // Verified=true 才放行
```

> **⚠ 最容易被"统一"掉的两处差异，务必保留**：
> 1. **微信 App 交 code、QQ App 交 token** —— 别为了接口统一让微信 App 也接受客户端 token（微信没有"校验 token 归属"的公开端点能做同等强度校验，`sns/auth` 只能验有效性，不能验 openid 主张）。
> 2. **`unionid` 才是多端打通键，`openid` 不是** —— 微信 web 与 app 是两个 appid，同一用户的 `openid` 在两者下**不同**、`unionid` **相同**。绑定表唯一键虽为 `provider + openid`，但登录查找必须**先按 `provider + unionid` 查**，查不到再按 `openid` 查，否则同一人从 PC 和 App 登录会变成两个账号。

#### 7.1.2 接线禁令清单（T-37c 必读，全部来自实测踩坑）

> 本节是给 **service 层接线者**的硬约束。SDK 内部的注释接线者不会读，所以把「会出事的地方」提到文档级。
> 三条来源：①`oauth-wechat` / `oauth-qq` 审计中**各自独立**发现的同一类风险；②两位成员都差点写出的错误实现；③我（lead）复核时实测复现的路径。

##### 禁令 1｜禁止把 `Token` / `User` 整体打进日志

`Token.Raw []byte` 保存**原始响应体**，而微信换 token 响应与 QQ 换 token 响应**都含 `access_token` + `refresh_token` 明文**（QQ 是裸 query string，更是直接可读）。

| 禁止写法 | 后果 |
|---|---|
| `fmt.Printf("%+v", tok)` / `fmt.Sprintf("%v", tok)` | `Raw:[123 34 97 ...]` 是**字节数组但不是加密**——`bytes.NewBuffer(...).String()` 或逐字节转 char 立即还原明文 |
| `zap.Any("token", tok)` / `zap.Infow("tok", tok)` | 同上，且结构化日志会被采集系统长期留存 |
| `json.Marshal(tok)` | `Raw` 是 `[]byte`，JSON 里会变成 **base64 字符串**，比字节数组更隐蔽 |
| `fmt.Errorf("failed: %+v", tok)` | 错误信息进日志 = 同一条泄漏路径 |
| `log.Infof("resp: %s", tok.Raw)` | 直接明文 |

**允许打日志的字段白名单**：`Provider` / `Channel` / `OpenID` / `UnionID`（debug 级）/ `ExpiresIn` / `Scope` / `Verified`。

**`Raw` 的唯一合法用途**：解析失败时在 **debug 级**日志里输出**长度**（`len(tok.Raw)`），而不是内容 —— 知道「上游返回了 0 字节 / 500 字节」通常足够定位，内容要看就上机器手工抓。

##### 禁令 2｜错误信息里禁止夹带响应体片段

实测教训：`oauth-qq` 一度写了 `qqTruncateForErr(body, 120)` 想把响应体前 120 字节塞进错误信息方便排错，写完自己意识到「这等于把『调用方可能打印』升级成『我们主动打印』」，主动删掉改为只报字节数。

**规则**：错误信息里只放**长度**、**HTTP 状态码**、**平台错误码**（`errcode=40029` / `ret=100019`），不放响应体、不放 token 片段、不放 openid 全值。

##### 禁令 3｜`AuthURL` / `Exchange` / `Refresh` 的参数必须先本地校验

三家 SDK 实现都已统一到 `ErrInvalidArgument`（`types.go:167`）：

| 场景 | 正确哨兵 | 错误做法（会误导调用方） |
|---|---|---|
| `AuthURL("")`（漏传 state） | `ErrInvalidArgument` | 照常拼 URL（**CSRF 保护静默失效**）；或套 `ErrScopeMissing`（调用方误判成「用户没授权」→ 多做一次重新授权引导） |
| `Exchange(ctx, "")` | `ErrInvalidArgument` | `ErrCodeInvalid`（那是「**平台**说 code 无效」，对应「引导用户重新授权」；空 code 是我们的 bug，对应「改代码」——处置相反） |
| `Refresh` 的 `tok == nil` / `RefreshToken == ""` | `ErrInvalidArgument` | 带着空 token 打上游（白耗限频配额） |

**判定口诀**：`ErrInvalidArgument` = **我的错，重试无用**；`ErrCodeInvalid` / `ErrTokenExpired` / `ErrUpstream` = **平台侧失败，可能要重试或引导用户**。两者混用会让调用方朝反方向处理。

##### 禁令 4｜`Token.UnionID` 空串必须先判空再查询

`(provider, unionid)` 若不是唯一索引，空串在 SQL 里**会互相匹配**（空串不等于 NULL）。

```go
// ✅ 正确
if tok.UnionID != "" {
    if b, err := findByUnionID(db, tok.Provider, tok.UnionID); err == nil { ... }
}
// ❌ 错误：所有拿不到 unionid 的用户（微信 web 常见、GitHub 恒无）
//    会被并成同一个账号 —— 比登录失败严重得多的数据事故
b, err := findByUnionID(db, tok.Provider, tok.UnionID)
```

##### 禁令 5｜`Channel=="app" && !Verified` 的 token 一律不信

这是 SDK 里的运行时硬约束（`UserInfo` 直接返回 `ErrTokenNotVerified`），但接线者要理解**为什么**：

- 微信 App：客户端交 **code**，后端 `Exchange` 换来 token → `Verified` 由 Exchange 置 true，可信。
- QQ App：客户端交 **access_token + openid**，两者都可伪造 → 必须 `ValidateToken`（内部调 `oauth2.0/me` 校验并**比对 openid 一致性**）后才 `Verified=true`。

**禁止**为了让流程跑通而手工 `tok.Verified = true` —— 那等于把伪造防护整条拆掉。

##### 禁令 6｜`sns/auth` / `oauth2.0/me` 的响应必须校验"是不是平台的响应"

实测缺陷（`oauth-wechat` 审计发现，已修）：微信 `sns/auth` 的成功体是 `{"errcode":0,"errmsg":"ok"}`，若用**值类型**接 `errcode`，字段缺失 → 零值 0 → 判成成功。后果：**上游返回任何非微信格式的 200 响应（网关错误页、空 body、CDN 兜底 JSON）都让伪造 token 通过校验**，`ErrTokenNotVerified` 硬约束被整条拆掉。

同一类问题在 QQ 侧出现两次（`oauth-qq` 审计发现，已修）：
- `url.ParseQuery` 把 HTML 错误页解成一个怪 key 且 `err=nil` → 需「必须解出至少一个已知字段」判定
- JSON 分支同样：`{"status":"error"}` 是合法 JSON 但不含 QQ 字段 → 同样需判定

**规则**：校验类端点的解析必须**双向验证**——①能解析；②解析出的内容确实含该平台的标志字段。只有 ① 等于没验。

##### 禁令 7｜`expires_in` 的边界（QQ app 特有）

QQ 移动端 SDK 回调的 `expires_in` 是**字符串** `"7776000"`（不是数字），且官方样例 `msg` 拼成 `"sucess"`。SDK 已用 `qqFlexInt` + `ParseQQAppLoginPayload` 兜住，但接线者要知道：

- **`ExpiresIn == 0` 的语义是「不过期」**（`types.go` 明确规定，GitHub 默认如此）。若上游因解析失败静默给了 0，**过期 token 会被当成永久有效** → `ExpiresIn` 的解析失败必须报错，不能兜底成 0（SDK 已这么做）。
- 溢出风险：`time.Duration(n) * time.Second` 是 int64 纳秒乘法，超过 ~292 年回卷到过去。SDK 已截断到 `math.MaxInt64 / int64(time.Second)`。

### 7.2 三家共有 vs 平台特有

**可放公共层（`oauthkit` 包内共享）**

| 能力 | 说明 |
|---|---|
| HTTP 客户端封装 | 统一超时（默认 15s，可配）、`io.LimitReader` 限流 1MB、状态码非 2xx 判定、Context 透传 |
| `Token` / `User` 归一化结构 | 见 §7.1 |
| 哨兵错误 | 三家错误码各自映射到同一批 `Err*`（§7.1 列表） |
| URL 参数拼装 | `url.Values` 构造 + `Encode()`（注意微信 `redirect_uri` 必 urlEncode） |
| `ExpiresIn → ExpiresAt` 推导 | 含 `ExpiresIn == 0 → 零值 time（不过期）` |
| 配置校验骨架 | `Configured()` 的"必填项判空"逻辑（各家只声明必填 key 列表） |
| 响应体读取 + 大小限制 | 三家共用 |

**平台特有（各自实现，不进公共层）**

| 平台 | 特有 |
|---|---|
| 微信 | ① `#wechat_redirect` 锚点追加；② **GET** 换 token；③ `secret` 参数名；④ `errcode`/`errmsg` 错误解析（HTTP 恒 200）；⑤ 响应里的 `openid`/`unionid` 直取；⑥ `Refresh` 的"未超时不换 token"语义；⑦ 可选的 `sns/auth` 校验；⑧ JS-SDK 内嵌二维码（不封装）；**⑨（§8 新增）app 渠道：scope 只能 `snsapi_userinfo`、`refresh_token` 180 天（web 是 30 天）、`unionid` 当且仅当已获 userinfo 授权才返回、客户端只交 code 不交 token；⑩（不实现）公众号渠道：`oauth2/authorize` + 参数顺序正则强匹配 + code 仅 5 分钟** |
| QQ | ① 三种响应格式解析器（query string / JSONP / JSON）；② `oauth_consumer_key` 参数名；③ **两步取 openid**（`oauth2.0/me`）；④ `ret`/`msg` 错误判定（HTTP 200）；⑤ `refresh_token` 一次有效 + 续票链 3 个月；⑥ unionid 需 `unionid=1` + 单独申请权限；⑦ `display=mobile`；**⑧（§8 新增）app 渠道：SDK 直给 access_token+openid（无 code 可换）、无 refresh_token、有效期 90 天（web 60 天）、`expires_in` 是字符串、字段含 `pay_token`/`pf`/`pfkey`、**必须 `ValidateToken` 校验 token 归属** |
| GitHub | ① POST form 编码换 token + `Accept: application/json`；② PKCE（S256）；③ `/user` + `/user/emails` 两次调用与 `primary && verified` 筛选；④ `ExpiresIn == 0` = 不过期；⑤ `error`/`error_description`/`error_uri` 解析；⑥ `scope` 响应侧逗号分隔；**⑦（§8 结论）无原生移动 SDK 模式，App 内嵌 WebView 走同一套 web 流程；Device Flow 本轮不实现** |

**边界原则**：**"HTTP 怎么发、body 怎么解"进各自实现；"发完之后数据结构长什么样"进公共层。** 不要把 QQ 的 JSONP 剥壳塞进公共层（只有一家用），也不要把三家的 4 个 HTTP 请求重复写三遍（公共层统一）。

### 7.3 配置结构建议

> **本节已按 §8.5 问题 1 修订（T-37a2）**：配置键统一为 `<provider>_<channel>_<field>`，Provider 实例按 `(provider, channel)` 构造。

**Go 侧结构体**

```go

	Scopes       []string      // 微信 web [snsapi_login] / 微信 app [snsapi_userinfo] / QQ [get_user_info] / GitHub [read:user user:email]
	SuccessURL   string        // 登录成功后前端跳转地址（非 OAuth 协议参数，业务用）
	Timeout      time.Duration // HTTP 超时，默认 15s

	// 平台特有
	WeChat *WeChatConfig
	QQ     *QQConfig
	GitHub *GitHubConfig
```

**数据模型建议（T-37b 决策点，供 lead 定）**

现有 `model.User` 只有 `github_id` / `github_username`。两个方案：

| 方案 | 结构 | 优点 | 缺点 |
|---|---|---|---|
| **A. 单表列扩展** | `users` 加 `wechat_openid` / `wechat_unionid` / `qq_openid` / `qq_unionid`（各 uniqueIndex） | 改动小、查询无 join、与现有 `github_id` 风格一致 | 每加一个平台加 2 列；一人多平台账号只能绑一个；**多渠道下语义更乱**（web/app 两个 openid 存一列？） |
| **B. 独立绑定表** `user_oauth_binding(id, user_id, provider, channel, openid, unionid, expires_at, union UNIQUE(provider, openid))` | 规范化 | 天然支持一人多绑、加平台零改动、**能记录渠道与 token 到期时间** | 要迁移现有 `github_id` 数据、多一次 join、`findOrCreate` 逻辑重写 |

**倾向 B（T-37a2 后更确定）**，理由：
1. `provider + openid` 唯一索引天然表达"同一平台内 openid 唯一"的语义，比散落的 4 个 uniqueIndex 列更不容易写错；
2. 将来加抖音/微博/B站不用改表；
3. **§8 带来的新硬需求**：同一平台的多渠道（微信 web/app）产生**不同的 openid**，还需要记录 `channel` 与各自不同的 `refresh_token` 到期时间（微信 web 30 天 / app 180 天），单表列扩展无法表达；
4. 本项目不兼容存量数据（AutoMigrate 全新建库），迁移成本一次性且很小。

> **⚠ 唯一键之外的查询修正（§8.5 问题 1 结论）**：唯一索引是 `(provider, openid)`，但**登录时的查找顺序必须是先 `provider + unionid`、后 `provider + openid`**。因为微信 web 与 app 是两个 appid，同一用户的 openid 在两端不同、unionid 相同；若只按 openid 查，同一人从 PC 与 App 登录会**变成两个账号**。`unionid` 为空时（GitHub、QQ 未申请 unionid 权限）退回 openid 查找。

## 8. 多渠道接入（移动端 SDK / 网页扫码）

> 本节为 T-37a2 追加（用户需求：微信和 QQ 要同时支持「移动端 SDK 授权登录」与「网页版扫码/快捷登录」）。
> 抓取产物在 `tmp/oauth/`：`wx_app_dev.txt`（微信移动应用开发指南）、`wx_app_union.txt`（移动应用授权后接口调用）、`wx_scan.txt`（移动应用扫码登录）、`wx_mp.txt`（公众号网页授权）、`qq_login.txt`（QQ Android SDK 环境搭建含登录返回）、`qq_client.txt`（QQ Client-side 攻略）、`gh.txt`（GitHub Device Flow）。

### 8.1 微信 — 三种接入形态的差异

#### 8.1.1 形态速查表

| 形态 | 授权入口 | 授权 URL / SDK | scope 取值 | 换 token 端点 | 可用环境 | code 有效期 |
|---|---|---|---|---|---|---|
| **移动应用（App）** | 客户端 SDK | `WXApi.sendReq(SendAuth.Req)` | **`snsapi_userinfo`（只能填这个）** | `sns/oauth2/access_token` | 已安装微信客户端的手机 | 10 分钟 |
| **网站应用（PC 扫码）** | 浏览器跳转 | `open.weixin.qq.com/connect/qrconnect` | **`snsapi_login`** | `sns/oauth2/access_token` | PC 浏览器 | 10 分钟 |
| **公众号（微信内 H5）** | 浏览器跳转 | `open.weixin.qq.com/connect/oauth2/authorize` | `snsapi_base` / `snsapi_userinfo` | `sns/oauth2/access_token` | **仅微信内置浏览器** | **5 分钟** |

**结论先行（三个要点）**：

1. **移动应用和网站应用是两个独立应用，appid 不同**。微信开放平台的「移动应用」与「网站应用」是管理中心里两个独立入口，各自单独提交审核、各自获得 AppID/AppSecret（官方原文：移动应用指南的准备工作要求"拥有一个已审核通过的**移动应用**，并获得相应的 AppID 和 AppSecret"；网站应用指南要求"拥有一个已审核通过的**网站应用**"）。→ **必须两套配置**（见 §8.5 问题 1）。
2. **换 token 走同一个端点** `https://api.weixin.qq.com/sns/oauth2/access_token`，参数与响应结构完全一致；`sns/oauth2/refresh_token`、`sns/userinfo`、`sns/auth` 也全部复用。→ **SDK 的 `Exchange`/`Refresh`/`UserInfo` 三家形态共用一份实现，只有 `AuthURL`（其实是客户端发起，后端用不到）与 scope/配置不同。**
3. **移动应用能拿到 unionid**，但有前置条件（官方原文，见下）。

#### 8.1.2 移动应用（App）登录

**第一步：客户端发起授权（SDK 侧，后端不参与）**

iOS（官方原文）：

```objc
-(void)sendAuthRequest {
    // 构造 SendAuthReq 结构体
    SendAuthReq* req = [[[SendAuthReq alloc] init] autorelease];
    req.scope = @"snsapi_userinfo";   // 只能填 snsapi_userinfo
    req.state = @"123";
    // 第三方向微信终端发送一个 SendAuthReq 消息结构
    [WXApi sendReq:req];
}
```

Android（官方原文）：

```java
// send oauth request
final SendAuth.Req req = new SendAuth.Req();
req.scope = "snsapi_userinfo";       // 只能填 snsapi_userinfo
req.state = "wechat_sdk_demo_test";
api.sendReq(req);
```

鸿蒙（官方原文）：

```ts
let req = new wxopensdk.SendAuthReq;
req.scope = "snsapi_userinfo";       // 只能填 snsapi_userinfo
req.state = "wechat_sdk_demo_test";
this.wxApi.sendReq(getContext(this) as common.UIAbilityContext, req)
```

**SDK 请求参数**

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `appid` | string | **是** | 应用唯一标识（**移动应用的 appid，不是网站应用的**） |
| `scope` | string | **是** | **只能填 `snsapi_userinfo`**（官方原文括号强调两次） |
| `state` | string | 否 | 原样带回；官方特别提示：**state 会作为 URL 的一部分传递，建议做 urlEncode**，防止含 `#`、`&` 等特殊字符导致无法正确回传 |

**SDK 回调返回（`SendAuth` 的 `Resp`）**

| 字段 | 类型 | 说明 |
|---|---|---|
| `ErrCode` | int | `ERR_OK = 0`（用户同意）/ `ERR_AUTH_DENIED = -4`（用户拒绝授权）/ `ERR_USER_CANCEL = -2`（用户取消） |
| `code` | string | 换取 access_token 的票据，**仅在 `ErrCode == 0` 时有效** |
| `state` | string | 原样回传，**长度不能超过 1K** |
| `lang` | string | 微信客户端当前语言 |
| `country` | string | 微信用户当前国家信息 |

> **后端注意**：`ErrCode != 0` 时客户端**不应该**上报 code（code 无效）。后端也应对空 code 直接拒绝，别把空串发给微信换 token（会吃 `41008 missing code`）。

**第二步：后端用 code 换 access_token（与网站应用同一端点）**

- **URL**：`https://api.weixin.qq.com/sns/oauth2/access_token`
- **Method**：`GET`（官方原文第 788 行明示该链接）

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `appid` | string | **是** | **移动应用**的 appid |
| `secret` | string | **是** | **移动应用**的 AppSecret |
| `code` | string | **是** | SDK 回传的 code（10 分钟有效，一次性） |
| `grant_type` | string | **是** | 固定 `authorization_code` |

**真实响应样例（官方原文，移动应用页）**

```json
{
  "access_token": "ACCESS_TOKEN",
  "expires_in": 7200,
  "refresh_token": "REFRESH_TOKEN",
  "openid": "OPENID",
  "scope": "snsapi_userinfo",
  "unionid": "o6_bmasdasdsad6_2sgVt7hMZOPfL"
}
```

**错误响应样例（官方原文）**

```json
{"errcode":40029,"errmsg":"invalid code"}
```

**字段说明（官方原文，注意 `unionid` 那句）**

| 字段 | 类型 | 说明 |
|---|---|---|
| `access_token` | string | 接口调用凭证 |
| `expires_in` | int | 超时时间，单位秒（7200） |
| `refresh_token` | string | 用于刷新 access_token |
| `openid` | string | 授权用户唯一标识 |
| `scope` | string | 用户授权的作用域（`snsapi_userinfo`） |
| `unionid` | string | **「当且仅当该移动应用已获得该用户的 userinfo 授权时，才会出现该字段」** |

> **这是回答"移动应用能拿到 unionid 吗"的官方依据**：能，但**条件是拿到了 userinfo 授权**。而 App 形态的 `scope` **只能填 `snsapi_userinfo`**，所以**正常走完授权流程的 App 登录一定有 unionid**。这与网站应用（scope 固定 `snsapi_login`，unionid 描述里没有"当且仅当"限定）形成对比——**App 端拿到 unionid 的确定性反而比网站端更高**。
> 官方**没有**要求"必须绑定开放平台账号才能拿 unionid"，只说 unionid 的**唯一性范围**是"同一开放平台账号下的应用"。绑定只影响**跨应用是否一致**，不影响**是否返回**。

**第三步：刷新 access_token**

- **URL**：`https://api.weixin.qq.com/sns/oauth2/refresh_token`
- **Method**：`GET`

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `appid` | string | **是** | 移动应用 appid |
| `grant_type` | string | **是** | 固定 `refresh_token` |
| `refresh_token` | string | **是** | 上一步获取的 refresh_token |

**真实响应样例（官方原文）**

```json
{
  "access_token": "ACCESS_TOKEN",
  "expires_in": 7200,
  "refresh_token": "REFRESH_TOKEN",
  "openid": "OPENID",
  "scope": "SCOPE"
}
```

**错误响应样例（官方原文）**

```json
{ "errcode": 40030, "errmsg": "invalid refresh_token" }
```

**⚠ 两种形态的 refresh_token 有效期不同（官方原文对照）**

| 形态 | refresh_token 有效期 | 官方原文位置 |
|---|---|---|
| 移动应用（App） | **180 天** | `wx_app_dev.txt:835`「refresh_token 拥有较长的有效期（**180 天**），当 refresh_token 失效后，需要用户重新授权」 |
| 网站应用（PC 扫码） | **30 天** | `wx_union.txt:743`「refresh_token 拥有较长的有效期（**30 天**）且无法续期」 |

→ 这是 §1 里"30 天"结论的**重要补充**：**不能跨形态套用**。SDK 的 token 存储必须按 `(provider, channel)` 分区。

**第四步：获取用户信息**

- **URL**：`https://api.weixin.qq.com/sns/userinfo`（与网站应用完全相同）
- **Method**：`GET`，参数 `access_token`（必）、`openid`（必）、`lang`（可选）
- **响应字段与样例**：见 §1.2.4（含 2021-10-20 起不返回性别/地区的问题）

**移动端特有错误码（单独列）**

**A. SDK 层错误码（`SendAuth.Resp.ErrCode`，不走 HTTP）**

| ErrCode | 常量 | 含义 | 后端处置 |
|---|---|---|---|
| `0` | `ERR_OK` | 用户同意授权 | 正常流程，code 有效 |
| `-2` | `ERR_USER_CANCEL` | **用户取消**（点了返回/关闭） | 前端提示"已取消"，**不上报 code** |
| `-4` | `ERR_AUTH_DENIED` | **用户拒绝授权** | 前端提示"授权失败"，**不上报 code** |

> 这三个是**客户端 SDK 返回值，不是微信服务端错误码**。后端 API 永远收不到它们——除非客户端把它们透传上来。SDK 层面无需后端处理，但**接口文档要给客户端写清楚**：`ErrCode != 0` 时不要调后端登录接口。

**B. 服务端错误码（移动应用新增/强调的）**

| errcode | errmsg | 含义 | 说明 |
|---|---|---|---|
| `10060` | 系统错误，错误码：10060 | **未上架应用的微信登录日限额（100 次/天）用尽** | 官方 FAQ 明确：已认证主体的**未上架**移动应用登录次数限制 **100 次/天**；解决方式是把 Android/iOS/鸿蒙**分别**设置为"已上架"并提交审核 |
| `45011` | `api minute-quota reach limit, must slower, retry next minute` | 分钟级限频 | **移动应用额外约束：同一用户（openid）一分钟内合计调用不得超过 180 次**，超过视为恶意攻击 |

> 其余 OF OAuth 相关错误码（`40029`/`40030`/`40163`/`42001`/`42002`/`41008` 等）与网站应用完全一致，见 §1.3。

**C. 移动应用 vs 网站应用 频率限制差异（官方原文）**

| 接口 | 移动应用 | 网站应用 |
|---|---|---|
| 通过 code 换取 access_token | **5 万/分钟** | 1 万/分钟 |
| 刷新 access_token | **10 万/分钟** | 5 万/分钟 |
| 获取用户基本信息 | 5 万/分钟 | 5 万/分钟 |

**D. 官方安全要求（必须落到实现里）**

官方原文（`wx_app_dev.txt:864-868`）：

- AppSecret 泄漏会导致应用数据泄漏；**存储在客户端极可能被反编译窃取**；
- access_token 相当于用户登录态，**存储在客户端**可能被恶意获取；
- refresh_token 泄漏等同于 access_token 泄漏；
- **「建议将 AppSecret、用户数据（如 access_token）放在 App 云端服务器，由云端中转接口调用请求」**。

→ **SDK 设计强制约束**：**AppSecret 永不下发客户端；App 登录必须走"客户端只交 code、云端换 token"**。这正是本 SDK 的形态（`POST /auth/wechat/app/login {code}`）。

#### 8.1.3 网站应用扫码登录（已调研，仅列与移动应用的差异）

| 维度 | 网站应用 | 移动应用 |
|---|---|---|
| appid / secret | 独立一套 | 独立一套 |
| 授权发起 | 后端给 URL，前端跳转/内嵌 iframe | 客户端 SDK 本地拉起微信 |
| scope | `snsapi_login`（固定） | `snsapi_userinfo`（只能填这个） |
| unionid 返回条件 | 描述为"同一开放平台账号下唯一"（未加限定） | **"当且仅当已获 userinfo 授权"** |
| 用户拒绝授权 | **无回调**（不重定向） | SDK 回调 `ErrCode = -2 / -4`（**有明确信号**） |
| refresh_token 有效期 | 30 天 | **180 天** |
| 换 token 频率 | 1 万/分钟 | 5 万/分钟 |
| `#wechat_redirect` | **必须** | 不涉及（SDK 调用） |

**补充：微信「快速登录」**（网站应用侧，第一轮已抓到的官方说明）——微信 3.9.11 for Windows+ / 4.0.0 for Mac+ 上，用户已登录 PC 微信客户端且未锁定时，`qrconnect` 会**优先提示免扫码确认**。这对「网页版快捷登录」是**零成本增强**：同一个 `qrconnect` 端点，无需任何改动，后端只感知到"用户很快回调了"。

#### 8.1.4 公众号网页授权（微信内 H5）

- **URL**：`https://open.weixin.qq.com/connect/oauth2/authorize`
- **Method**：`GET`（浏览器跳转）
- **运行环境**：**仅微信内置浏览器**（公众号会话、自定义菜单、微信内打开的链接）

**请求参数（官方原文）**

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `appid` | string | **是** | **服务号的唯一标识（仅支持填写已认证的服务号 appid，其他类型的账号不支持）** |
| `redirect_uri` | string | **是** | 授权后重定向地址，需 **urlEncode**；必须与微信公众平台「设置与开发 - 账号设置 - 功能设置 - **网页授权域名**」配置一致 |
| `response_type` | string | **是** | 固定 `code` |
| `scope` | string | **是** | `snsapi_base`（不弹授权页，直接跳转，**只能拿 openid**）/ `snsapi_userinfo`（弹授权页，可拿昵称、性别、所在地；**未关注也能拿**） |
| `state` | string | 否 | 重定向后带回；**只允许 `a-zA-Z0-9`，最多 128 字节**（注意：与网站应用的"随机数+session"不同，这里有字符集硬限制） |
| `#wechat_redirect` | — | **是** | **「无论直接打开还是做页面 302 重定向时候，必须带此参数」** |
| `forcePopup` | bool | 否 | 强制本次授权弹窗确认；默认 `false`；用户命中特殊场景静默授权逻辑时此参数不生效 |

**scope 差异（官方原文）**

| scope | 行为 | 能拿到 |
|---|---|---|
| `snsapi_base` | 静默授权，自动跳回，不弹确认框 | **仅 openid**（无昵称头像） |
| `snsapi_userinfo` | 需用户手动同意（已关注用户在公众号会话/菜单进入时可静默） | openid + 昵称 + 头像 + unionid（见下） |

**unionid 的关键限定（官方原文，`wx_mp.txt:384`）**：

> 用户统一标识（针对一个微信开放平台账号下的应用，同一用户的 unionid 是唯一的），**只有当 scope 为 `"snsapi_userinfo"` 时返回**

→ **`snsapi_base` 静默授权拿不到 unionid**。若业务需要"微信内 H5 静默登录 + 与 App/PC 打通账号"，`snsapi_base` 走不通，必须 `snsapi_userinfo`（会弹窗，或依赖"已关注用户从公众号进入"这一静默场景）。

**官方原文 URL 样例**

```text
scope 为 snsapi_base 的示例
https://open.weixin.qq.com/connect/oauth2/authorize?appid=wx520c15f417810387&redirect_uri=https%3A%2F%2Fchong.qq.com%2Fphp%2Findex.php%3Fd%3D%26c%3DwxAdapter%26m%3DmobileDeal%26showwxpaytitle%3D1%26vb2ctag%3D4_2030_5_1194_60&response_type=code&scope=snsapi_base&state=123#wechat_redirect

scope 为 snsapi_userinfo 的示例
https://open.weixin.qq.com/connect/oauth2/authorize?appid=wx807d86fb6b3d4fd2&redirect_uri=http%3A%2F%2Fdevelopers.weixin.qq.com&response_type=code&scope=snsapi_userinfo&state=STATE#wechat_redirect
```

**回调返回（官方原文）**

```text
redirect_uri/?code=CODE&state=STATE
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `code` | string | **作为换取 access_token 的票据，每次用户授权带上的 code 将不一样，code 只能使用一次，5 分钟未被使用自动过期** |
| `state` | string | 原样带回 |

> **⚠ code 有效期 5 分钟，不是 10 分钟**。这是三种微信形态里最短的（网站/App 都是 10 分钟）。SDK 的超时/重试策略要按渠道分别配置。

**公众号特有的坑**

1. **授权链接参数顺序强匹配**（官方原文）：「由于授权操作安全等级较高，所以在发起授权请求时，微信会对授权链接做**正则强匹配校验，如果链接的参数顺序不对，授权页面将无法正常访问**」。
   → **拼 URL 时参数顺序必须与官方模板完全一致**：`appid` → `redirect_uri` → `response_type` → `scope` → `state`（→ `forcePopup`）→ `#wechat_redirect`。用 `url.Values.Encode()` 会按字母序重排（`appid, forcePopup, redirect_uri, response_type, scope, state`），**`forcePopup` 跑到了第二位** → 可能被判顺序错。这是**必须手写有序拼接**的一个实现点。
2. **必须是已认证服务号**，订阅号/未认证服务号不支持。
3. **需配置「网页授权域名」**，且 `redirect_uri` 必须在该域名下。
4. **2022-07-12 起的网页快照页限制**（官方原文）：「当开发者在网页中在不规范使用发起 `snsapi_userinfo` 网页授权时，微信将默认打开**网页快照页**模式进行基础浏览」。用户**未做任何交互**（点击按钮）就直接跳转授权链接时，网页会被固化，展示「点击访问完整网页」。
   → **必须由用户交互（点击"微信登录"按钮）触发跳转**，不能页面加载即跳。
5. **只能微信内置浏览器打开**，PC/其他浏览器不行。

**结论：是否符合"网页版快捷登录"需求？**

**不符合，只能算补充渠道。** 理由：
- 它**只在微信内置浏览器里可用**，PC 站/外部浏览器打开直接失效；
- 它需要**服务号**（已认证），是**第四套凭据**（公众号 appid/secret），与网站应用/移动应用都不同；
- `snsapi_base` 拿不到 unionid，`snsapi_userinfo` 要弹窗且受快照页限制。

→ **建议**：本轮**不实现**公众号 H5 授权，但**在 `oauthkit` 里预留 `ChannelMP` 常量与配置位**，将来做"微信内分享落地页静默登录"时直接接。若用户明确要"微信内 H5 也能登录"，则按 §8.5 问题 3 增加第 7 组端点。

#### 8.1.5 移动应用扫码登录（App 内扫码，多设备场景）

官方「移动应用扫码登录」（`wx_scan.txt`）——**注意这不是网页版扫码**，是**在 App 内部拉起二维码**，用于「多设备登录、智能硬件、电视盒子」场景。官方原文：「扫码登录能力，指的是开发者可在移动应用内使用此能力，拉取二维码，用户使用微信客户端扫描二维码后可以登录此移动应用」。

**接口（三端）**

| 平台 | 接口签名 | 关键回调 |
|---|---|---|
| iOS | `(BOOL)Auth:(NSString *)appId nonceStr:(NSString *)nonceStr timeStamp:(NSString*)timeStamp scope:(NSString *)scope signature:(NSString *)signature schemeData:(NSString *)schemeData;` | `onAuthGotQrcode:(UIImage *)image`（拿到二维码）、`onAuthFinish:(int)errCode AuthCode:(NSString *)authCode`（授权完成拿 code） |
| Android | `boolean auth(String appId, String scope, String noncestr, String timestamp, String signature, OAuthListener listener)` | `onAuthGotQrcode(qrcodeImgPath, imgBuf)`、`onQrcodeScanned()`、`onAuthFinish(OAuthErrCode, authCode)` |
| 鸿蒙 | `startOAuth(appId, scope, noncestr, timestamp, signature, callback): void` | `onGotQRCode` 等 |

**参数（官方原文）**

| 参数 | 必填 | 说明 |
|---|---|---|
| `appId` | 是 | 应用唯一标识 |
| `scope` | 是 | 授权作用域，多个用逗号分隔，App 所拥有的 scope |
| `nonceStr` / `noncestr` | 是 | 随机串，使每次 `signature` 不同 |
| `timeStamp` / `timestamp` | 是 | 时间戳 |
| `signature` | 是 | **签名**（需按开放平台规则计算，官方该页未给完整算法） |
| `schemeData` | 否（iOS） | 会在扫码后拼在 scheme 后 |

**结论**：**本轮不实现**。理由：① 场景是"多设备/智能硬件"，不是登录主链路；② 需要**客户端本地计算 signature**（官方此页未给算法），后端无参与；③ 拿到 code 后仍走 `sns/oauth2/access_token`，与 App 登录完全相同的后半段。
→ SDK 侧**无需新增任何能力**：客户端扫码拿到 code 后，直接调已有的 `POST /auth/wechat/app/login {code}` 即可。

#### 8.1.6 微信端点复用矩阵

| 端点 | 网站扫码 | 移动应用 | 公众号 H5 | SDK 是否复用 |
|---|---|---|---|---|
| `open.weixin.qq.com/connect/qrconnect` | ✅ | — | — | 否（后端只拼 URL） |
| `open.weixin.qq.com/connect/oauth2/authorize` | — | — | ✅ | 否（后端只拼 URL） |
| 客户端 SDK `SendAuth.Req` | — | ✅ | — | 否（客户端职责） |
| `api.weixin.qq.com/sns/oauth2/access_token` | ✅ | ✅ | ✅ | **✅ 完全复用** |
| `api.weixin.qq.com/sns/oauth2/refresh_token` | ✅ | ✅ | ✅ | **✅ 完全复用** |
| `api.weixin.qq.com/sns/userinfo` | ✅ | ✅ | ✅ | **✅ 完全复用** |
| `api.weixin.qq.com/sns/auth` | ✅ | ✅ | ✅ | **✅ 完全复用** |

→ **微信三形态的 SDK 代价极低**：4 个后端端点 100% 复用，只需按渠道换 appid/secret 与拼不同的授权 URL。

### 8.2 QQ — 移动端与网页端流程完全不同

#### 8.2.1 两种形态对比表（这是本节最重要的表）

| 维度 | 网页登录（Server-side） | 移动端 SDK 登录 |
|---|---|---|
| 授权发起 | 后端给 URL → 浏览器跳转 | 客户端 `Tencent.login()` / 拉起手机 QQ SSO |
| 换 token | **必须后端换**（`oauth2.0/token`，code → token） | **不需要换**——SDK **直接返回 access_token** |
| 拿 openid | 需额外调 `oauth2.0/me`（JSONP） | **SDK 直接返回 openid** |
| code | 后端用一次 | 后端**根本收不到 code** |
| access_token 有效期 | **60 天（5184000 秒）** | **90 天（7776000 秒）** |
| refresh_token | 有（一次有效，续票链最长 3 个月） | **没有** |
| token 过期后 | 用 refresh_token 续票 | **只能让用户重新登录**（官方：用户再次登录时自动刷新） |
| 后端需要做什么 | 换 token → 拉 openid → 拉 userinfo | **校验 token → 拉 userinfo** |
| appid | 网站应用 appid/appkey | **移动应用 appid**（独立一套） |

#### 8.2.2 移动应用（App）登录

**关键确认（逐条对照用户提问）**

| 提问 | 确认结果 | 官方依据 |
|---|---|---|
| SDK 直接返回 `access_token` + `openid` + `expires_in`？ | **✅ 准确** | Android SDK 环境搭建页「(3) 登录成功后获取的数据」给出的完整字段清单 |
| 后端不需要换 token？ | **✅ 正确** | 同上：code 不出现在返回里，SDK 内部已完成换取 |
| 返回字段全清单？ | 见下表（**7 个字段**） | 同上 |
| access_token 有效期也是 60 天？ | **❌ 不是。是 90 天（`expires_in: "7776000"`）** | 同上官方样例 |
| SDK 不返回 refresh_token？ | **✅ 正确** | 返回样例无该字段；Android SDK 功能列表也无"获取 refresh_token"能力 |
| 后端拿到后直接调 `user/get_user_info`？ | **✅ 是，且必须传 `openid`** | 该端点通用参数要求 `access_token` + `oauth_consumer_key` + `openid` |

**第一步：客户端登录（SDK 侧，后端不参与）**

Android 官方示例：

```java
public void login() {
    mTencent = Tencent.createInstance(AppId, this.getApplicationContext(), Authorities);
    if (!mTencent.isSessionValid()) {
        mTencent.login(this, Scope, listener);   // listener 是 IUiListener 实例
    }
}
```

官方特别注意：**SDK 内部用弱引用持有 listener**，`Tencent.login()` 传入的 `IUiListener` 必须是**当前类的成员变量**，否则用户在授权页停留过久时弱引用被回收 → 回调不执行。

**第二步：SDK 登录成功回调的完整字段（官方原文样例，`qq_login.txt:194-203`）**

Android `onComplete(JSONObject arg0)` 回传：

```json
{
  "ret":0,
  "pay_token":"xxxxxxxxxxxxxxxx",
  "pf":"openmobile_android",
  "expires_in":"7776000",
  "openid":"xxxxxxxxxxxxxxxxxxx",
  "pfkey":"xxxxxxxxxxxxxxxxxxx",
  "msg":"sucess",
  "access_token":"xxxxxxxxxxxxxxxxxxxxx"
}
```

| 字段 | 类型（实测标注） | 说明 |
|---|---|---|
| `ret` | int | **0 = 成功**；非 0 失败 |
| `msg` | string | 结果信息。**官方样例是 `"sucess"`（漏了一个 c）** → 解析时不要对 msg 做任何字符串断言 |
| `access_token` | string | 用户 access_token |
| `expires_in` | **string**（注意：官方样例是带引号的字符串 `"7776000"`，不是数字） | 有效期**秒**，**7776000 = 90 天** |
| `openid` | string | 用户在本移动应用内的唯一标识 |
| `pay_token` | string | 支付相关 token（登录场景不用，但**必须容忍它存在**） |
| `pf` | string | 平台标识，官方样例 `"openmobile_android"`（iOS 端会是别的值） |
| `pfkey` | string | 支付相关 key（同上，不用但不报错） |
| `refresh_token` | — | **不存在** |

**→ 三个实现要点**：

1. **`expires_in` 是字符串**，解析成 `int64` 前要兼容 `"7776000"` 与 `7776000` 两种形态（用 `json.Number` 或先按 string 解再 `strconv.ParseInt`）。
2. **字段多于所需**（`pay_token`/`pf`/`pfkey`），解析结构体不要用 `DisallowUnknownFields`。
3. **`ret` 必须判**，非 0 直接失败。

**第三步：后端校验 token（必做，不能省）**

**这是移动端与网页端最本质的安全差异**：

- 网页端：`access_token` 是**后端用自己的 secret 换来的** → 天然可信；
- 移动端：`access_token` 是**客户端上报的** → **完全不可信**。客户端可以伪造/篡改/重放任意 openid 与 token 的组合。

**校验方式**：`GET https://graph.qq.com/oauth2.0/me?access_token=YOUR_ACCESS_TOKEN`

- 该端点同时完成两件事：**① 校验 access_token 有效性；② 返回该 token 真正对应的 openid**。
- 响应格式与 §2.2.4 完全相同（JSONP `callback( {...} );`）。
- **必须比对**：`me` 返回的 `openid` 与客户端上报的 `openid` **一致**，否则拒绝登录（防止"用 A 的 token 配 B 的 openid 拿 B 的资料"）。

```text
callback( {"client_id":"YOUR_APPID","openid":"YOUR_OPENID"} );
```

**校验失败样例（官方原文，JSONP 内嵌 error）**

```text
callback(
{
"error":100016,
"error_description":"access token check failed",
}
);
```

> 100016 = access token 验证失败（可能过期或不正确）。另：官方 Android SDK 功能列表里也有「校验 token」「校验 token 并统计 DAU」两项能力，但那是**客户端侧**校验；**后端必须独立校验一次**，不能信任客户端自检结果。

**第四步：拉取用户信息（同一个端点）**

- **URL**：`https://graph.qq.com/user/get_user_info`
- **Method**：`GET`
- **通用参数（必须三个都传）**

| 参数 | 必填 | 说明 |
|---|---|---|
| `access_token` | **必须** | SDK 返回的 access_token |
| `oauth_consumer_key` | **必须** | **移动应用的 appid**（不是网站应用的 appid） |
| `openid` | **必须** | SDK 返回的 openid（**该端点参数里明确要求传 openid**） |

完整 URL：

```text
https://graph.qq.com/user/get_user_info?access_token=YOUR_ACCESS_TOKEN&oauth_consumer_key=YOUR_APP_ID&openid=YOUR_OPENID
```

**→ 回答用户提问**：**是，直接调 `user/get_user_info` 即可，且必须传 `openid`**（三个通用参数一个都不能少）。这与网页端完全同一个端点、同一套参数。

**移动端 userinfo 返回字段（官方原文样例，`qq_login.txt:232-247`）**

```json
{
  "is_yellow_year_vip": "0",
  "ret": 0,
  "figureurl_qq_1": "http://q.qlogo.cn/qqapp/222222/8C75BBE3DC6B0E9A64BD31449A3C8CB0/40",
  "figureurl_qq_2": "http://q.qlogo.cn/qqapp/222222/8C75BBE3DC6B0E9A64BD31449A3C8CB0/100",
  "nickname": "小罗",
  "yellow_vip_level": "0",
  "msg": "",
  "figureurl_1": "http://qzapp.qlogo.cn/qzapp/222222/8C75BBE3DC6B0E9A64BD31449A3C8CB0/50",
  "vip": "0",
  "level": "0",
  "figureurl_2": "http://qzapp.qlogo.cn/qzapp/222222/8C75BBE3DC6B0E9A64BD31449A3C8CB0/100",

  "figureurl": "http://qzapp.qlogo.cn/qqapp/222222/8C75BBE3DC6B0E9A64BD31449A3C8CB0/30"

```

> **重要差异**：这份官方样例里 **没有 `province` / `city` / `year` / `constellation`**（网页端 `get_user_info` 的社区观测字段表里有）。原因是 SDK 内部调的是 `GRAPH_SIMPLE_USER_INFO`（简化版用户信息）。→ **§2.2.5 的字段表要按"可能缺失"处理**，SDK 只取 `nickname` + `figureurl_qq_2` + `gender`，其余不落库（这与 §2.2.5 的落库建议一致，此处得到官方样例佐证）。

**移动端特有错误码（单独列）**

**A. SDK 层（`ret` / `UiError`，不走微信式 errcode）**

| 来源 | 码 | 含义 | 处置 |
|---|---|---|---|
| `onComplete` 的 `ret` | `0` | 成功 | 继续 |
| `onComplete` 的 `ret` | 非 `0` | 失败（含用户拒绝、无权限等） | 转成 `ErrCodeInvalid`，需要看 `msg` 定位 |
| `IUiListener.onCancel()` | — | **用户取消授权** | 前端提示"已取消"，不上报后端 |
| `IUiListener.onError(UiError)` | `errorCode` / `errorMessage` / `errorDetail` | SDK/网络/SDK 未初始化等错误 | 记录三个字段，**不要丢 errorDetail** |

**B. 服务端（与网页端共用，但移动端最常见的三类）**

| 错误码 | 含义 | 移动端场景与处置 |
|---|---|---|
| `100016` | access token 验证失败 | **最常遇到**：客户端上报的 token 已过期/伪造 → 返回"请重新登录"，**不要提示"系统错误"** |
| `100013` | access token 失效（用户取消授权或过期被回收） | 同上，重新登录 |
| `100014` | access token 过期（**token 过期时间为 60 天**） | 注意：此码注释写 60 天，但**移动端 token 实为 90 天**（见下方矛盾 #9）→ 以 `me` 的实际返回为准，不做天数硬编码 |
| `100030` | 用户没有对该 api 授权，或用户在腾讯侧删除了该 api 权限 | 重新走授权流程 |
| `100031` | 第三方应用没有对该 api 操作的权限 | 需邮件申请 OpenAPI 权限 |
| `100048` | 没有设置 companyID（未申请 unionid 权限） | 移动端若请求 unionid 会撞到（见下） |

**移动端 unionid**

- QQ 移动端 **SDK 登录返回里没有 unionid**（只有 openid，见字段清单）。
- 要拿 unionid：**后端调 `oauth2.0/me?access_token=...&unionid=1`**（需先在 connect.qq.com 申请 UnionID 权限，否则 `100048`）。
- 官方原文（UnionID 介绍页）：「同一 QQ 互联平台下的不同应用，unionID 是相同的」——注意范围是**同一 QQ 互联平台**，跨开发者账号是否一致官方未明说。

**第五步：token 过期后怎么办（官方答复）**

- **没有 refresh_token**，所以**不能后端续期**。
- 官方 Client-side 文档的说法：「获取到的 access token 具有 60 天有效期，**用户再次登录时自动刷新**」。
- 实际做法：**token 过期 → 让用户重新点"QQ 登录"** → SDK 走 SSO（手机 QQ 已登录时**无需输入密码**，用户几乎无感）→ 拿到新 access_token。
- → **工程结论**：移动端**不需要**存储/管理 refresh_token；后端只需存 `openid` 做账号绑定，access_token **仅用于当次登录换取用户信息，用完即弃**（或短期缓存 `ExpiresAt`，但**不要**依赖它做长期会话）。

#### 8.2.3 网页登录（已调研，补充 Client-side 模式）

**补充一种此前未覆盖的模式：Client-side / Implicit Grant（浏览器 JS）**

- **URL**：`https://graph.qq.com/connect/?appid=[YOUR_APPID]&redirect_uri=[YOUR_REDIRECT_URI]&response_type=token&lang=zh_CN&color_theme=auto&scope=[THE_SCOPE]`
- **返回值在 URL fragment（`#` 之后）**，官方原文例子：

```text
http://www.qq.com/?#access_token=YOUR_ACCESS_TOKEN&expires_in=3600
```

- 官方原文：「可通过 js 方法 `window.location.hash` 来获取 URL 中 `#` 后的参数值」
- 官方原文：「获取到的 access token 具有 **60 天有效期，用户再次登录时自动刷新**」
- **`expires_in=3600` 与"60 天"自相矛盾**（见矛盾 #10）

**是否纳入 SDK？结论：不纳入。** 理由：
- fragment 里的 token **永远不会到后端**（`#` 后内容不发服务器），后端无从校验；
- 前端拿到 token 后再上报后端 = 与 QQ 移动端同构（都需要后端二次校验），但移动端有官方 SDK 契约、Client-side 没有；
- 我们的场景（服务端签发自家双 token）不需要它。
- **但它的存在解释了移动端 token 的校验需求**：QQ 生态里"客户端拿 token 交后端"是常态，所以 `ValidateToken` 是 QQ 分支的**必备能力**，不是可选项。

#### 8.2.4 QQ 端点复用矩阵

| 端点 | 网页登录 | 移动端 | Client-side（不纳入） | SDK 复用 |
|---|---|---|---|---|
| `graph.qq.com/oauth2.0/authorize` | ✅ | — | — | 否（后端只拼 URL） |
| 客户端 SDK `Tencent.login` | — | ✅ | — | 否（客户端职责） |
| `graph.qq.com/oauth2.0/token` | ✅ | — | — | 网页专用 |
| `graph.qq.com/connect/?response_type=token` | — | — | ✅ | 不实现 |
| `graph.qq.com/oauth2.0/me` | ✅ 取 openid | **✅ 校验 token + 取 openid** | 同左 | **✅ 复用（用途不同）** |
| `graph.qq.com/user/get_user_info` | ✅ | ✅ | ✅ | **✅ 完全复用** |

→ **QQ 两形态的差异只有一个**：**谁去拿 access_token**。网页端后端换，移动端客户端给。拿到 token 之后**全部复用**。

### 8.3 GitHub

**结论 1：GitHub 没有"移动端 SDK 授权"模式。**

证据：GitHub 官方提供的两条授权路径只有 ——
1. **Web application flow**（浏览器跳转，即第一轮调研的 4 个端点，也是**移动 App 里嵌 WebView 时唯一可行的方式**）；
2. **Device flow**（无浏览器/受限输入设备场景）。

GitHub **不提供** iOS/Android 原生 SDK。移动 App 接 GitHub 登录只能：
- **方案 A（推荐）**：App 内嵌 WebView 打开 `github.com/login/oauth/authorize`，回调到 App 的 deep link，拿到 code 后**交给后端换 token**（后端换 token 才安全，理由同微信 §8.1.2 第四点）；
- 方案 B：Device Flow（体验差，要用户手输 8 位码，不适合普通 App 登录）。

→ **不需要为 GitHub 新增任何渠道**。现有 Web 流程 + 一个 App 端 deep link 回调即可。

**结论 2：Device Flow 不值得本轮支持。**

| 项 | 值 |
|---|---|
| 端点 1 | `POST https://github.com/login/device/code`（参数 `client_id`、`scope`） |
| 端点 2 | `POST https://github.com/login/oauth/access_token`（参数 `client_id`、`device_code`、`grant_type=urn:ietf:params:oauth:grant-type:device_code`，**不需要 `client_secret`**） |
| 用户侧 | 到 `https://github.com/login/device` 手输 8 位 `user_code`（格式 `WDJB-MJHT`） |
| 返回 | `device_code`、`user_code`、`verification_uri`、`expires_in: 900`、`interval: 5` |
| 轮询错误码 | `authorization_pending` / `slow_down`（每次 +5s）/ `expired_token` / `unsupported_grant_type` / `incorrect_client_credentials` / `incorrect_device_code` / `access_denied` / `device_flow_disabled` |
| 限速 | 提交验证码 **50 次/小时/应用**；轮询快于 `interval` 会 `slow_down` |

**不支持的理由（三条）**：
1. **场景不匹配**：本项目的 GitHub 登录是 Web/App 普通用户登录，用户在手机上点一下浏览器就完事；Device Flow 是为 **CLI / 无浏览器设备**设计的（官方原文："a headless application, such as a CLI tool or the Git Credential Manager"）；
2. **体验倒退**：用户要记住并手输 8 位码，登录转化率必然低于一键授权；
3. **要额外开关**：必须在 OAuth App 设置里**显式启用** device flow，否则报 `device_flow_disabled`。

→ **本轮不实现，但记入 SDK 的 `ChannelCLI` 预留位**（将来做 `fantwo` CLI 工具时直接接）。若真要做，`oauthkit` 只需多一个 `DeviceLogin(ctx) (*DeviceCode, error)` + `PollDeviceToken(ctx, deviceCode) (*Token, error)`，不污染现有接口。

### 8.5 三个设计问题的结论

#### 问题 1：同一平台多套配置怎么组织

**结论：配置键统一为 `<provider>_<channel>_<field>`，Provider 实例按 `(provider, channel)` 构造，不是一个 provider 一个实例。**

命名方案（对齐本仓库现有 snake_case 配置键风格）：

| 配置 key | 类型 | 敏感 | 默认值 | 说明 |
|---|---|---|---|---|
| `wechat_web_appid` | string | 否 | `""` | 网站应用 AppID |
| `wechat_web_secret` | string | **是** | `""` | 网站应用 AppSecret |
| `wechat_web_redirect_uri` | string | 否 | `""` | 扫码回调（域名须与开放平台授权域名一致） |
| `wechat_app_appid` | string | 否 | `""` | **移动应用 AppID（与 web 不同）** |
| `wechat_app_secret` | string | **是** | `""` | 移动应用 AppSecret（**只在云端使用**） |
| `qq_web_appid` | string | 否 | `""` | 网站应用 appid |
| `qq_web_appkey` | string | **是** | `""` | 网站应用 appkey |
| `qq_web_redirect_uri` | string | 否 | `""` | 网页回调 |
| `qq_app_appid` | string | 否 | `""` | **移动应用 appid（与 web 不同）** |
| `github_client_id` | string | 否 | `""` | 保持现有 key，不改名（只有一套） |
| `github_client_secret` | string | **是** | `""` | 同上 |
| `github_redirect_uri` | string | 否 | `""` | 同上 |
| `github_success_redirect_url` | string | 否 | `/` | 同上 |
| `github_scope` | string | 否 | `read:user user:email` | 同上 |
| `wechat_web_success_redirect_url` | string | 否 | `/` | 前端成功跳转（web 渠道） |
| `wechat_app_success_redirect_url` | string | 否 | `/` | 前端成功跳转（app 渠道，实际由 App 处理） |
| `qq_web_success_redirect_url` | string | 否 | `/` | 同上 |
| `wechat_web_scope` | string | 否 | `snsapi_login` | 网站应用固定值 |
| `wechat_app_scope` | string | 否 | `snsapi_userinfo` | 移动应用固定值 |
| `qq_web_scope` | string | 否 | `get_user_info` | 逗号分隔 |
| `qq_use_unionid` | bool | 否 | `false` | 是否请求 unionid（需先申请权限） |

**为什么不沿用 `wechat_app_id` / `qq_app_id` 这种裸命名**：

1. **两套 appid 必须能区分**。§8.1.2 已确认微信移动应用与网站应用是独立 appid；QQ 同理（创建应用时先选类型）。裸命名会导致"配了网站应用的 appid 却拿去换 App 的 code"→ 微信报 `40013 invalid appid` / QQ 报 `100008 该appid不存在`，而且**错误信息看不出来是配错了**。
2. **`<provider>_<channel>_<field>` 可以机器生成 `ConfigKey(provider, channel, field)`**，SDK 里按 `(provider, channel)` 自动拼 key，不用维护 20 个常量字符串。
3. **向后兼容**：`github_*` 只有一套渠道，保持原名不改（现有 5 个 key 已在 `github_oauth.go:27-31` 定义，改名等于制造迁移成本且无收益）。

**Provider 构造方式**：

```go
// 每个 (provider, channel) 组合一个实例。
// 微信：wechat/web、wechat/app（+ 预留 wechat/mp）
// QQ：  qq/web、qq/app
// GitHub：github/web（+ 预留 github/device）
p, err := oauthkit.New("wechat", "app", oauthkit.Config{...})
```

**`Name()` 返回值**：`"wechat"` / `"qq"` / `"github"`（**不带渠道**，因为 DB 唯一键按平台算：`provider + openid`，同一用户从 web 还是 app 登录都应命中同一条绑定记录——微信两套 appid 下同一用户的 openid **不同**，所以要靠 `unionid` 打通，这正是 unionid 存在的意义）。
**新增 `Channel()` 方法**返回 `"web"` / `"app"` / `"mp"` / `"device"`，用于配置读取、日志、路由。

> **⚠ 这里有个必须写进文档的关键结论**：微信 web 与 app 是**两个 appid**，同一用户的 `openid` 在两者下**不同**，但 `unionid` **相同**（同一开放平台账号下）。所以**微信多端打通必须靠 unionid，不能靠 openid**。QQ 同理（移动应用与网站应用的 openid 是否相同，官方未明确 → 见矛盾 #11，必须按"可能不同"设计）。→ **绑定表的唯一键若只用 `provider + openid`，微信 web/app 会绑定成两个账号**。这是 §7.3 数据模型建议（方案 B）的**重要修正**：唯一键应为 `provider + openid`，**但登录查找逻辑必须先按 `provider + unionid` 找**，找不到再按 `openid`。

#### 问题 2：接口要不要加"直接注入 token"的方法

**结论：不新增 `UserInfoByToken(ctx, accessToken, openID)`；改为「`Token` 结构允许手工构造后直接调 `UserInfo`」+ **新增一个 `ValidateToken` 方法**。**

**理由（为什么不需要 `UserInfoByToken`）**：

1. `UserInfo(ctx, tok *Token)` 本来就接受外部 `Token` 对象。手动构造 `Token{AccessToken: x, OpenID: y}` 后调它，语义与"从 Exchange 拿到的 token"完全一致——**多加一个方法等于同一个能力两条路径**，测试与实现都要写两遍。
2. QQ 移动端登录的真正差异**不是"token 从哪来"，而是"token 可不可信"**。这一点靠加一个 `UserInfoByToken` 解决不了——它仍然会拿着未校验的 token 去拉数据。
3. 因此**缺的不是"注入 token 的入口"，而是"校验 token 的能力"**。

**必须新增的方法**：

```go
// ValidateToken 校验一个外部传入的 token 是否有效，并补全/校正其中的标识字段。
//
// 用途：移动端 SDK 登录场景 —— access_token 由客户端上报，不可信，必须校验。
//   - QQ：调 oauth2.0/me?access_token=X，比对返回的 openid 与 tok.OpenID 是否一致；
//         不一致返回 ErrTokenMismatch（防"用 A 的 token 配 B 的 openid"）。
//   - 微信：调 sns/auth?access_token=X&openid=Y；errcode=0 为有效。
//   - GitHub：调 GET /user 探活（顺带校验 token 未撤销）。
//
// 对"后端自己换来的 token"（网页流程），调用方可跳过本方法。
ValidateToken(ctx context.Context, tok *Token) (*Token, error)
```

**为什么 `ValidateToken` 返回 `*Token` 而不是 `error`**：QQ 的 `me` 端点**同时返回 openid**，所以校验即补全——返回的 token 带上了可信的 openid（若调用方只传了 access_token 没传 openid，也能补齐）。这一步让"客户端只交 access_token、openid 由后端自己算"成为可能，**比要求客户端同时上报 openid 更安全**。

**`Token` 结构需补两个字段**：

```go
type Token struct {
    // ... 原有字段
    Channel   string // "web" / "app" / "mp" / "device"：token 来源渠道，影响有效期语义与错误提示
    Verified  bool   // 是否已经过 ValidateToken 校验（true 才允许 UserInfo）
}
```

**`UserInfo` 的前置校验**：`UserInfo` 内部对 `tok.Channel == "app" && !tok.Verified` 直接返回 `ErrTokenNotVerified`，**强制调用方先 `ValidateToken`**。这是把"安全要求"做成"类型系统挡不住但运行时会拦"的硬约束——比写在注释里靠人记更可靠。

**新增哨兵错误**：

```go
ErrTokenNotVerified = errors.New("oauthkit: token from client must be validated before use")
ErrTokenMismatch    = errors.New("oauthkit: token does not belong to the claimed openid")
```

**综合后的调用姿势（两个渠道对比）**：

```go
// 网页渠道：token 由后端换来，天然可信
tok, _ := p.Exchange(ctx, code)          // 微信/QQ/GitHub 都走这条
u, _ := p.UserInfo(ctx, tok)             // 直接可用

// 移动端 QQ：token 由客户端上报，必须先校验
tok := &oauthkit.Token{AccessToken: req.AccessToken, OpenID: req.OpenID, Channel: "app"}
tok, err := p.ValidateToken(ctx, tok)     // 校验 + 补全可信 openid
if err != nil { /* 100016 → "请重新登录" */ }
u, _ := p.UserInfo(ctx, tok)              // Verified=true 才放行

// 移动端微信：code 仍是后端换的，不需要 ValidateToken
tok, _ := p.Exchange(ctx, code)           // app 渠道同样走 Exchange（官方同端点）
u, _ := p.UserInfo(ctx, tok)
```

> **注意微信 App 与 QQ App 的不对称性**：微信 App **仍然交 code**（后端换 token，可信），QQ App **直接交 access_token**（不可信）。这个差异是官方协议决定的，**SDK 必须如实反映，不能抹平**——抹平的结果就是把 QQ 的安全检查也套到微信上（多一次无意义的 `sns/auth` 调用），或者把微信的安全模型套到 QQ 上（直接信任客户端 token，严重漏洞）。

#### 问题 3：登录入口矩阵（最终暴露的后端端点）

**核心原则**：`(provider, channel)` → 一组端点；**是否需要后端换 token** 决定端点数（网页/微信 App：2 个端点"取 URL + 回调"；QQ App：1 个端点"POST 登录"）。

| # | 渠道 | 后端端点 | 方法 | 入参 | 出参 | 后端换 token |
|---|---|---|---|---|---|---|
| 1 | 微信-网页扫码 | `GET /api/v1/auth/wechat/web/url` | GET | —（state 由后端生成存 Redis） | `{ url, state }` | — |
| 2 | 微信-网页扫码 | `GET /api/v1/auth/wechat/web/callback` | GET | `code`、`state` | 302 到前端 + 双 token（或 JSON） | **是** |
| 3 | 微信-App | `POST /api/v1/auth/wechat/app/login` | POST | `{ code, state?, deviceId? }` | 双 token + user | **是**（同端点同参数，只是 appid 换了） |
| 4 | QQ-网页 | `GET /api/v1/auth/qq/web/url` | GET | — | `{ url, state }` | — |
| 5 | QQ-网页 | `GET /api/v1/auth/qq/web/callback` | GET | `code`、`state` | 302 / JSON | **是** |
| 6 | QQ-App | `POST /api/v1/auth/qq/app/login` | POST | `{ accessToken, openid?, expiresIn?, deviceId? }` | 双 token + user | **否**（`ValidateToken` → `UserInfo`） |
| 7 | GitHub-Web | `GET /api/v1/auth/github/url` | GET | — | `{ url, state }` | — |
| 8 | GitHub-Web | `GET /api/v1/auth/github/callback` | GET | `code`、`state` | 302 / JSON | **是** |
| 9 | 账号绑定（跨渠道） | `POST /api/v1/auth/oauth/bind` | POST | `{ provider, channel, code 或 accessToken }` | 绑定结果 | 视渠道 |
| 10 | 解绑 | `DELETE /api/v1/auth/oauth/bind/:provider` | DELETE | — | — | — |
| 11 | 已绑定列表 | `GET /api/v1/auth/oauth/bindings` | GET | — | `[{ provider, channel, nickname, boundAt }]` | — |

**本轮要实现的核心 8 个**（#1-#8，即 3 组渠道 × (取URL + 回调) + 微信 App + QQ App）：

```
微信：wechat/web/url  wechat/web/callback  wechat/app/login
QQ：  qq/web/url      qq/web/callback      qq/app/login
GitHub：github/url     github/callback
```

**可选扩展（本轮不做，预留）**：

| 渠道 | 端点 | 不做的理由 |
|---|---|---|
| 微信-公众号 H5 | `/auth/wechat/mp/url` + `/auth/wechat/mp/callback` | 只微信内可用、需第四套凭据、`snsapi_base` 无 unionid（§8.1.4 结论） |
| GitHub-Device | `/auth/github/device/code` + `/auth/github/device/poll` | 场景是 CLI 不是 App（§8.3 结论） |
| 微信-App扫码 | 无 | 客户端拿 code 后复用 `/auth/wechat/app/login`，后端零新增（§8.1.5 结论） |

**与现有端点的关系**：现仓库已有 GitHub 的 3 个端点（`GithubAuthURL` / `GithubCallback` / `GithubRedirectURL`，见 `auth_service.go:528-596`）。上表 #7/#8 应**复用现有路由路径**（保持前端零改动），只把内部实现换成走 SDK。**路由命名要兼容现状**——如果现有路径是 `/auth/github` 而非 `/auth/github/url`，就保留现有路径，新增渠道再加 `_routes.go` 里的新路径。

### 8.6 §7.1 接口修订说明

**结论：§7.1 的接口需要改，共 3 处（1 改 2 增）。**

| # | 改动 | 原因（来自 §8 的哪条结论） |
|---|---|---|
| 1 | `Name()` 语义收窄为**平台**（`"wechat"`），**新增 `Channel()`** 返回渠道（`"web"`/`"app"`/`"mp"`/`"device"`） | §8.5 问题 1：一个平台多套 appid，Provider 实例必须按 `(provider, channel)` 构造；但账号唯一键仍按平台算，两者不能混 |
| 2 | **新增** `ValidateToken(ctx, tok) (*Token, error)` | §8.2.2 第三步：QQ 移动端 token 由客户端上报，**不可信**，必须调 `oauth2.0/me` 校验并比对 openid；§8.2.3 结论"`ValidateToken` 是 QQ 分支必备能力，不是可选项" |
| 3 | `Token` **新增** `Channel` 与 `Verified` 两个字段；`UserInfo` 对 `Channel=="app" && !Verified` 硬拒绝（`ErrTokenNotVerified`） | §8.5 问题 2：安全要求做成运行时硬约束，而不是写在注释里 |

**不改的部分（以及为什么）**：

- `AuthURL` / `Exchange` / `UserInfo` / `Refresh` 四方法**签名不变**。微信 App 仍然走 `Exchange`（官方同端点），QQ App 不走 `Exchange`（没有 code）——但这个差异由**调用方选择调哪个方法**表达（网页/微信App 调 `Exchange`，QQ App 用 `ValidateToken`），**不需要**给 `Provider` 加一个"我没有 Exchange"的语义。三家的 `Provider` 接口实现里，QQ 的 `Exchange` 只服务 `qq/web` 实例；`qq/app` 实例的 `Exchange` 返回 `ErrExchangeUnsupported`（新哨兵），语义清晰。
- 不加 `UserInfoByToken`：见 §8.5 问题 2 理由 1-3。
- 不加 `DeviceLogin`：见 §8.3 结论 2（CLI 场景，本轮不做）。

## 9. SDK 独立化与分发（T-37f）

把 `oauthkit` 从 `internal/` 移到 `pkg/`，使其成为**可被外部模块 import** 的独立 SDK。

### 9.1 为什么要搬

Go 的 `internal/` 语义是**编译器强制**的：任何位于 `internal/` 下的包，只能被
其父目录树内的代码 import。外部模块（哪怕是同一 git 仓库的其它 module）写

```go
import "github.com/SugarLess-CN/fantwo-core/internal/pkg/oauthkit"
```

会直接编译失败：`use of internal package ... not allowed`。

所以「可独立分发」= 必须去掉 `internal/` 前缀，没有第二条路。

### 9.2 搬包方案：直接改 import，不保留别名包

| 方案 | 做法 | 取舍 |
|---|---|---|
| A（未采纳） | `pkg/oauthkit` 放真实现，`internal/pkg/oauthkit` 保留为 `type X = pkg.X` 的转发包 | 调用方零改动，但**永久留两套同名包**：读者要判断「该用哪个」、`go doc` 会重复出现、类型别名层还会吞掉编译期错误（改了字段名不报错） |
| **B（采纳）** | 一次性把 5 个引用文件的 import 全改到 `pkg/oauthkit`，删除 `internal/pkg/oauthkit` | 改 5 处 import + 3 处注释里的路径；**收敛成一套**，无历史包袱 |

**选 B 的理由**：引用方只有 5 个文件（`internal/model/config.go`、`internal/service/`
下 4 个），一次 sed 改完，成本远低于永久维护一套别名层。项目已有「不留两套并存、
旧的收敛掉」的纪律，此处照做。

搬包用 `git mv`，git 全部识别为 `R`（rename），**文件历史不丢**。

| 未实现的键 | 为什么不要 |

### 9.7 QQ 上游限制：是频率限制，不是 WAF 封锁

**此前记录「QQ `/authorize` 与 `/token` 被腾讯 WAF 拦（HTTP 501）」是误判。** 实测澄清：

| 端点 | 实测结果 |
|---|---|
| `graph.qq.com/oauth2.0/authorize` | **HTTP 302**（正常，145ms） |
| `graph.qq.com/oauth2.0/token` | `callback({"error":100005,...})` ← 正常业务错误 |
| `graph.qq.com/oauth2.0/me` | `callback({"error":100013,...})` ← 正常 |
| `graph.qq.com/user/get_user_info` | `{"ret":-22,"msg":"openid is invalid"}` ← 正常 |

真实原因：**短时间连续请求触发限流**，间隔 ≥ 3 秒即恢复；真实浏览器跳转不受影响。
自动化测试必须节流（README §6 给 `qqThrottle()` 参考实现）。
