### 关于 §二.8：已完成的细节 + 一处交接单笔误

**① 交接单有个笔误：`read-all` 是 `POST` 不是 `PUT`。**

```
internal/router/message_routes.go:57   msg.POST("/read-all", h.MarkAllRead)
curl -X PUT  .../read-all  → 404
curl -X POST .../read-all  → 200
```
我们的 spec 与实现一致（都是 `POST`）。**请前端改成 POST**（一行）。
我们**不加 PUT 别名** —— 现在正在清理重复 operationId，再加一个语义相同的方法会雪上加霜。

**② 只补参数是不够的，顺带修了一个真 bug。**

站内消息有**两套已读载体**：
- 广播（`is_broadcast=true`）→ 已读在 `message_read` 回执表，行内 `is_read` 不参与
- 个人（`is_broadcast=false`）→ 已读是行内 `is_read` 列

原实现 `if is_broadcast { 标广播 } else { 标个人 }` 是**二选一**。
前端只传 `?type=system`（不带 `is_broadcast`）→ 走 else 分支 → **广播型通知永远标不掉**，
表现就是你说的「点了没反应」。

真机对比：
```
只补注解、不改这处：?type=system 之后 → system 仍是未读   ← 点了没反应
两种载体一起标：    ?type=system 之后 → system=0，另两条未读 ✅
```

**新行为**：`type` 现在是 query 参数，取值 `private` / `system` / `notification`；
不传 = 全部（向后兼容）；非法值 → `10001` + HTTP 400（不是 500）。

## 三、§三.2「列表包装字段名不统一」—— 属实，但需要双方同时改

确认现状：

| DTO | 字段 | 用在哪 |
|---|---|---|
| `dto.PageBody` | **`list`** + `meta` | 大多数分页接口 |
| `dto.ConversationListDto` | **`data`** + `meta` | `GET /message/private/conversations` |
| `dto.PrivateHistoryDto` | **`data`** + `meta` | `GET /message/private/conversations/{id}/messages` |

**这是 breaking change**：我们把 `data` 改成 `list`，前端必须**同一时间**改解析。
所以我**不在字段补齐这轮动它** —— 混在一起做会导致「前端不知道哪个版本对应哪个行为」。

**建议**：字段补齐全部落地后，单独发一版。届时：
- 后端：两个 DTO 的 `data` → `list`，同步 service 组装点
- 前端：两处 `res.data.data` → `res.data.list`
- 两边同一次发版

需要时告诉我，我可以先出一个「两个字段都返回」的过渡版
（`{data, list, meta}` 同时给，前端灰度切换后再收掉 `data`）。

## 六之二、本轮三个决策（含依据）

### 决策 1｜`equipped_decorations` 的 map key 用**大写**

`{"AVATAR_FRAME": {...}, "COMMENT_BUBBLE": {...}}` —— 不是 snake_case。

**依据**（原 NestJS 源码）：
```typescript
// common/utils/user-decorator.util.ts:114
equippedDecorations[decoration.type] = transformDecorationToFrontend(decoration)
// 而 decoration.type 的取值见 achievement/USER-DECORATIONS-INTEGRATION.md:47
AVATAR_FRAME: { id, name, type, imageUrl, rarity },
```
key 直接取枚举原值（大写），且我们 DB 里存的也是 `AVATAR_FRAME`。

> 这不违反「全站 snake_case」：那条规则管**字段名**，这里是 map 的**动态 key**
> （key 本身是另一个枚举的取值），属 docs/21 §四 认可的例外形态。

### 决策 2｜`GET /user/{id}` 恢复**公开**（OptionalAuth）

**依据**（原 NestJS 源码）：
```typescript
// user.controller.ts:342
@Get(":id")
@UseGuards(JwtAuthGuard)
@NoAuth()                                    // ← 可选鉴权
findOne(@Param("id") id, @Req() req: Request & { user?: User })
```
`@NoAuth()` + `req.user?` 表明：**游客能看，登录后额外拿到登录态**。
我们 2026-11-25 收紧成 `user:read` 是偏离契约，已恢复。

**同时收紧敏感字段**（公开的前提）：`FindUser` 里只有「自己看自己」才返回
`config`（佣金/隐私/通知偏好）与 `wallet`（真实余额）；他人/匿名一律 `config` 不传、`wallet=0`。

### 决策 3｜浏览历史**保持唯一索引**，不改 append-only

交接单说「同一文章同一天看两次会被合并成一条」，但：

**原 NestJS 就是这么设计的**：
```typescript
// article/entities/browse-history.entity.ts:15
@Index(["userId", "articleId"], { unique: true })
@Column({ type: "int", default: 1, comment: "浏览次数" })
viewCount: number;
```

即「同一用户 + 同一文章 = 一行，重复浏览是 `viewCount++` 并刷新 `updated_at`」。
这是**有意的产品语义**（历史列表里同一篇文章出现多次是噪音），不是缺陷。

**所以：`id` 已给出**（解决你说的 `keyExtractor` 去重键问题），
但「两次两条」不做 —— 那需要去掉唯一索引改成 append-only 流水，
会连带改变「最近浏览」去重与 `view_count` 语义。

如果产品确实要「浏览流水」，那是新需求（另建 `browse_events` 表存流水，
`browse_history` 保持聚合），可以单独立项。
