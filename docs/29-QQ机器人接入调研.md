# 29 — QQ 官方机器人（BOT API v2）接入调研

> 用途：为「QQ 机器人发放邀请码 + 后台与用户对话」提供技术依据。
> 来源：QQ 机器人官方文档（bot.q.qq.com / bot.qq.com wiki）。
> 日期：2026-11-27

---

## 一、结论速览（决定架构的 5 条事实）

| # | 事实 | 对设计的影响 |
|---|---|---|
| 1 | 单聊被动回复窗口 **60 分钟**，每条消息可回复 **4 次** | 窗口比预想宽（不是 5 分钟）；`msg_seq` 1→4 可发 4 条 |
| 2 | **主动消息官方支持**，但用户可关「允许主动发送」开关 | 不必自己造轮子发消息，但仍需池子兜住「用户关闭了主动消息」 |
| 3 | 主动消息额度：单关系 **20/qpm**、每用户 **1000 条/天** | 池子重投必须限速，天然满足批量审批场景 |
| 4 | **互动召回消息** `is_wakeup=true`：用户对话后 30 天内，4 个周期各 1 条 | 窗口过期后的**首选**补救手段，比普通主动消息更容易送达 |
| 5 | 官方错误码**可区分**「窗口过期 / 频控 / 永久失败」 | 池子的状态机直接由错误码驱动，不靠猜 |

## 二、获取 access_token

```
POST https://api.bot.qq.com/app/getAppAccessToken
Content-Type: application/json
{ "appId": "...", "clientSecret": "..." }
```

**响应**：`{ "access_token": "...", "expires_in": "7200" }`

| 要点 | 说明 |
|---|---|
| 有效期 | 7200 秒（2 小时） |
| 刷新行为 | 有效期内重复获取返回**同一个值**；**临近过期 60 秒内**才返回新值（旧值这 60 秒仍有效） |
| 错误判定 | **业务错误走响应体 `code`，HTTP 仍是 200** —— 不能只看 HTTP 状态码 |
| 调用方式 | 请求头 `Authorization: QQBot {access_token}` |

**access_token 错误码**：`100001` Too many requests / `100007` appid invalid（含机器人被封禁或已删除）/ `100016` appid 或 secret 不正确 / `10004` 机器人不存在

> `expires_in` 在响应里是**字符串** `"7200"` 而不是数字 —— 反序列化必须兼容（用 `json.Number` 或自定义类型）。

## 三、发送单聊消息（核心接口）

```
POST /v2/users/{user_openid}/messages
Authorization: QQBot {access_token}
Content-Type: application/json
```

### 3.1 请求体关键字段

| 字段 | 类型 | 说明 |
|---|---|---|
| `msg_type` | int | 0=文本(content) / 2=Markdown / 6=输入中 / 7=富媒体 / 8=图文卡片 |
| `content` | string | msg_type=0 时的全文 |
| `markdown` | object | msg_type=2 时必填；**填了 markdown 则 content 必须为空** |
| `msg_id` | string | **被动回复用**。来自事件 `d.id`，60 分钟内有效 |
| `event_id` | string | 被动回复事件的 ID（与 msg_id 二选一） |
| `msg_seq` | int | 与 msg_id 联用。**相同 msg_id + msg_seq 重复发送必失败**；递增可多次回复，不填默认 1 |
| `is_wakeup` | bool | 互动召回消息，**与 msg_id / event_id 互斥** |

### 3.2 三种发送模式（互斥）

```
① 被动回复   { msg_id, msg_seq }        —— 60 分钟内，最多 4 次
② 互动召回   { is_wakeup: true }        —— 对话后 30 天内，4 个周期各 1 条
③ 普通主动   {}                          —— 20/qpm，1000 条/天，用户可关闭
```

### 3.3 响应

```json
{ "id": "ROBOT1.0_xxx", "timestamp": "2026-07-21T10:30:00+08:00",
  "ext_info": { "ref_idx": "REFIDX_xxx==" } }
```

## 四、时效窗口与池子设计（本项目的核心问题）

### 4.1 官方能力矩阵

| 模式 | 时效 | 次数/额度 | 用户可否阻断 |
|---|---|---|---|
| 被动回复 | 收到消息后 **60 分钟** | 每条 **4 次**（单聊） | 否（一定会尝试送达） |
| 互动召回 | 用户对话后 **30 天** | 4 周期 × 1 条 | 是（关闭主动消息） |
| 普通主动 | 随时 | 20/qpm、1000/天 | 是（关闭主动消息） |

**结论：官方「支持存量发送」**（主动消息 + 互动召回），所以不需要从零造一套传输通道；
但**用户可单方面关闭主动消息**，此时任何非被动消息都会永久失败 —— 这才是必须要池子的真实原因。

### 4.2 错误码分类（池子状态机直接由它驱动）

| 错误码 | 含义 | 归类 | 池子动作 |
|---|---|---|---|
| `40034005` | 回复消息 msg_id 已过期 | **窗口过期** | → `DEFERRED`，等用户下次发消息 |
| `304103` | 消息 ID 已过期，不能回复 | **窗口过期** | → `DEFERRED` |
| `40034128` | 被动回复时间或次数超限 | **窗口过期/次数用尽** | → `DEFERRED` |
| `40034100` | 主动消息超过频控限制 | 可重试 | → `PENDING`，退避重试 |
| `40054005` | 消息被去重（msg_seq 冲突） | 可重试 | msg_seq 递增后重试 |
| `50055002` | 消息发送异常，请稍后重试 | 可重试 | → 退避重试 |
| `40054013` | **用户拒收消息** | **永久失败** | → `FAILED`（用户关了主动消息） |
| `40054004` | 无好友关系 | **永久失败** | → `FAILED`（需引导加好友） |
| `40054007` / `40054018` | 消息长度超限 / 过长或异常 | **永久失败** | → `FAILED`（内容问题，需修内容） |
| `40034006` | 消息内容违规 | **永久失败** | → `FAILED`（审核拦截） |
| `40034105` | 主动消息无权限 | **永久失败** | → `FAILED`（机器人权限不足） |
| `40034122` | 召回消息已达区间上限 | **换模式** | → `KindWakeupExhausted`：去掉 `is_wakeup` 用普通主动重发一次（**不重试召回、不改变池子状态**） |

> 这张表是 SDK 最有价值的产出：**调用方不解析错误码**，只看 `ErrorKind` 三分类。

### 4.3 池子状态机

```
                 ┌──────────────── 用户发新消息（窗口激活） ────────────────┐
                 ↓                                                        │
[PENDING] ──发──→ 成功 ──→ [SENT]                                         │
    │                    ↑                                                │
    │  窗口过期错误        │                                                │
    ├──────────────→ [DEFERRED] ───────────────────────────────────────────┘
    │                    │
    │                    └─ 有互动召回额度 → 尝试 is_wakeup ──成功──→ [SENT]
    │                                                    └─失败──→ 留在 DEFERRED
    │  频控/去重 → 退避重试（留在 PENDING，attempts+1，next_retry_at 推后）
    │
    └─ 永久失败 → [FAILED]（出池，进死信列表供人工处理）
```

**关键规则（用户明确要求）**：「如果显示没有发送，消息就不从池子里面出去，而是一直在池子中，
直到对应用户再次发送消息激活窗口后再发送」——
即 **`DEFERRED` 不是终态，绝不删行**；只有 `SENT` / `FAILED` 才出池。

### 4.4 触发重投的三个入口

1. **webhook 收到该用户的 `C2C_MESSAGE_CREATE`** → 立刻投递该用户全部 `DEFERRED`
2. **定时扫描**（asynq 周期任务）→ 处理 `PENDING` 且 `next_retry_at <= now`
3. **人工「重试」按钮** → 强制把 `FAILED`/`DEFERRED` 拉回 `PENDING`

## 五、Webhook 事件接入

### 5.1 回调地址限制

- **必须是 HTTPS**，端口只允许：**80 / 443 / 8080 / 8443**
- 管理端配置：`https://q.qq.com/qqbot/#/developer/webhook-setting`

### 5.2 回调地址验证（op=13）

平台会先验证地址，请求体形如：

```json
{"d":{"plain_token":"Arq0D5A61EgUu4OxUvOp","event_ts":"1725442341"},"op":13}
```
请求头带 `User-Agent: QQBot-Callback`、`X-Bot-Appid: {appid}`。

**必须返回**：`{"plain_token":"...","signature":"..."}`

### 5.3 签名算法（ed25519，官方 Golang 示例逐字照搬）

```go
seed := botSecret
for len(seed) < ed25519.SeedSize {   // 32
    seed = strings.Repeat(seed, 2)
}
seed = seed[:ed25519.SeedSize]
reader := strings.NewReader(seed)
_, privateKey, err := ed25519.GenerateKey(reader)   // 只取私钥

var msg bytes.Buffer
msg.WriteString(validationPayload.EventTs)          // 先 event_ts
msg.WriteString(validationPayload.PlainToken)       // 后 plain_token
signature := hex.EncodeToString(ed25519.Sign(privateKey, msg.Bytes()))
```

> ⚠️ 顺序是 **event_ts 在前、plain_token 在后**，反了就验不过。
> ⚠️ `seed` 必须循环填充到 **32 字节**（`ed25519.SeedSize`），不是直接 hash。

### 5.4 事件类型

| 事件 | 用途 |
|---|---|
| `C2C_MESSAGE_CREATE` | 用户单聊发消息 → **落库 + 激活窗口 + 触发池子重投** |
| `GROUP_AT_MESSAGE_CREATE` | 群内 @机器人 |
| `FRIEND_ADD` | 加好友（可作为 `event_id` 被动回复） |
| `INTERACTION_CREATE` | 按钮回调（可作为 `event_id` 被动回复） |

**去重**：相同 `msg_id` 可能**多次推送**，必须按 `msg_id` 幂等落库（唯一索引）。

---

### 5.5 群消息事件的作者字段与单聊不同（**已核实，易错点**）

`GROUP_AT_MESSAGE_CREATE` 官方事件文档字段表原文：

> `author` | GroupUser | 发送者（**member_openid 有值**）

`GroupUser` 完整结构：

| 字段 | 说明 |
|---|---|
| `id` | 用户唯一标识（OpenID 格式） |
| `username` | 用户昵称 |
| `avatar` | 用户头像 URL |
| `bot` | 是否为机器人 |
| `union_openid` | 跨应用关联用户 openid |
| **`member_openid`** | **群成员 OpenID ← 群场景的对方标识** |
| `member_role` | `member` / `admin` / `owner` |
| `member_nickname` | 群内昵称 |

**与单聊的差异**：

| 场景 | 事件 | 作者结构 | 对方标识字段 |
|---|---|---|---|
| 单聊 | `C2C_MESSAGE_CREATE` | `MessageUser` | **`user_openid`** |
| 群聊 | `GROUP_AT_MESSAGE_CREATE` | `GroupUser` | **`member_openid`** |

**踩坑后果**：用同一个结构体会让群内申请全部落成空 openid。
所以 `pkg/qqbot` 里 `MessageUser` 与 `GroupUser` 必须是**两个独立类型**（不能复用）。

### 5.6 业务事件的签名校验（官方 `安全和授权` 页）

op=13 的地址验证用「自己算签名返回」，而**业务事件（op=0）用「校验平台发来的签名」**，
是两套方向相反的流程，容易混。

| 项 | 值 |
|---|---|
| 签名头 | `X-Signature-Ed25519`（hex 编码的 64 字节） |
| 时间戳头 | `X-Signature-Timestamp` |
| 签名对象 | **`timestamp + 原始 body 字节`**（不是重新序列化的 JSON，**不能 trim**） |
| 派生密钥 | 同一个 seed（BotSecret 循环填充到 32 字节）派生的**公钥**验签 |

官方示例在 hex 解码后还有一道严格校验：

```go
if len(sig) != ed25519.SignatureSize || sig[63]&224 != 0 {
    return false
}
```

`sig[63]&224 != 0` 是 Ed25519 S 值的高位预筛（防延展性攻击）。Go 标准库 `ed25519.Verify`
内部也会拒绝非规范 S，但官方明确要求，且能快速失败不进验签计算。

### 5.7 官方给出的两个可执行锚点（用来证明实现正确）

**锚点 A —— seed 派生**
```
secret: naOC0ocQE3shWLAfffVLB1rhYPG7      (28 字节)
seed:   naOC0ocQE3shWLAfffVLB1rhYPG7naOC  (32 字节 = repeat 后取前 32)
publicKey: [215 195 98 254 120 174 248 31 242 50 135 180 147 98 139 93
            176 42 60 79 227 11 33 94 77 25 96 155 93 118 103 58]
```
28×2=56 > 32，会触发截断路径 —— 比「16 字节 secret」更能证明是「repeat 后截断」而非 hash。

**锚点 B —— 业务事件验签：⚠️ 官方这个 DEMO 的 sig 无法复现，不能当验收标准**

官方文档给了：

```
secret:    naOC0ocQE3shWLAfffVLB1rhYPG7
timestamp: 1725442341
body:      { "op": 0,"d": {}, "t": "GATEWAY_EVENT_NAME"}
官方 sig:  865ad13a61752ca65e26bde6676459cd36cf1be609375b37bd62af366e1dc25a8dc789ba7f14e017ada3d554c671a911bfdf075ba54835b23391d509579ed002
```

**实测：用该 DEMO 自身给出的输入，无法算出这个 sig。**

穷举了 60 种合理解释，全部不匹配：
- 3 种 seed 派生：repeat 后截断 / 补零到 32 / sha256(secret)
- 5 种 body 字节：原文（带前后空格）/ 紧凑 / 尾换行 / 前后换行 / 尾空格
- 4 种拼接顺序：`ts+body` / `body+ts` / `ts\n+body` / `ts+body\n`

而**同一个页面的锚点 A（seed → publicKey）是逐字节匹配的**，证明密钥派生实现正确。
所以问题出在锚点 B 的 sig 本身 —— 判定为**文档占位值**（作者手写，未实际计算）。

**结论与对策**：
1. **不要拿锚点 B 当验收标准** —— 拿一个错的锚点做验收，会让写对了的人怀疑自己。
2. 「与官方一致」改由两件事共同保证：
   - 密钥派生：锚点 A 逐字节匹配官方公钥；
   - 签名对象与头名：官方文档**文字**规定（非 DEMO）——`X-Signature-Ed25519`、
     `X-Signature-Timestamp`、签名体 = `timestamp + 原始 body`、用派生公钥验。
3. 验签逻辑的正确性用**自洽锚点**守：自己签 → 自己验必须过；任何字节改动（多一个空格、
   换 timestamp、重新序列化）必须验不过。

> 这段结论已固化为 `pkg/qqbot/anchor_test.go` 的注释与用例，后续维护者不必重复踩。

## 六、Go 生态 SDK 调研

| 候选 | 结论 |
|---|---|
| `tencent-connect/botgo` | 官方维护，但面向**频道（Guild）**为主，v2 单聊/群聊支持较晚且与 v1 混排；依赖重（含 ws 全家桶） |
| `Infinityay/qqbot`、各类 fork | 玩具级，无错误码分类、无 token 并发刷新保护 |
| 自实现 | **采用**。理由：本项目只需要 HTTP 发消息 + webhook 校验，不需要 WebSocket 长连接；官方错误码表才是核心价值，第三方库都没有做分类 |

## 八、本轮不做（明确排除）

- **WebSocket 长连接**：webhook 已够用，ws 会引入常驻连接与重连复杂度
- **群聊发码**：邀请码是私密信息，只走单聊（群事件作者字段是 `member_openid`，
  与单聊不同，见 §5.5；本轮不做群场景，但 SDK 结构体已分开，后续可加）
- **富媒体(Markdown/卡片/按钮)**：先用纯文本，接口留出 `msg_type` 扩展位
- **频道(Guild)场景**：与社区业务无关
