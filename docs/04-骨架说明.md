# 04 · Go 骨架说明（T-05a）

> 生成日期：2026-11-19。对应交付：Go+Gin 项目骨架，`go build ./...` 与 `go vet ./...` 通过，health/ping 可访问。

## 1. 总体结构

代码直接放仓库根目录（`go.mod` 在根，模块名 `github.com/SugarLess-CN/fantwo-core`），未再嵌套 `server/` 目录——单服务仓库无需多一层。

```
cmd/server/main.go     启动入口：配置→zap→DB/Redis(懒连接)→AutoMigrate→路由→WS hub→优雅退出
internal/config/       viper 配置加载
internal/database/     GORM(PostgreSQL) + go-redis 初始化
internal/model/        GORM 实体（BaseModel + 示例实体 Sample）
internal/handler/      HTTP 处理层（doc.go 占位）
internal/service/      业务逻辑层（doc.go 占位）
internal/repository/   数据访问层（doc.go 占位）
internal/middleware/   JWT / CORS / zap 日志 / recovery
internal/pkg/jwtx/     JWT 签发与解析
internal/pkg/response/ 统一响应包装
internal/pkg/errcode/  错误码体系
internal/router/       路由注册
internal/ws/           WebSocket hub 骨架
internal/queue/        asynq 封装
migrations/            AutoMigrate 入口
```

启动流程（main.go）：`config.Load()` → zap logger → `MustInitPostgres`/`MustInitRedis`（失败仅 warning，返回 nil，服务降级运行）→ `migrations.Run(db)`（db 为 nil 时跳过）→ `jwtx.NewSigner` → `router.New` → WS hub → `http.Server` + signal 优雅退出（10s 超时，对齐原 `enableShutdownHooks`）。

## 2. 分层职责（handler → service → repository）

| 层 | 职责 | 禁止 |
|---|---|---|
| handler | 解析请求、binding 校验、调 service、统一响应 | 业务逻辑 |
| service | 业务规则、状态机、事务编排、事件/队列投递 | 接触 gin.Context |
| repository | GORM 读写封装、分页、预加载 | 业务判断 |

事务边界：service 层用 `db.Transaction(func(tx){...})` 显式开启，repository 方法接受 `*gorm.DB`（可为 tx），与原 NestJS `createQueryRunner` 事务语义对齐（支付回调/退款链将依赖此模式）。

与原 NestJS 的映射：controller → handler，service → service，TypeORM repository/entity → model + repository，guard → middleware，interceptor/filter → response 包 + 全局中间件，gateway → internal/ws。

## 3. 统一响应与错误码设计

对齐原仓库三处证据（`transform.interceptor.ts` / `http-exception.filter.ts` / `business.exception.ts`）：

- 成功：`{code:200, message:"操作成功", data}`（TransformInterceptor 原样；不带 timestamp）。
- 失败：`{code, message, data:null, timestamp(毫秒), path}`（HttpExceptionFilter 原样）；HTTP 状态码与 code 一致。
- 分页：`data = {list, meta:{total, page, limit, totalPages}}`（PaginatedResponseDto 原样）。
- **code 体系**：code 直接复用 HTTP 状态码（400/401/403/404/409/429/500），与原 BusinessException 一致；另设 **1000+ 业务细分段**（ErrUserAlreadyExists=1001 等）映射到对应 HTTP 状态，供支付/审核等需要前端区分细粒度错误的场景。
- 校验错误只取第一条消息（原 filter 的 `message[0]` 语义，业务批次在 binding 错误处理时保持）。
- health/ping 按任务书要求用 `{code:0, message:"ok"}`（`response.Health`），与业务成功码 200 并存——探针端点专用。

## 5. 关键设计决策

1. **懒连接**：gorm.Open 带 `DisableAutomaticPing`（真正懒握手），go-redis 天然懒连接；本机无 PG/Redis 时 main 正常启动、health 可通，业务端点降级。已冒烟验证。
2. **PostgreSQL**：原选型 MySQL → 用户 2026-11-19 改定 PostgreSQL（gorm.io/driver/postgres，DSN host/port/user/... 格式）；不需兼容存量数据，全新建库。
3. **迁移选 AutoMigrate**（`migrations.Run` 统一注册实体）：用户确认不需兼容存量数据；若未来需要受控变更，同目录引入 golang-migrate + SQL 版本文件。
4. **主键 UUID(char 36)**：保留 TypeORM uuid 主键语义（新库也用 uuid，前端 id 字符串化）；`BaseModel.BeforeCreate` 用 `github.com/google/uuid` 生成——该库不在 docs/03 清单内，属补充依赖（零传递依赖的生态标准库，替代自写 RFC4122 代码，符合第三方优先）。
5. **软删**：`gorm.io/plugin/soft_delete.DeletedAt` 索引列，对齐 TypeORM `@DeleteDateColumn`。
6. **JWT claims 内嵌 roles/permissions**：原 PermissionGuard 不查库、直接用 JWT 内权限比对（OR 关系），`jwtx.Claims` 保留 `uid/did/roles/perms`；`middleware.JWTAuth`（强制）、`OptionalAuth`（对应 @NoAuth 可选登录）、`RequirePermissions`（RBAC OR）三件套齐备。
7. **WS hub**：gorilla/websocket，`Frame{event,data}` JSON 帧对应 socket.io emit 语义；hub 提供注册/注销/房间/全体广播/定向广播（房间或单用户多端命中）；端点挂 `/api/v1/ws-message` 对齐原 namespace；事件名常量按 docs/01 §5 清单占位，读写泵骨架已通，事件分发在 message 批次实现。
8. **队列**：asynq 三队列名与原 Bull 完全一致（image-audit/text-audit/video-compression），并发 5/10/2、重试 5 次、指数退避、超时 5 分钟语义在 `NewServerConfig` 平移；任务 type 常量 `audit:image / audit:text / video:compress` 占位。
9. **gin 全局中间件顺序**：ZapLogger → ZapRecovery → gzip → CORS（全开，对齐原 enableCors 无配置；`AllowCredentials=false` 是 gin-contrib/cors 与 AllowAllOrigins 互斥的强制约束）。
10. **信任代理**：原仓库 `trust proxy` 开启，Go 侧暂用 gin 默认 `ClientIP()`；反代部署时在 main 设 `engine.SetTrustedProxies`（遗留项，见 §7）。
