# 媒体库与存储桶 —— 设计实现建议

> **本文是提案，不是现状。** 现状见 `docs/23-媒体库与存储桶-当前实现.md`。
> 每一条都标了「为什么现在不对」+「改成什么」+「成本与风险」，你可以逐条取舍。
>
> 快照时间：2026-11-25

---

## 零、先给结论：现有骨架是对的，问题都在细节

**不需要重构架构。** 两个驱动、两条上传路径、sha256 去重 + 引用计数，这套设计是合理的（对齐原仓库且更清晰）。

**要修的是 4 类问题**：

| 类别 | 条数 | 性质 |
|---|---|---|
| **静默失败** | 3 | 配错了不报错，偷偷降级 —— 最危险 |
| **数据一致性** | 2 | 引用计数、迁移，缺事务或幂等 |
| **权限语义** | 2 | 权限点选得不精确 |
| **可观测性** | 2 | 出问题时看不出来 |

下面按**优先级**排，不按模块排。

---

## 一、P1：把三处「静默失败」改成「显式失败」

### 1.1 S3 配置不全**静默降级** `local`

**现状**（`infra.go:200`）：
```go
if cfg.Storage.Driver == "s3" && (cfg.S3.Bucket == "" || cfg.S3.Endpoint == "") {
    cfg.Storage.Driver = "local"   // ← 只在日志里留一行
}
```

**为什么不对**：生产环境 `S3_BUCKET` 拼错一个字符 → 服务正常启动 → **所有文件写到容器本地盘** →
容器重启全丢。而监控显示一切正常。

**改成**：
```go
// 显式声明「允许降级」才降级，否则启动失败
if cfg.Storage.Driver == "s3" && (Bucket == "" || Endpoint == "") {
    if cfg.Storage.AllowFallback {
        log.Warn("S3 配置不全，按 allow_fallback 降级到 local —— 生产环境请勿依赖此行为")
        cfg.Storage.Driver = "local"
    } else {
        return fmt.Errorf("storage.driver=s3 但 bucket/endpoint 为空；" +
            "如确实要降级到本地，设 storage.allow_fallback=true")
    }
}
```

**新增配置**：`storage.allow_fallback`（默认 **false**）。

**成本**：1 个配置项 + 3 行代码。
**风险**：已有部署若依赖静默降级会启动失败 —— **但这正是我们要的**（早失败好过静默丢数据）。

### 1.2 `s3` 驱动下 `/upload/presign` 返回 503 但前端不知道原因

**现状**：`storage.go:612` 注释写着「driver!=s3 或 S3 未配置时返回 503（前端应回退到 `/upload/file`）」。
但响应体是通用 503，**没有 `capability` 字段告诉前端「为什么不能直传」**。

**改成**：503 响应带结构化原因
```json
{
  "status_code": 10009,
  "message": "Direct upload is not available",
  "data": {
    "reason": "storage_driver_local",     // 或 "s3_not_configured"
    "fallback": "POST /upload/file"       // 明确告诉前端该走哪条路
  }
}
```

**成本**：加 1 个 dto + 1 个分支。
**收益**：前端不用猜，且**这个字段本身就是运维诊断信息**。

### 1.3 `verifyS3Magic` 失败只记日志，记录照常入库

**现状**（`storage.go:692`）：直传确认阶段重新嗅探魔数，**失败时只打日志**，`uploads` 记录仍然建。

**为什么不对**：前端声明 `image/png` 实际传 `.exe` → 魔数不匹配 → 日志一行 → **但记录入库了**，
后续 `URL` 可访问，审核链路拿到的 `mimeType` 是假的。

**改成**：魔数不匹配 → **拒绝入库** + 删掉 S3 对象（避免留下孤儿文件）
```go
if err := verifyS3Magic(...); err != nil {
    _ = f.removeStored(req.storage, req.key)   // 清理刚传上去的脏文件
    return nil, errcode.ErrBadRequest.WithKey(i18n.UploadMimeMismatch)
}
```

**成本**：5 行。
**风险**：合法但奇怪的文件格式可能被误拒 —— 需要把白名单做成可配置（`upload_allowed_mime` 已在种子里有）。

## 二、P1：引用计数必须进事务

**现状**（`storage.go:218-226`）：
```go
existing, err := f.findByHash(ident)
if existing != nil {
    f.db.Model(&model.Upload{}).Where("id = ?", existing.ID).
        UpdateColumn("reference_count", gorm.Expr("reference_count + 1"))
    return existing
}
```

**问题**：`findByHash` 和 `+1` 之间没有事务，也没有行锁。并发上传同一文件：
- 两个请求都 `findByHash` 命中同一条
- 两个都 `+1`
- 结果 `reference_count = 3`（实际只应有 2）

**后果**：引用计数虚高 → **删文件时该删的不删**（磁盘泄漏）；计错少了则**不该删的删了**（数据丢失）。

**改成**（二选一）：

**方案 A：原子 UPSERT（推荐）**
```go
// 一条 SQL 完成「有则 +1，无则插入」
err := f.db.Clauses(clause.OnConflict{
    Columns:   []clause.Column{{Name: "hash"}},
    DoUpdates: clause.Assignments(map[string]interface{}{
        "reference_count": gorm.Expr("uploads.reference_count + 1"),
    }),
}).Create(&upload).Error
```
**优点**：单语句原子，无锁竞争。
**缺点**：`Create` 会把其它字段也带进去，需要确认 `OnConflict` 时只更新 `reference_count`
（用 `DoUpdates` 显式指定即可）。

**方案 B：事务 + `SELECT ... FOR UPDATE`**
```go
f.db.Transaction(func(tx *gorm.DB) error {
    var existing model.Upload
    tx.Clauses(clause.Locking{Strength: "UPDATE"}).Where("hash = ?", hash).First(&existing)
    if existing.ID != "" { /* +1 */ } else { /* insert */ }
    return nil
})
```
**优点**：逻辑直白。
**缺点**：`hash` 是唯一索引，冲突时靠 DB 报错，需处理重试。

**我倾向 A** —— 少一层事务、少一次往返，且天然并发安全。

**成本**：约 15 行（含测试）。
**验证**：并发 100 个 goroutine 上传同一文件，断言 `reference_count == 100`、磁盘只有 1 份。

## 三、P2：权限点语义修正

### 3.1 迁移端点用 `upload:delete` 不合适

**现状**：`/upload/migration/*` 三个端点都要求 `upload:delete`。

**为什么不对**：
- 语义错：迁移是「搬存储」，不是「删文件」
- 安全错：给了删除权限的人就能**搬空整个媒体库到 S3**
- 运维错：真实场景里「能删单个文件」和「能执行全库迁移」不是同一类人

**改成**：新增 `upload:manage`（已有此权限点，`upload:list/delete/create` 之外）：
```go
g.GET("/migration/stats",     append(infraChain(opt, "upload:manage"), h.MigrationStats)...)
g.POST("/migration/process",  append(infraChain(opt, "upload:manage"), h.MigrationProcess)...)
g.POST("/migration/metadata", append(infraChain(opt, "upload:manage"), h.MigrationMetadata)...)
```

**成本**：3 行 + 确认角色里 `upload:manage` 已分配给 super-admin。
**风险**：如果有普通运营角色带 `upload:delete` 但没 `upload:manage`，迁移会 403 —— **这是预期的收紧**。

### 3.2 `/upload/info/:id` 的 NoAuth

**现状**：NoAuth，返回含 `path` / `userId` / `hash` / `originalName` 的完整元数据。

**为什么保留原语义但我建议改**：原仓库对齐 `@NoAuth` 是为了「前端 <img> 标签能直接用」。
但**元数据公开**与**文件可访问**是两件事：
- 文件本身可访问（CDN/静态路由）—— 合理
- 元数据（谁传的、原文件名、hash）—— **不需要公开**

**改成**：拆两个端点
```
GET /upload/info/:id        → 需要登录（返回完整元数据）
GET /upload/public/:id      → NoAuth，只返回 { url, mimeType, size }  ← 前端 <img> 用这个
```

**成本**：新增 1 个 handler + 1 个 dto。
**风险**：前端若依赖 `/info/:id` 拿 URL 需改调 `/public/:id` —— **breaking change，需前端配合**。

**如果你不想动前端**，退一步：`/info/:id` 保持 NoAuth，但**去掉 `userId` / `hash` / `originalName`** 三个敏感字段。

## 四、P2：迁移的幂等与可恢复

**现状**：`migration/process` 每次全表扫描 `storage='local'` 的记录，逐条搬。
中断后重跑会**从头再扫**（虽然逻辑上幂等，但浪费）。

**改成**（低成本版）：
1. **加进度游标**：`process` 接受 `after_id` 参数，从上次中断处继续
2. **加幂等标记**：搬成功的记录置 `storage='s3'`（现在就是这么做的，OK）
3. **失败隔离**：单条失败 → 记 `migration_failed_reason`，继续下一条，不中断整批

**成本**：约 30 行。
**收益**：大批量迁移（几十万条）可分段执行，中断可恢复。

## 五、P3：可观测性

### 5.1 `/upload/config` 应暴露「真实生效值」

**现状**：返回配置项，但**不区分**「来自 DB」还是「来自 env 兜底」。
运维改 DB 没生效时，看不出是缓存还是 key 写错了。

**改成**：每个字段附带来源
```json
{
  "limits": { "imageMB": 20 },
  "sources": { "imageMB": "db" }     // db | env | default
}
```

**成本**：中（要改 `GetUploadConfig` 的取值层）。
**收益**：运维排障快 —— 这是 T-34e 那轮验收时反复确认过的事。

### 5.2 媒体库健康度端点

```
GET /upload/health   （需 upload:manage）
→ {
    "total": 12345,
    "byStorage": {"local": 12000, "s3": 345},
    "orphanFiles": 12,          ← 磁盘有文件但表里没记录
    "missingFiles": 3,          ← 表里有记录但磁盘没文件
    "zeroRefNonDeleted": 8,     ← reference_count=0 但没软删
    "jsonbNullThumbs": 0
  }
```

**为什么值得做**：媒体库最容易出的问题就是**表和磁盘不同步**（删了记录没删文件、或反之）。
现在要发现只能手工比。这个端点把「体检」变成一次请求。

**成本**：约 60 行（三个 count 查询 + 一次目录扫描）。
**风险**：全表扫描可能慢 —— 加 `LIMIT` 采样或只在低峰跑。

## 六、设计取舍：三个「不做」的建议

这几条是我**建议保持现状**的，列出来避免后人反复提：

### 6.1 不做「本地驱动也支持直传」

**理由**：本地磁盘没有预签名机制，要实现就得自己造一套（临时 token + 独立上传端点），
复杂度接近重写一个 S3。**本地驱动定位是开发环境，大文件慢一点可以接受。**

### 6.2 不做「`storage.driver` 运行期切换」

**理由**：minio client 在 `New()` 时初始化，运行期换驱动要处理「旧 client 怎么回收、
新 client 初始化失败怎么回滚、在途上传怎么办」。**收益远小于复杂度。**
现在的做法（改配置 → 重启）是明确的、可预期的。

### 6.3 不做「文件内容去重之外的分块上传」

**理由**：`sha256` 全文件去重已经覆盖了 90% 的场景（同一张图被多个帖子引用）。
分块上传（chunked/multipart）解决的是「单个超大文件」，本项目最大 500MB 视频，
`minio-go` 的 `PutObject` 已自带分块。

## 七、改动优先级与预估

| 序 | 改动 | 优先级 | 成本 | 风险 |
|---|---|---|---|---|
| 1 | S3 配错显式失败（`allow_fallback`） | **P1** | 低 | 已有部署可能启动失败（预期） |
| 2 | 引用计数原子 UPSERT | **P1** | 中 | 需并发测试 |
| 3 | presign 503 带结构化原因 | P1 | 低 | 无 |
| 4 | `verifyS3Magic` 失败拒绝入库 | P1 | 低 | 需确认 mime 白名单 |
| 5 | 迁移权限改 `upload:manage` | P2 | 低 | 收紧权限（预期） |
| 6 | 迁移加游标 + 失败隔离 | P2 | 中 | 无 |
| 7 | `/upload/info/:id` 拆公开/私有 | P2 | 中 | **breaking change** |
| 8 | `/upload/config` 暴露来源 | P3 | 中 | 无 |
| 9 | `/upload/health` 体检端点 | P3 | 中 | 全表扫描可能慢 |

## 八、如果要动，建议的落地顺序

```
第一批（半天）：1 + 3 + 4      ← 三个静默失败，都是小改动、高收益
第二批（一天）：2              ← 引用计数进事务，必须配并发测试
第三批（半天）：5 + 6          ← 权限收紧 + 迁移健壮性
第四批（待定）：7              ← 需前端配合，排期前先确认
第五批（可选）：8 + 9          ← 可观测性，看运维需求
```

**第一批为什么最优先**：三条都是「配错了不报错」——
这类问题**发现时通常已经造成损失**（文件写错地方、脏文件入库），
而修复成本极低（合计不到 20 行）。

## 九、需要你拍板的三个问题

1. **`storage.allow_fallback` 默认 false 会导致已有部署启动失败** —— 接受吗？
   （我建议接受：早失败好过静默丢数据。若担心，可先设 true 观察一段时间再改 false）

2. **`/upload/info/:id` 拆端点会 breaking change** —— 前端能配合吗？
   如果不能，退一步只去掉 3 个敏感字段，成本更低但仍需前端确认。

3. **`/upload/health` 要不要做？** —— 它需要全表扫描，
   如果媒体库只有几千条无所谓；几十万条要考虑加采样或异步。
