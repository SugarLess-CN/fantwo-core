## 二、A 段：requestBody（4 个接口）

| # | 接口 | Go 现状 | 判定 |
|---|---|---|---|
| A1 | `POST /user/email/verification` | `dto.EmailCodeRequest` | ✅ 已有 |
| A2 | `POST /user/password/reset` | `dto.ResetPasswordRequest` | ✅ 已有 |
| A3 | `POST /user/password/change` | `dto.ChangePasswordRequest` | ✅ 已有 |
| A4 | `PATCH /user/profile/contact` | `dto.UpdateProfileRequest`（通用 9 字段） | ⚠️ **DTD 选错** |

### A4 详情

`UpdateProfileRequest` 是**通用资料更新** DTO：

```go
type UpdateProfileRequest struct {
    Nickname, Avatar, Description, Background, Address,
    Gender, BirthDate, Email, Phone      // 9 个指针字段
}
```

但 `/user/profile/contact` 语义是「改邮箱 / 手机号，**必须带验证码**」。
`handler/user.go:70` 的注释写着「带验证码校验走 BindPhone」，**实际实现没有验证码**。

**应改为专用 DTO**：

```go
// UpdateContactRequest 修改联系方式（PATCH /user/profile/contact）。
//
// 为什么独立：改联系方式必须验证码，改昵称不需要。
// 共用 UpdateProfileRequest 会让「带验证码」这条安全约束无处安放。
type UpdateContactRequest struct {
    Email            string `json:"email" example:"alice@example.com"`
    Phone            string `json:"phone" example:"13800138000"`
    VerificationCode string `json:"verification_code" example:"123456"`
}
```

**风险（修复前）**：可**无验证码直接改邮箱/手机号** —— 账号接管（account takeover）面。

**已落地的语义（2026-11-27）**：

| 规则 | 原因 |
|---|---|
| `verification_code` **必填** | 无码改联系方式 = 接管 |
| `email` 与 `phone` **一次只能传一个** | 验证码按 `(target, scene)` 签发，一个 code 物理上不可能同时命中新邮箱与新手机号 |
| 改邮箱走 scene `verification` | 与 `POST /user/email/verification` 同 scene |
| 改手机走 scene `bind_phone` | 与 `POST /user/profile/phone/code` 同 scene |

> **若前端需要「一次改两项」**：得改成两个验证码字段（`email_code` + `phone_code`），
> 或加 `target_type` 参数区分。当前是「一次一项」。

## 三、B 段：请求体 DTO 缺字段（**全缺，优先做**）

### B1. `RegisterRequest` 缺 2 个字段

| 字段 | 现状 | 说明 |
|---|---|---|
| `invite_code` | ❌ 无 | Go 用独立端点 `POST /invite/use`，注册时不带 |
| `verification_code` | ❌ 无 | Go 注册**不校验邮箱验证码** |

```go
// 现状（5 字段）
type RegisterRequest struct {
    Username, Nickname, Password, Email, Phone
}
```

**两种选择**：

| 方案 | 做法 | 代价 |
|---|---|---|
| **A. 前端改** | 注册后单独调 `POST /invite/use` 用邀请码 | 前端多一次请求 |
| **B. 后端补**（推荐） | `RegisterRequest` 加 `invite_code` + `verification_code`，service 内消费 | 后端改，前端零改动 |

**推荐 B**：邀请注册是高频路径，两次请求可能出现「注册成功但邀请码失败」的中间态。
补齐后 `POST /invite/use` 保留（用于已注册用户补填邀请码）。

> ⚠️ 补 `verification_code` 意味着**注册必须验邮箱** —— 需确认产品是否accept。

**已落地的语义（2026-11-27）**：**非空才校验**（不是必填）。理由：现有客户端全都不传，
改必填会把调用方一次性打成 400。要改必填只需删掉一层 `if`，是产品决策不是实现问题。

**邀请码是「先预校验、建号后再消费」**：预校验在建号前（避免「用户已建、邀请码是错的」中间态），
真正的 `PENDING→USED` 状态变更在事务提交后做（失败只 warn 不踢用户 —— 号已经建好了）。

### 唯一真缺口：`UserDto` 缺 `config`

`LoginResultDto` 与 `UserProfileDto` **都内嵌 `UserDto`**，所以只要给 `UserDto` 加一个字段，两个接口同时满足。

```go
type UserDto struct {
    // ... 现有 30 个字段 ...

    // Config 用户的配置全集（通知 / 隐私 / 水印 / 佣金）。
    //
    // 为什么内嵌到 UserDto 而不是各自加：
    // 登录一次就要拿到全部配置，否则前端进设置页要再发一次 /user/config。
    // 用指针 + omitempty：列表接口不加载配置时整个字段不传（docs/21 规则 ③）。
    Config *UserConfigDto `json:"config,omitempty"`
}
```

**注意**：`UserDto` 被**列表接口**（`GET /user`、关注/粉丝列表）也用。
列表页 N 个用户各带一份 28 字段配置 = 响应体爆炸。

**必须**：只在**详情类**接口（login / profile / user/{id}）填充 `Config`，
列表接口留 `nil`（omitempty 保证不出现）。

## 五之二、⚠️ 路径契约澄清：前端交接单引用了 3 个不存在的路径

前端 `api-compat-handover.md` 的 D 段提到 `/search/articles`、`/search/tags`、`/search/users`。
**实测两个版本都没有这些路径**：

| 前端写的路径 | JS 版有 | Go 版有 | 实际该用哪个 |
|---|---|---|---|
| `GET /search/articles` | ❌ | ❌ | **`GET /article/search`**（两版都有，最接近） |
| `GET /search/tags` | ❌ | ❌ | **`GET /tag`**（两版都有，加 `keyword` 即等价） |
| `GET /search/users` | ❌ | ❌ | **`GET /user`**（两版都有，已有 `keyword` 参数） |

另：`GET /search`（无 articles 后缀）**只有 Go 版有**（我们新增的 ES 直查端点，与 `/article/search` 的 DB 查询是两条不同实现）。

**结论**：
- 前端可能一直在调 404 路径，然后靠本地过滤兜住 —— 这解释了交接单里「拉全量 + 本地过滤」的做法
- 补齐 `sort_by` / `category_id` 后，前端改调 `/article/search` 即可获得服务端排序与分类筛选

### ✅ `/search/tags`、`/search/users` 已按用户决定新建（2026-11-27）

| 端点 | 实现 | 与旧路径的关系 |
|---|---|---|

### 唯一的 3 个「残留」是误报

`Decoration` 的 `ACHIEVEMENT_BADGE` / `AVATAR_FRAME` / `COMMENT_BUBBLE` ——
JS 的 schema 生成器把 **`type` 字段的枚举值当成了属性名**。我们用 `type` 字段表达，语义正确。
