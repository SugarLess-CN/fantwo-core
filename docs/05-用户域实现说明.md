## 2. 认证实现要点

| 能力 | 实现 | 与原项目的对应 |
|---|---|---|
| 账号密码登录 | 账号含 `@` 走邮箱、否则用户名；`bcrypt.CompareHashAndPassword` 校验 | 原 `validateUser`（NotFoundException userNotExist / BadRequest passwordError） |
| 双 token | access（1h）+ refresh（7d），claims 含 `uid/did/roles/perms/pv` | 原 `jwtUtil.generateTokens` |
| refresh 落库 | refresh token 的 bcrypt 哈希存 `user_device.hashed_refresh_token` | 原 `bcrypt.hash(refreshToken, 10)` |
| 刷新 | 验签 + 黑名单 + logout_all 时间 + 哈希比对 → 重签 access（滑动过期） | 原 `refreshToken` |
| 单端登出 | 删设备记录 + access token 进 Redis 黑名单（**Key TTL = token 剩余生命**） | 原 `logout` + 设备删除 |
| 全端登出 | Redis `user:{id}:logout_all` 时间戳 + 清全部设备；中间件拒绝 `iat` 早于该时间的 token | 原仓库无此接口，任务书 §1 新增 |
| 短信登录 | 验证码校验后按手机号取用户；未注册自动建号（随机密码 + `user` 角色） | 原仓库无，任务书 §1 新增 |
| 验证码 | `verify:code:{scene}:{target}` 10 分钟；`verify:sent:{scene}:{target}` 1 分钟防重发 | 原 `verification_code:{email}` / `send_verification_code:{email}:{type}` |
| 改密 / 重置密码 | 改密与重置后写 `logout_all` 时间戳（强制全端重新登录） | 原 `changePassword` / `resetPassword` |
| 密码哈希 | bcrypt cost 10（与 Node bcrypt `$2a/$2b` 零迁移兼容，见 docs/03 §七） | — |

**权限版本（perm_ver）机制**：JWT 携带签发时的 `p` 快照（`pv`）；`JWTAuthV2` 验签后比对 Redis `user:{id}:permver`，不一致直接 401 `code=2002`。角色权限/菜单/状态变更、用户角色变更时 `INCR` 受影响用户的版本号（`BumpPermVerMany` 批量 pipeline），令旧 token 立即失效。

## 3. 账号注销三态

| 动作 | 端点 | 状态变化 |
|---|---|---|
| 提交 | `POST /user/account/deletion` | `account_deletion.status=1`（冷静期），`scheduled_at=now+7d`；同时向 asynq **延迟队列**投递 `account:deletion:execute`（`ProcessIn(7*24h)`） |
| 查询 | `GET /user/account/status` | 返回 `status / deletionPending / scheduledAt` |

| 到期执行 | `UserService.ExecuteDueDeletions` | `status=2` + 用户转 `INACTIVE` + `logout_all`；可挂 asynq handler 或定时任务兜底（扫描 `DueDeletions`，不依赖队列是否可用） |

## 6. 降级与错误语义

- DB 为 nil（骨架懒连接降级）：业务端点统一 `503 / code=5031`，health 不受影响。

## 8. provider 实装（T-15 / T-23）

三处占位已按「**可配置即生效、未配置即降级**」实装，配置统一从 config 表读取（复用基础设施域 `ConfigService`，进程内缓存 → Redis → DB；`Deps.Cfg` 抽象为 `ConfigReader` 接口便于测试注入）。

| provider | 文件 | 配置键（config 表） | 未配置时行为 | 已配置时行为 |
|---|---|---|---|---|
| GitHub OAuth | `internal/service/github_oauth.go` | `github_client_id` / `github_client_secret` / `github_redirect_uri` / `github_success_redirect_url` / `github_scope` | 400 + code=4022（原占位语义保留） | 真实 authorize（state 存 Redis 10 分钟防 CSRF）→ 换 access_token → 拉 /user（email 空则补 /user/emails 取 primary+verified）→ 按 `github_id` 找用户，找不到按邮箱合并绑定，仍无则建号（用户名冲突追加 `-gh<3位>`、随机密码不可密码登录、默认 user 角色）→ 签发双 token |
| 邮件（SMTP） | `internal/service/mailer.go` | `smtp_host` / `smtp_port` / `smtp_user` / `smtp_password` / `smtp_from` / `smtp_from_name` / `smtp_implicit_tls` | 只写 Redis + 打 log（开发模式日志含验证码） | 标准库 `net/smtp` 发送：465 隐式 TLS / 其余 STARTTLS，MIME UTF-8 + base64 正文 |
| 短信网关 | `internal/service/sms.go` | `sms_channels`（JSON 数组） | 只写 Redis + 打 log（手机号脱敏） | 按渠道逐个尝试通用 HTTP 网关（GET/POST、自定义 headers、`{{phone}}/{{code}}/{{scene}}` 模板、`successContains` 响应匹配、`timeoutMs`），任一成功即止 |

**为什么短信走 config 表而不是独立渠道表**：Go 侧不存在 `admin/sms/channels` 表（原 NestJS 仓库也没有短信模块，全仓库 grep 无实现）。用 config 表的 JSON 值即可满足「渠道可配置」，不新增表、不侵入基础设施域模型。

`sms_channels` 配置样例：

```json
[{"name":"dev-gateway","enabled":true,"url":"https://sms.example.com/send",
  "method":"POST","contentType":"application/json",
  "headers":{"X-App-Key":"APPKEY"},
  "bodyTemplate":"{\"phone\":\"{{phone}}\",\"code\":\"{{code}}\",\"scene\":\"{{scene}}\"}",
  "successContains":["\"ok\":true"],"timeoutMs":5000}]
```

投递分发逻辑在 `AuthService.SendCode`：目标含 `@` → 邮件；否则手机号 → 短信。`users` 表 `github_id` 已有唯一索引（`model.User.GithubID`）。

单测：`internal/service/provider_test.go`（9 例：模板渲染、三 provider 未配置降级、假 HTTP 网关收发与响应不匹配判定、授权链接与 state、邮件正文、目标形态判定、日志脱敏）。

## 10. 跨域事件发布端（T-32）

`internal/event/ops_events.go` 的常量此前只有订阅端、发布端空缺（表现为「签到后积分仍为 0、成就 completed:0」）。用户域补齐 5 个事件的发布，**全部在业务事务提交之后**调用，payload 类型与定义完全一致：

| 事件 | 发布位置 | payload | 消费方效果 |
|---|---|---|---|
| `user.dailyLogin` | `UserService.Sign`（签到成功，含 getProfile 自动签到） | `event.UserDailyLoginPayload{UserID, ConsecutiveDays}` | 积分活动 `DAILY_LOGIN` 触发 + `LOGIN_7_DAYS` / `LOGIN_30_DAYS` 成就 |
| `user.followed` | `UserService.Follow`（仅首次建立关注时） | `event.UserFollowedPayload{UserID: 关注者, TargetUserID: 被关注者}` | `FIRST_FOLLOW` / `FOLLOW_10`（关注者） |
| `user.receivedFollow` | 同上（同一处双发） | `event.UserReceivedFollowPayload{UserID: 被关注者, FollowerID: 关注者}` | `FIRST_FOLLOWER` / `FOLLOWER_100` / `FOLLOWER_1000`（被关注者） |
| `user.profileCompleted` | `UserService.UpdateProfile` / `UpdateUser`（**不完整 → 完整**跃迁时只发一次） | `event.GenericPayload{UserID}` | `PROFILE_COMPLETED` |
| `user.levelUp` | `UserService.AddExperience`（新等级 > 旧等级时） | `event.UserLevelUpPayload{UserID, Level}` | `LEVEL_10` / `LEVEL_30` / `LEVEL_50` |

**签到链路的完整闭环**（`Sign` 内顺序，均在签到记录落库后）：

1. 发布 `user.dailyLogin`（连续天数）；
2. `PointsService.TryAddByRule(userID, "DAILY_LOGIN", "sign_in", 日期)` 按活动规则发放积分（活动 `DAILY_LOGIN` 每日限 1 次，未配置/超限则静默跳过）——这是「签到后 `/points/balance` 应有积分」的直接来源；
3. `AddExperience(+5)` 加经验，命中门槛则内部发布 `user.levelUp`；
4. 连续 7 的倍数天额外 +7 积分（保留原 `performSignIn` 语义）。

**等级规则**：`internal/service/level.go` 的 `levelConfig` 对齐原 `level.service.ts` 的 `LEVEL_CONFIG`——`0:0 / 1:100 / 2:300 / 3:600 / 4:1000 / 5:1500 / 6:2100`，`calculateLevel` 取命中最高档。原仓库上限即 6 级，故 `LEVEL_10/30/50` 成就与原项目一样不可达（不擅自延伸档位）。

**为什么资料补全用「跃迁判定」而非 Redis 标记**：更新前后各判一次 `isProfileComplete`（昵称 + 头像 + 简介三项齐备），仅 `false → true` 时发布，天然幂等、不依赖 Redis、可重复调用不虚增成就进度。

**单测**：`internal/service/level_test.go`（7 例）——5 个事件的发布触发与 payload 字段逐一断言、空 UserID 不发布、等级门槛全档位、资料补全判定矩阵。
