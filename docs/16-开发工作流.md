# 开发工作流（改完代码之后做什么）

> 固化的标准流程。每次改动代码，按本文件的 7 步走完才算交付完成。
> AGENTS.md 的「标准工作流」章节是精简版指针，本文件是详细版（含命令、验收标准、踩过的坑）。
>
> 最后更新：2026-11-25

---

## 总览：七步

```
Step 1  代码质量门         gofmt / build / vet / test 全绿
Step 2  swag 重新生成      改了 handler 注解 / 类型 / 新增端点才做
Step 3  真机验证           改了行为或接口必须做
Step 4  Apifox 导入        swagger 变了才做（含分类保护 + 导入后核对）
Step 5  文档与账本         reports / todo / AGENTS 三处
Step 6  提交推送
Step 7  收口确认
```

**判断哪些步骤可跳**：

| 改动类型 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
|---|:-:|:-:|:-:|:-:|:-:|:-:|:-:|
| 拼写 / 注释 / 文案 | ✅ | — | — | — | ✅ | ✅ | ✅ |
| 纯内部实现（无接口变化） | ✅ | — | ✅ | — | ✅ | ✅ | ✅ |
| 新增 / 修改 handler 或 DTO | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |
| 只改 i18n 文案 | ✅ | — | ✅ | — | ✅ | ✅ | ✅ |
| 只改 migrations | ✅ | — | ✅ | — | ✅ | ✅ | ✅ |

## Step 1：代码质量门（永远不能跳）

```bash
gofmt -l internal/ migrations/ cmd/     # 期望：空输出
go build ./...
go vet ./...
go test ./... -count=1                  # 期望：16 包全绿
```

**任一项红 → 停下来修，不许带着红进入下一步。** 尤其是 `go test`：允许阶段性失败（并行成员写到一半），但提交前必须全绿。

常见红的原因（本会话踩过）：
- `.Msg` 字段改 `.Msg()` 方法 → 所有断言连锁失效
- 删了某个类型（如 `GithubProfile`）→ 引用它的测试编译不过
- `undefined: i18n` / `undefined: log` → 并行成员的文件处于中间态，等它收口或自己兜底

## Step 2：swag 重新生成

**什么时候做**：新增/删除 HTTP 端点、改 handler 的 `@Summary`/`@Router`/`@Param` 注解、改 handler 签名里的 DTO 类型、改 swagger_types.go。

```bash
make swag
# 等价于：swag init -g cmd/server/main.go -o docs/swagger --parseDependency --parseInternal --exclude tmp,internal/dto
```

⚠️ **本机没有 `make`**（Windows/MSYS 实测 `make: command not found`，2026-11-25 两位成员先后踩到）。
用等价命令，效果完全相同：

```bash
"$(go env GOPATH)/bin/swag.exe" init -g cmd/server/main.go -o docs/swagger \
  --parseDependency --parseInternal --exclude tmp,internal/dto
echo "exit=$?"        # ★ 必须看 exit code
```

**为什么必须看 exit code**：有成员写了 `swag ... 2>&1 | grep -i error`，把 `No such file` 这类
"命令根本不存在"的错误过滤掉了，**误以为跑成功**——当时看到的 definitions 变化其实是另一个成员
并行跑出来的。swag 是外部二进制，不在 PATH 里时失败得非常安静。

### 必查三项

**① `--exclude tmp` 不能丢**
`tmp/` 下若有「整个项目源码的副本」（如 `tmp/deploy-pkg`，由 `make-deploy-pkg.sh` 生成），
swag 会把它当成包 `tmp_deploy-pkg_internal_handler` 扫进去，`$ref` 全部指向错误定义。

```bash
python -c "
import json; d=json.load(open('docs/swagger/swagger.json',encoding='utf-8'))
defs=list(d.get('definitions',{}).keys())
print('paths:', len(d.get('paths',{})), '| definitions:', len(defs))
print('污染:', [x for x in defs if 'tmp' in x] or '无 ✓')"
```
**期望**：`污染: 无 ✓`。出现 `tmp_*` 前缀 → `tmp/` 下又有源码副本，删掉它。

**② 新增端点必须真的进了 paths**
```bash
grep -c "你新增的路径片段" docs/swagger/swagger.json
```

**③ 新 handler 的 `@ID` 符合规范**
```bash
grep -B2 "@Router" internal/handler/<你改的文件>.go | grep "@ID"
```
规范：`<Controller名>_<方法名>`，如 `OAuthBindingController_listBindings`。
**禁止**中文、纯 snake_case（`post_user_login`）、纯方法名。存量 307 个中文 operationId 是历史遗留，不批量改。

### 已知的非阻塞警告

```
warning: route POST /certification/admin/applications/{id}/revoke is declared multiple times
```
certification 系 7 条重复声明，**非本轮引入**，不影响产物正确性（swag 取最后一个）。要修得改 `internal/router/user_routes.go` 的重复注册，属独立任务。

## Step 3：真机验证

**什么时候做**：改了任何对外可见行为（接口、错误码、统计口径、配置读取、支付回调逻辑）。

**为什么不能只靠单测**：单测是 mock 的，测不到「配置从 DB 读得到吗」「路由真的注册了吗」「响应契约真的对吗」。本会话的真缺陷（微信 `sns/auth` 缺 errcode 静默放行、QQ stripJSONP 误伤、`withThumbnails` 口径虚高）**全部是单测绿但真机才暴露**。

### 起服务

```bash
# 方式 A：用 .env（推荐，godotenv 已启用）
cp .env.example .env    # 首次
# 填 POSTGRES_PASSWORD / JWT_SECRET
go run ./cmd/server

# 方式 B：显式 env（临时验证，端口要避开默认 3000，防与常驻进程冲突）
go build -o tmp/verify.exe ./cmd/server
(POSTGRES_HOST=127.0.0.1 POSTGRES_PORT=5432 POSTGRES_USER=postgres \
 POSTGRES_PASSWORD=*** POSTGRES_DATABASE=fantwo_core POSTGRES_SSL_MODE=disable \
 JWT_SECRET=verify-only-32chars-min REDIS_ADDR=127.0.0.1:6379 \
 SERVER_PORT=3987 ./tmp/verify.exe > tmp/verify.log 2>&1 &)
sleep 16    # 等 AutoMigrate + 种子完成（首次建表会慢）
```

### 断言清单

| 检查项 | 期望 |
|---|---|
| 响应契约 | `{"data":...,"message":"...","status_code":N,"trace_id":"...","timestamp":...}`；data/message 为空时**字段省略** |
| 错误码 | `status_code` 是 5~6 位业务码（≠ HTTP）；HTTP 码独立（404/401/403） |
| 文案 | 全英文，来自 i18n；不含中文、不含 `%s` 未替换 |
| 空数据 | list 类是 `[]` 不是 `null` |
| 日志 | 无 token / openid 明文（docs/14 §7.1.2 禁令 1） |

### 收尾（**必做**）

```bash
taskkill //IM verify.exe //F        # 必须停，否则下次端口占用
# 清理测试数据（造过的绑定/用户）
docker exec postgre psql -U postgres -d fantwo_core -c "DELETE FROM ... WHERE ..."
```

### 关键：抓真实响应贴进报告

`reports/NN` 的第 ④ 节要求**真实命令与真实输出**，不许写「已验证」。所以验证时就把 curl 的输出留下。

## Step 4：Apifox 导入

**什么时候做**：Step 2 产出了新/改的 swagger。

### 4.1 分类保护（**最容易漏，漏了会造成 Apifox 目录混乱**）

Apifox 按 `tags` 自动匹配已有目录。tag 名与 Apifox 原有目录名**不完全一致** → 会新建同义不同名的目录。

**新增 tag 时必做**：
1. 用只读 MCP 读 Apifox 现有 OAS，收集所有已有 tag/目录名
2. 通读新接口的 path + summary，按**业务语义**归入最匹配的已有目录
3. 把新映射写进 `scripts/gen-apifox-enhanced.py` 的 `TAG_MAP`

**当前 TAG_MAP 覆盖 20 条**（成就→成就管理、消息→信息管理、统计→统计模块…）。
未覆盖的 tag 会原样导入 → 若 Apifox 没有同名目录就会新建。

> 历史事故：曾用 swagger 的两字 tag（「文章」「轮播」）直接导入，Apifox 建了 17 个两字目录，
> 而原有的是四字（「文章管理」「轮播管理」）→ 原有目录变空，需手工清理。

### 4.2 生成增强版批次

```bash
python scripts/gen-apifox-enhanced.py docs/swagger/swagger.json tmp/apifox-enhanced/
# 产出：tmp/apifox-enhanced/s-*.json（schema，每个 1 个）
#       tmp/apifox-enhanced/o-*.json（operation，每个 1 个）
```

增强内容（相对裸 swag 产物）：
- 每个 operation 补 `description`、`example`（真实感模拟数据）
- 补 5 个错误响应（400/401/403/404/409/429/500）各带 example
- 响应 example 含 `trace_id` + `timestamp`
- `$ref` 从 `#/definitions/` 改为 `#/components/schemas/`
- tag 按 TAG_MAP 映射

### 4.3 导入

```bash
node scripts/apifox-import.mjs tmp/apifox-enhanced/
# 断点续传：--start N
# 演练：--dry-run
# 日志：tmp/apifox-import.log（每行带时间戳 + 成功/失败 + 计数）
```

底层是直调 Apifox Open API（与 `apifox-import-mcp@1.0.1` 同协议）：
```
POST https://api.apifox.com/v1/projects/{id}/import-openapi
Body: { "input": "<OAS3 JSON 字符串>", options: { endpointOverwriteBehavior: "AUTO_MERGE" } }
```
**关键**：`input` 是**字符串**不是对象；每次 1 个 operation（2 个以上必 422）。

### 4.4 导入后核对（**容易漏**）

```bash
# ① 看计数
tail -20 tmp/apifox-import.log      # 期望：成功 N / 失败 0

# ② 用只读 MCP 核对 Apifox 里的实际 paths 数
#    mcp__apifox-picart__refresh_project_oas_*   ← 先刷新
#    mcp__apifox-picart__read_project_oas_*      ← 读 paths 数
#    对比 本地 swagger 的 paths 数
```

失败不为 0 → 看日志里的 `✗` 行，按 `.claude/skills/apifox-import/SKILL.md` 的 422 排查表处理。

## Step 5：文档与账本（三处，都不能漏）

### 5.1 报告 `reports/NN-T<任务号>-<主题>.md`

编号只增不改（当前到 09）。五节结构，缺一节算未完成：

```markdown
## 一、本轮改了什么
逐文件逐函数，行号区间，改前 → 改后

## 二、功能变化
对用户 / 前端 / 运维可见的行为差异。必须写清「改前行为」与「改后行为」

## 三、配置项 / 接口清单
新增/变更的配置键、端点、错误码

## 四、验证证据
真实命令 + 真实输出（贴 curl 响应、go test 输出）。
禁止写「已验证」「已通过」这类无证据描述

## 五、遗留与风险
明确写出没做的、有疑问的、需要用户决策的
```

### 5.2 `reports/README.md` 索引表加一行

```markdown
| 10 | `10-T37e-账号绑定管理.md` | 3 端点 + 解绑安全规则 + 硬删决策 | ✅ 2026-11-25 |
```

### 5.3 `todo.md` 与 `AGENTS.md`

- `todo.md`：条目状态打勾 + 写清关键决策与验证结果（不是只写「完成」）
- `AGENTS.md`：`## 变更记录` 追加一行（含 commit hash 关键决策）

> `AGENTS.md` / `todo.md` 都是 **gitignored 的本地治理文件**，不入仓库。

## Step 6：提交推送

```bash
git add -A
git status --porcelain        # 必须确认：tmp/ 不在列表、AGENTS.md / todo.md 不在列表
```

### commit message 的坑

**message 里含反引号（\`）或特殊字符时，必须用文件传入**：

```bash
cat > tmp/msg.txt <<'EOF'
feat(scope): 标题

正文...
EOF
git commit -F tmp/msg.txt
```

直接用 `git commit -m "...\`code\`..."` 会被 shell 吞掉反引号内容（当命令替换执行）。

### 提交信息约定

```
<type>(<scope>): <中文摘要>

<正文：改了什么、为什么、关键决策与理由>

## 验证
<真实输出摘要>
```

`type`：`feat` / `fix` / `test` / `docs` / `chore` / `refactor` / `merge`

```bash
git push origin main
```

## Step 7：收口确认

```bash
git status --porcelain          # 期望空
git log --oneline -1            # 本地 HEAD
git ls-remote origin main       # 远程 hash，必须与本地一致
```

三项都对上才算交付完成。

## 周期性 / 发布时才做的（不属于每轮工作流）

| 动作 | 命令 | 何时 |
|---|---|---|
| 打部署包（源码，服务器编译） | `bash scripts/make-deploy-pkg.sh` | 发布到测试/生产 |
| 打二进制包（服务器只拷） | `bash scripts/make-binary-pkg.sh` | 发布，且目标机不能编译 |
| 重建镜像 | `make docker-build` | 改了 Dockerfile / go.mod / 依赖 |
| 路由审计 | `make route-audit` | 核对与 docs/02 的差异 |
| 覆盖率 | `make cover` | 阶段性质量检查 |
| `go mod tidy` | — | **只在动了 go.mod 时**（go.mod 归 lead 独占，成员禁改） |

## 检查清单（复制到每轮开头用）

```
□ Step 1  gofmt 空 / build OK / vet 零输出 / test 16 包全绿
□ Step 2  (改接口才做) swag init（本机无 make，用 swag.exe 等价命令 + 看 exit code）→ definitions 无 tmp_ 污染 / 新端点已进 paths / @ID 合规
□ Step 3  (改行为才做) 真机起服务 → 契约/错误码/文案/空数据 四项断言 → 抓真实响应 → 停进程 + 清测试数据
□ Step 4  (swagger 变了才做) 分类保护核对 → gen 增强版 → import → 日志计数 + 只读 MCP 核对 paths
□ Step 5  reports/NN 五节 + README 索引 + todo 打勾 + AGENTS 变更记录
□ Step 6  git add -A → 确认 tmp/ 与治理文件未进 → commit -F → push
□ Step 7  status 空 / log 与 ls-remote 一致
```

## 附：本会话踩过的坑（新增步骤时的参考）

| 坑 | 症状 | 教训 |
|---|---|---|
| swag 扫到 `tmp/deploy-pkg` | definitions 6→11，`$ref` 指向 `tmp_deploy-pkg_internal_handler.*` | `--exclude tmp` 必须保留 |
| tag 与 Apifox 目录名不一致 | 原有目录变空，出现 17 个同义新目录 | 导入前必须做分类保护 |
| commit message 含反引号 | shell 当命令替换，message 被截断 | 用 `git commit -F 文件` |
| 单测绿但真机崩 | 微信 `sns/auth` 缺 errcode 静默放行伪造 token | 安全相关改动必须真机验证 |
| 先启动服务后灌库 | 配置读不到（Redis 缓存空值 10 分钟） | 灌库后重启服务，或走 `PATCH /config` |
| 并行成员改同一文件 | `undefined: i18n` 中间态 | write scope 要互斥，lead 兜底收敛 |
| 测试断言改不动就改实现 | 微信 40001 映射被误判 | 断言错就改断言，实现错就改实现，不许互相迁就 |
