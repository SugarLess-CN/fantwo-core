# 08 · 配置迁移运维手册

> 适用版本：2026-11-23 起的 `fantwo-core`（commit `2b3ad7d` 及之后）
> 相关报告：`reports/06-T34e-真机验收.md`（验收证据）、`reports/07-配置迁移全貌-env对照与数据库现状.md`（完整 key 对照）

---

## 一、一句话说明改了什么

**运行期可调的配置从「只能改 env + 重启」变成「DB config 表优先，改完不重启即生效」。**

env 变量**一个都没删**，只是从「唯一通道」降级为「兜底默认值」。

---

## 二、三个通道：哪个配置走哪条路

### 通道 A — DB config 表（推荐，改完不重启）

生效优先级：**DB config 表 → env → 代码内置默认值**

改法（需 `setting:update` 权限）：

```bash
# 单条
curl -X PATCH http://<host>/api/v1/config/<id> \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"value":"7"}'

# 批量（key 维度）
curl -X PATCH http://<host>/api/v1/config \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '[{"key":"upload_max_image_size","value":"7"},{"key":"upload_max_file_count","value":"3"}]'
```

响应语义：

```json
{"code":200,"data":{"updated":2,"skipped":0}}
```

- `updated` = **真实写库的行数**（不是请求条数）
- `skipped` = 被跳过的条数，两种情况：key 不存在；敏感项传了空串或 `***`

**走这条通道的配置**（共 22 项有后端消费点）：

| 分类 | key |
|---|---|
| 上传 | `upload_max_image_size` / `_video_size` / `_audio_size` / `_other_size` / `upload_max_file_count` / `upload_compression_enabled` / `upload_thumbnail_specs` |
| 水印 | `upload_watermark_enabled` / `_text_template` / `_position` / `_opacity_percent` / `_font_size` |
| 存储 | `storage_local_dir` |
| CDN | `cdn_base_url` |
| 搜索 | `search_enabled` / `search_addresses` / `search_username` / `search_password` / `search_articles_index` |
| 审核 | `content_audit_provider` / `_auto_block` / `_review_mode` / `_sensitivity` / `_image_enabled` / `_comment_enabled` / `_avatar_enabled` / `_article_enabled` + 8 个 provider 凭据 |
| 敏感词 | `sensitive_words`（**必须走专用接口**，见第五节） |

### 通道 B — env（只作兜底）

改 env 仍然有效，但**必须重启**，且**只有在 DB 里没有该行或该行为空时才看得到效果**。

这是最容易踩的坑：改了 env、重启、发现没变 —— 因为 DB 里有值覆盖了它。

先确认：

```sql
SELECT key, value FROM config WHERE key = 'upload_max_image_size' AND deleted_at = 0;
```

### 通道 C — 仅 env（没有 DB key，改了必须重启）

| 项 | 为什么不能迁 |
|---|---|
| `STORAGE_DRIVER` | 启动期决定建本地还是 S3 的 client |
| `S3_ENDPOINT` / `S3_BUCKET` / `S3_ACCESS_KEY` / `S3_SECRET_KEY` / `S3_REGION` / `S3_USE_SSL` / `S3_FORCE_PATH_STYLE` | minio client 启动期创建，对象读写全走该 client。迁进 DB 会导致「前端看到 B、实际写 A」，删老文件还会删错桶 |
| `POSTGRES_*` / `REDIS_*` / `JWT_*` / `SERVER_*` / `LOG_*` / `SWAGGER_ENABLED` | 进程启动的前提（没有 DB 连接串就读不到 DB） |

**这 9 项（storage_driver + S3 七项 + 基础设施）在数据库里查不到，是设计选择。**

尝试用管理端写入这类 key 会被拒绝：

```json
{"code":400,"message":"配置项 s3_bucket 属于启动期配置（存储 / 搜索客户端在服务启动时按它初始化），写入数据库不会生效；请改环境变量或配置文件后重启服务才会生效"}
```

四个写入口都拦：`Create`(POST) / `Update`(PATCH :id) / `UpdateOne`(业务域直写) / `UpdateAll`(PATCH 批量，整批 400 回滚)。

## 三、生效时间表

| 改什么 | 生效时间 |
|---|---|
| 上传上限 / 压缩 / 缩略图 / 水印 / 本地目录 / CDN / 审核开关 | **下一个请求**（≤1 秒） |
| 搜索开关 / 地址 / 账号 / 索引名 | ≤1 秒 + 下一次用到 ES 的请求（client 按配置签名惰性重建） |
| 敏感词 | 即时（前缀树重建） |
| **用 SQL 直接改库**（绕过 API） | **≤10 分钟**（Redis 配置缓存 TTL，不会主动失效） |
| 仅 env 的项（通道 C） | 重启后 |

> 「走 API 改」会立即让缓存失效；「SQL 直改库」缓存不知道，只能等过期。**运维请优先走 API。**

## 四、密钥保护语义（重要，别踩）

`GET /config` 系列对敏感项**不会返回明文**：

```json
{
  "key": "search_password",
  "value": "***",
  "hasValue": true,
  "masked": true,
  "startupOnly": false,
  "createdAt": "...", "updatedAt": "..."
}
```

| 字段 | 含义 |
|---|---|
| `value` | 敏感项恒为 `***`（DB 有值）或空串（DB 无值） |
| `hasValue` | 后端是否真的配过值 —— **想知道「到底配没配」只能看这个** |
| `masked` | 本条是否被打码 |
| `startupOnly` | 是否为启动期配置（前端应置灰只读；即便漏判，后端也会拒写） |

**PATCH 规则**：

- 敏感项传 `""` 或 `"***"` → **不修改**，库里原值保留
- 所以前端可以安全地把读到的对象原样回传，不会把密钥覆盖成 `***`
- 想真正清空某个密钥：目前需要 SQL（`UPDATE config SET value='' WHERE key='...'`）后手动清缓存（或等 10 分钟）

**哪些是敏感项**：`s3_access_key` / `s3_secret_key` / `search_password` / `tencent_secret_id` / `tencent_secret_key` / `aliyun_access_key_id` / `aliyun_access_key_secret`，外加命名兜底（含 `password` / `secret` / `access_key` / `_token` / `private_key` 任一子串的新 key 会自动打码）。

## 五、敏感词必须走专用接口

不要用 `PATCH /config` 改 `sensitive_words`（虽然能改，但不会重建前缀树，且容易写坏 JSON）：

```bash
POST   /api/v1/config/sensitive-words          # body: {"word":"xxx"}
DELETE /api/v1/config/sensitive-words          # body: {"word":"xxx"}
POST   /api/v1/config/sensitive-words/batch    # body: {"words":["a","b"]}
DELETE /api/v1/config/sensitive-words/batch    # body: {"words":["a","b"]}
POST   /api/v1/config/sensitive-words/clear-cache
```

## 六、老库清理 SQL（升级必做一次）

`EnsureSeeds` **只插不删**。如果某个环境历史上手工插过「已废弃」或「启动期」的 key，升级它们不会被清掉，需要一次性清理：

```sql
-- 1) 预览要删什么（先跑这条，确认没有误伤）
SELECT key, value, "group"
FROM config
WHERE deleted_at = 0
  AND (
        key = 'content_audit_text_enabled'   -- 死配置：全仓无读取点，原仓库也没有这个 key
     OR key LIKE 's3\_%'                      -- S3 七项：启动期配置，不应在库里
     OR key = 'storage_driver'                -- 存储驱动：启动期配置，不应在库里
  )
ORDER BY key;

-- 2) 确认后清理（幂等，没匹配到就是 0 行）
DELETE FROM config
WHERE key = 'content_audit_text_enabled'
   OR key LIKE 's3\_%'
   OR key = 'storage_driver';

-- 3) 清掉可能残留的 Redis 配置缓存（否则最长 10 分钟内还读得到旧值）
--    Redis 里 key 形如  config:cache:<config key>
--    下面这条会删掉全部配置缓存，对业务无害（下次读取自动回填）
--    在 redis-cli 里执行：
--      EVAL "local k=redis.call('KEYS','config:cache:*') if #k>0 then return redis.call('DEL',unpack(k)) end return 0" 0
```

清理后重启一次服务，让 `EnsureSeeds` 补插缺失的种子（幂等，已有的跳过）。

## 七、升级后自检清单

```sql
-- ① 种子总数应为 56（8 个分组）
SELECT count(*) FROM config WHERE deleted_at = 0;
-- 期望 56

SELECT "group", count(*) FROM config WHERE deleted_at = 0 GROUP BY 1 ORDER BY 1;
-- 期望：advertisement 10 / audit 16 / cdn 1 / search 5 / site 10 / storage 1 / system 1 / upload 12

-- ② 确认启动期配置没有落库
SELECT count(*) FROM config WHERE deleted_at = 0 AND (key LIKE 's3\_%' OR key = 'storage_driver');
-- 期望 0

-- ③ 确认死配置没有回潮
SELECT count(*) FROM config WHERE deleted_at = 0 AND key = 'content_audit_text_enabled';
-- 期望 0
```

API 层自检：

```bash
# ④ 公开配置不含密钥（应无输出）
curl -s http://<host>/api/v1/config/public | grep -oE '"(s3_[a-z_]+|search_password|tencent_secret_key|aliyun_access_key_secret|sensitive_words)"'

# ⑤ 搜索真实可用性（别看开关字段，看这个）
curl -s http://<host>/api/v1/search/status

# ⑥ 上传配置能读到 DB 值
curl -s http://<host>/api/v1/upload/config | head -c 400
```

## 八、常见坑

| 现象 | 原因 | 处理 |
|---|---|---|
| 改了 env 并重启，配置没变 | DB config 表里有同名行，DB 优先 | 查表；或改用 API 改 DB |
| 用 SQL 改库，等了半天才生效 | Redis 配置缓存 TTL 10 分钟 | 走 API 改；或手动清 Redis（见第六节第 3 步） |
| 管理端保存密钥后，密钥变成 `***` | 前端把打码值原样写回，但版本不支持「空串/`***` 不修改」 | 本版本已修复（传 `***` 会 skip）；若仍出现，说明前端直连了旧版后端 |
| 改 `search_enabled=true` 但搜索还是不可用 | `Enabled() = 开关 && 地址非空`；地址为空视为未启用 | 同时配 `search_addresses` |
| 改 `search_articles_index` 后搜不到东西 | 新索引是空的 | 跑 `POST /api/v1/search/sync/articles` 重建索引 |
| 改 `storage_local_dir` 后老图片 URL 404 | 老文件还在老目录，DB 里的 path 指向老目录 | 改目录属运维级操作，需人工迁移文件；不要改完就删老目录 |
| 关掉压缩后上传，前端 `thumbnails` 是 `null` | 旧版本返回 jsonb `'null'` | 本版本已修为 `[]`（数组），前端可安全遍历 |
| 管理端列表里出现 `s3_bucket` 这类行 | 历史残留 | 跑第六节的清理 SQL |
