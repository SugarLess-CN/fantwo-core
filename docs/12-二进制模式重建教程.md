# 12 · 二进制模式重建教程（容器内不编译）

> 适用：`docker-compose.binary.yml` 模式 —— 容器里只跑二进制，编译在开发机完成。
> 核心优势：**升级只需换一个 68.5MB 的二进制文件，重建约 5 秒**。

---

## 一、要上传什么（一次上传，之后只换二进制）

### 首次部署：上传这 4 个

```
/opt/fantwo-core/
├── Dockerfile.binary              5.6 KB   ← 镜像定义
├── docker-compose.binary.yml      6.6 KB   ← 编排
├── .env.binary.example            9.8 KB   ← 配置模板
└── dist/
    └── fantwo-core-linux-amd64    68.5 MB  ← 二进制（压缩后约 21.6MB）
```

打成一个包（21.6MB）：

```bash
bash scripts/make-binary-pkg.sh
# 产出 dist/fantwo-core-binary-pkg-amd64.tar.gz
```

**不要上传**：源码（`cmd/` `internal/` `migrations/` `docs/` `go.mod`）、`tmp/`、`.git/`、`reports/`、`test/`。
binary 模式容器内不编译，源码完全用不到。

### 后续升级：只上传 1 个

```
dist/fantwo-core-linux-amd64      68.5 MB   ← 换掉服务器上同名文件
```

`Dockerfile.binary`、compose、`.env` 都不用动。

---

## 二、第一次部署（完整流程）

### 2.1 开发机：交叉编译

在项目根目录（Windows / macOS / Linux 都可以，**不需要 Linux 环境**）：

```bash
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 \
  go build -trimpath -ldflags="-s -w" \
  -o dist/fantwo-core-linux-amd64 ./cmd/server
```

三个参数各管一件事：

| 参数 | 作用 | 不写会怎样 |
|---|---|---|
| `CGO_ENABLED=0` | 纯静态二进制 | 动态链接 glibc，alpine 里跑不起来（报 not found） |
| `GOOS=linux` | 目标操作系统 | 编出 Windows `.exe`，容器里 exec format error |
| `GOARCH=amd64` | 目标架构 | arm64 服务器上 exec format error |

体积：**68.5 MB**（`-s -w` 去掉了调试符号，不加约 95MB）。

#### 确认架构对不对

```bash
# 服务器真实架构
uname -m
#   x86_64  → GOARCH=amd64
#   aarch64 → GOARCH=arm64
#   armv7l  → GOARCH=arm（需自行确认容器支持）
```

**ARM64 服务器**（AWS Graviton / 阿里云倚天 / 华为鲲鹏）：

```bash
CGO_ENABLED=0 GOOS=linux GOARCH=arm64 \
  go build -trimpath -ldflags="-s -w" \
  -o dist/fantwo-core-linux-arm64 ./cmd/server
```

### 2.2 打包（可选，方便一次传完）

```bash
bash scripts/make-binary-pkg.sh
```

脚本会：

1. 交叉编译（默认 amd64，可用 `ARCH=arm64 bash scripts/make-binary-pkg.sh` 换）
2. **校验产出是 ELF**（防止误编成 Windows exe 传上去，用 `cmp` 比对前 4 字节 `7f 45 4c 46`）
3. 只收集 4 个必需文件
4. 打成 `dist/fantwo-core-binary-pkg-amd64.tar.gz`（21.6MB）

### 2.3 上传

```bash
scp dist/fantwo-core-binary-pkg-amd64.tar.gz root@<服务器IP>:/opt/
```

### 2.4 服务器：解压 + 配 .env

```bash
mkdir -p /opt/fantwo-core
tar xzf /opt/fantwo-core-binary-pkg-amd64.tar.gz -C /opt/fantwo-core
cd /opt/fantwo-core

ls -R
# Dockerfile.binary  docker-compose.binary.yml  .env.binary.example  dist/

cp .env.binary.example .env
openssl rand -hex 32          # 生成 JWT_SECRET，复制输出
vim .env
```

**.env 最少改这几项**：

```ini
# 必填
JWT_SECRET=<上面 openssl 生成的那串>
POSTGRES_PASSWORD=<你的 PG 密码>

# 网络（最关键，填错服务能起但数据库全挂）
EXTERNAL_NETWORK=<PG 所在的 Docker 网络名>

# 依赖地址（用容器名，不是 127.0.0.1）
POSTGRES_HOST=<PG 容器名>
REDIS_ADDR=<Redis 容器名>:6379
```

查网络名和容器名的命令：

```bash
# PG 容器名
docker ps --format '{{.Names}}' | grep -i postgres

# 它在哪个网络
docker inspect <PG容器名> --format '{{range $k,$v := .NetworkSettings.Networks}}{{$k}} {{end}}'

# ES（需要全文检索时）
docker ps --format '{{.Names}}' | grep -i elastic
```

### 2.5 构建并启动

```bash
docker compose -f docker-compose.binary.yml up -d --build
```

输出（实测约 5 秒）：

```
 Image fantwo-core-app Building
 Image fantwo-core-app Built
 Container fantwo-core Creating
 Container fantwo-core Created
 Container fantwo-core Starting
 Container fantwo-core Started
```

### 2.6 验证

```bash
# ① 容器状态（必须 healthy，不是只 Up）
docker ps --filter name=fantwo-core --format '{{.Names}}\t{{.Status}}'

# ② 依赖连通（这是真健康，注意看 postgres 那行）
curl -s http://127.0.0.1:8079/health | python3 -m json.tool
# 期望：
#   "status": "up"
#   "dependencies": {"postgres": {"status": "up"}, "redis": {"status": "up"}}

# ③ 容器内 DNS 能解析 PG（排网络问题最快的一招）
docker exec fantwo-core ping -c 1 -W 3 <PG容器名>

# ④ 数据库已建表 + 种子（56 条）
docker exec <PG容器名> psql -U fantwo_core -d fantwo_core \
  -c "SELECT count(*) FROM config WHERE deleted_at=0;"
```

> ⚠️ `/health` 返回 200 **不代表**数据库通了。它只判 HTTP 可达，
> 依赖状态在 `data.dependencies` 里。必须看那个字段。

## 三、后续升级（只换二进制，这是 binary 模式的价值）

### 3.1 开发机

```bash
# 1) 改代码后重新编译
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 \
  go build -trimpath -ldflags="-s -w" \
  -o dist/fantwo-core-linux-amd64 ./cmd/server

# 2) 只传这一个文件（覆盖服务器上的同名文件）
scp dist/fantwo-core-linux-amd64 root@<服务器IP>:/opt/fantwo-core/dist/
```

### 3.2 服务器

```bash
cd /opt/fantwo-core
docker compose -f docker-compose.binary.yml up -d --build
```

`--build` 会让 Docker 发现 `dist/` 里的二进制变了，重新执行 `COPY`（约 5 秒），
然后重建容器。**`.env`、compose、Dockerfile 都不用动。**

### 3.3 回滚

binary 模式回滚极简单 —— 换回旧二进制即可：

```bash
# 升级前先备份
cp dist/fantwo-core-linux-amd64 dist/fantwo-core-linux-amd64.bak

# 出问题回滚
cp dist/fantwo-core-linux-amd64.bak dist/fantwo-core-linux-amd64
docker compose -f docker-compose.binary.yml up -d --build
```

> 建议按日期留几份：`fantwo-core-linux-amd64.20261124`。
> 二进制 68.5MB，留 3~5 份不占多少空间。

## 四、常见错误

| 报错 | 原因 | 解决 |
|---|---|---|
| `exec format error` | 架构不匹配（amd64 二进制跑在 arm64 上） | `uname -m` 查清，用 `GOARCH=arm64` 重编 |
| `no such file or directory`（文件明明在） | 忘了 `CGO_ENABLED=0`，动态链接找不到 glibc | 加 `CGO_ENABLED=0` 重编 |
| `failed to read dockerfile: open Dockerfile.binary: no such file` | 不在项目根目录，或没上传 Dockerfile.binary | `cd` 到 compose 所在目录 |
| `COPY failed: file not found in build context: dist/fantwo-core-linux-amd64` | `dist/` 里没有二进制，或路径不对 | 确认 `ls dist/` 有文件；或 `.env` 里改 `BINARY_PATH` |
| `hostname resolving error: lookup xxx on 127.0.0.11:53` | app 和 PG 不在同一 Docker 网络 | 查 `EXTERNAL_NETWORK`，见第五节 |
| `network xxx declared as external, but could not be found` | `EXTERNAL_NETWORK` 填了不存在的网络名 | `docker network ls` 查真实名字 |
| `Bind for 0.0.0.0:3000 failed: port is already allocated` | 宿主机端口被占（1panel 面板常占 3000） | `.env` 改 `SERVER_BIND_PORT=8079` |
| 上传的文件重建后丢失 | `uploads` 卷没挂上，或改了 `STORAGE_LOCAL_DIR` | 用命名卷（compose 已配），别改成 `./uploads` |

## 五、网络问题专项（最容易卡住的地方）

### 症状

```
failed to connect to `user=fantwo_core database=fantwo_core`:
hostname resolving error: lookup 1Panel-postgresql-Oyls on 127.0.0.11:53: no such host
```

`127.0.0.11:53` 是 Docker 内嵌 DNS，**它只解析「同一网络」里的容器名**。

### 诊断三步

```bash
# 1) PG 在哪个网络
docker inspect <PG容器名> --format '{{range $k,$v := .NetworkSettings.Networks}}{{$k}} {{end}}'

# 2) app 在哪个网络
docker inspect fantwo-core --format '{{range $k,$v := .NetworkSettings.Networks}}{{$k}} {{end}}'

# 3) 从 app 容器里直接测解析
docker exec fantwo-core ping -c 1 -W 3 <PG容器名>
```

三次输出对比，**第 1 步和第 2 步必须至少有一个共同网络名**。

### 三种修法

**A. 改 `EXTERNAL_NETWORK`（推荐，持久）**

```bash
# .env
EXTERNAL_NETWORK=<PG 所在的网络名>
```

```bash
docker compose -f docker-compose.binary.yml up -d
```

**B. 临时把 app 接进 PG 的网络（不持久，重启容器后丢失）**

```bash
docker network connect <PG的网络名> fantwo-core
docker exec fantwo-core ping -c 1 -W 3 <PG容器名>
```

**C. 不用容器名，走宿主机端口**

`.env`：

```ini
EXTERNAL_NETWORK=          # 留空
POSTGRES_HOST=host.docker.internal
REDIS_ADDR=host.docker.internal:6379
```

compose 已配 `extra_hosts: host.docker.internal:host-gateway`，
Linux 上也能解析到宿主机。前提是 PG/Redis 把端口映射到了宿主机。

## 六、与 build 模式的对比

| | binary 模式（本文档） | build 模式 |
|---|---|---|
| 编排 | `docker-compose.binary.yml` | `docker-compose.build.yml` |
| env 模板 | `.env.binary.example` | `.env.build.example` |
| 上传内容 | **二进制 68.5MB** + 3 个配置文件 | 源码（`cmd internal migrations docs` + go.mod/go.sum）1.8MB |
| 服务器需要 | 只要 Docker | 只要 Docker |
| 开发机需要 | **Go 环境** | 不需要 |
| 首次构建 | **约 5 秒** | 3~15 分钟 |
| 升级重建 | **约 5 秒** | 约 30 秒（依赖已缓存） |
| 回滚 | 换二进制文件 | 用旧 tag 或 git checkout |
| 产物 | 完全相同的运行镜像 | 完全相同的运行镜像 |

**选 binary 模式的理由**：
- 服务器网络差，拉不动 1.23GB 的 golang 镜像
- 想要秒级升级 / 回滚
- 不想让服务器装 Go 工具链

**选 build 模式的理由**：
- 开发机没装 Go
- 想让镜像完全可复现（同源码同镜像，不依赖本地环境）
- 用 CI/CD 一条命令构建

## 七、文件清单速查

| 文件 | 上传？ | 说明 |
|---|---|---|
| `Dockerfile.binary` | ✅ 首次 | 镜像定义（4 个阶段，binary 用 `from-binary`） |
| `docker-compose.binary.yml` | ✅ 首次 | 编排（只跑 app，依赖在外部容器） |
| `.env.binary.example` | ✅ 首次 | 配置模板，服务器上 `cp` 成 `.env` |
| `dist/fantwo-core-linux-amd64` | ✅ **每次升级** | 交叉编译产物 |
| `scripts/make-binary-pkg.sh` | ❌ 不用传 | 只在开发机跑 |
| `cmd/ internal/ migrations/ docs/ go.mod go.sum` | ❌ 不用传 | binary 模式容器内不编译 |
| `docker-compose.build.yml` / `.env.build.example` | ❌ 不用传 | build 模式专用（本教程是 binary 模式） |
| `tmp/ .git/ reports/ test/` | ❌ 不用传 | 与运行无关 |
